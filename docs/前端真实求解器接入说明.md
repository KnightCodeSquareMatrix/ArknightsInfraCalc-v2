## 1. Worker 连接

`infra-cli serve` 是长驻子进程，前端通过 stdin/stdout 传输 NDJSON。每行一个 JSON 对象，stdout 只能输出协议帧，日志在 stderr。

```json
{"id":0,"method":"ping","params":{}}
```

兼容 Worker 的 ping 结果包含：

```json
{
  "protocol_version": 1,
  "plan_schema_version": 1,
  "supported_plan_schema_versions": [1, 2, 3, 4, 5, 6, 7],
  "plan_contract_sha256": "<v1 sha256>",
  "plan_contract_sha256_by_version": {
    "1": "<v1 sha256>",
    "2": "<v2 sha256>",
    "3": "<v3 sha256>",
    "4": "<v4 sha256>",
    "5": "<v5 sha256>",
    "6": "<v6 sha256>",
    "7": "<v7 sha256>"
  },
  "solver_executable_sha256": "<sha256>",
  "solver_git_commit": "<commit or null>",
  "solver_built_at": "<UTC timestamp or null>"
}
```

兼容判断：

- v1 请求：`protocol_version === 1` 且 `plan_schema_version === 1`。
- v2 请求：除上述条件外，`supported_plan_schema_versions` 必须包含 `2`。
- v3 请求（使用 `options.fiammetta_enable`）：`supported_plan_schema_versions` 必须包含 `3`。
- v4 请求（显式断言与完整菲亚开关）：`supported_plan_schema_versions` 必须包含 `4`。
- v5 请求（主动组合开关和 `main_backup_24_24`）：`supported_plan_schema_versions` 必须包含 `5`。
- v6 请求：按 `contracts/plan-compute-v6.schema.json` 中的闭集 profile 发送。
- v7 请求（普通二/三班拓扑 + 时长对象）：必须确认支持版本包含 `7`，并按 `plan_contract_sha256_by_version["7"]` 校验 `contracts/plan-compute-v7.schema.json`。对象不能发送给 v6。
- 旧 Worker 没有 `supported_plan_schema_versions` 时，只发送 v1 请求。

同一 Worker 只允许一个 in-flight 请求。请求超时后终止 Worker，当前请求失败，不自动重发。

## 2. 请求版本

普通排班继续用 v1：

```json
{
  "id": 1,
  "method": "plan.compute",
  "params": {
    "schema_version": 1,
    "layout": "完整 BaseBlueprint",
    "operbox": "完整 OperBox 数组",
    "labels": {
      "layout": "243",
      "operbox": "当前干员数据"
    },
    "options": {
      "rotation": "abc_12_6_6",
      "top": 20,
      "system_preferences": {},
      "maa_title": "243 排班"
    }
  }
}
```

`12/12/12` 必须用 v2：

```json
{
  "id": 2,
  "method": "plan.compute",
  "params": {
    "schema_version": 2,
    "layout": "完整 BaseBlueprint",
    "operbox": "完整 OperBox 数组",
    "labels": {
      "layout": "243",
      "operbox": "当前干员数据"
    },
    "options": {
      "rotation": "abc_12_12_12",
      "top": 20,
      "system_preferences": {},
      "maa_title": "243 · 12/12/12 排班"
    }
  }
}
```

需要显式关闭菲亚梅塔回岗时用 v3：

```json
{
  "id": 3,
  "method": "plan.compute",
  "params": {
    "schema_version": 3,
    "layout": "完整 BaseBlueprint",
    "operbox": "完整 OperBox 数组",
    "labels": {
      "layout": "243",
      "operbox": "当前干员数据"
    },
    "options": {
      "rotation": "abc_12_6_6",
      "top": 20,
      "system_preferences": {},
      "maa_title": "243 排班",
      "fiammetta_enable": false
    }
  }
}
```

注意：`fiammetta_enable` 默认 `true`，省略即保持回岗启用；设置为 `false` 且 `rotation` 为 `fiammetta_8_8_4_4` 时请求会失败（该 profile 本身就是菲亚事件班）。

注意：`layout` 和 `operbox` 是内联对象，不是文件路径。未知字段会被 schema 拒绝；真实布局必须包含完整房间，真实干员数据必须是完整数组。

当前支持的 `rotation` wire 值：

| wire 值 | 班次 | 周期 |
|---|---:|---:|
| `abc_12_6_6` | 12/6/6 | 24h |
| `abc_12_12_12` | 12/12/12 | 36h |
| `main_backup_12_12` | 12/12 | 24h |
| `main_backup_24_24` | 24/24 | 48h |
| `fiammetta_8_8_4_4` | 8/8/4/4 | 24h |
| `abyssal_7_5_7_5` | 7/5/7/5 | 24h |

v1–v6 的 `rotation` 保持各自 schema 的 named profile 字符串闭集。v7 新增 `{"topology":"main_backup","shift_hours":[8,16]}` 与 `{"topology":"abc","shift_hours":[6,12,6]}` 两种对象；数组顺序就是班次顺序，数组长度由拓扑结构限定，具体合法时长组合由前端过滤。普通 `4`、五班及以上仍不支持。泛型输入下每个超过 12h 的班次最多生成一次菲亚动作；ABC 并列最长时休班相位放在较短班；周期由前端限制为 24h、36h 或 48h。自定义 >24h 按实际 ETA/心情准入，不复用姓名名单。

主备 24/24 named profile 从 v5 开始支持，v6/v7 继续接受 `options.rotation: "main_backup_24_24"`，应核对本次选择版本的 ping 能力及契约 hash；第 4 节 v1–v3 的 beta 迁移清单只描述历史接入步骤。返回两个 `duration_hours: 24` 状态，daily 使用 48h 周期分母；MAA 计划说明下一计划间隔 24h。

## 2.1 v7 泛型时序

需要普通二/三班自定义时长时，使用 Worker v7 topology 对象；旧 named timing 仍可在 v7 中照常使用：

```json
{"schema_version":7,"options":{"rotation":{"topology":"main_backup","shift_hours":[8,16]}}}
```

```json
{"schema_version":7,"options":{"rotation":{"topology":"abc","shift_hours":[6,12,6]}}}
```

以上是 `plan.compute.params` 的局部片段。主备与 ABC 保持各自 topology 语义，`shift_hours` 保持输入顺序。前端负责过滤不合法班数/时长组合；不要在客户端按 profile 名称恢复输出时长，读取 `rotation.shifts[].duration_hours`。v1–v6 schema 文件与 wire 含义不变，不能把 v7 对象发送给 v6。菲亚开启下泛型每个超过 12h 的班次最多一次动作；ABC 并列最长时休班相位放在较短班；周期由前端限制为 24h、36h 或 48h。自定义 >24h 按实际 ETA/心情准入，不复用姓名名单。

## 3. 读取响应

成功响应的核心形状：

```json
{
  "id": 2,
  "ok": true,
  "elapsed_ms": 1200,
  "solver": {
    "git_commit": "<commit or null>",
    "built_at": "<UTC timestamp or null>"
  },
  "result": {
    "schema_version": 2,
    "profile": {},
    "rotation": {
      "profile": "abc_12_12_12",
      "daily": {
        "trade": 5.128,
        "manufacture": 9.184,
        "power": 3.656
      },
      "shifts": []
    },
    "maa": {},
    "training_room": {
      "schema_version": 1,
      "shifts": [
        { "trainee": null, "trainer": null }
      ]
    },
    "training_advice": {
      "schema_version": 2,
      "context": {},
      "newbie_section_status": "shown",
      "incomplete_newbie": [],
      "combinations": [],
      "recommendations": []
    }
  }
}
```

前端应检查：

- `result.schema_version` 必须等于本次请求的 schema version。
- `profile.schema_version` 是画像结构版本，目前为 `4`，不要与请求版本混用。
- v7 的 `rotation.profile` 是结果侧的 scalar profile，不保证等于请求的 `options.rotation`：named 字符串请求返回对应 named profile；generic 对象若时长精确匹配 `main_backup` `[12,12]`、`[24,24]` 或 ABC `[12,6,6]`、`[12,12,12]`，会归一到对应兼容 named profile；其他 generic 主备/ABC 对象分别返回 `generic_main_backup` / `generic_abc`。实际班次时长必须读取 `rotation.shifts[].duration_hours`，不能从 profile 字符串恢复。
- `abc_12_12_12` 的 `rotation.shifts[].duration_hours` 应为 `[12, 12, 12]`。
- 三个班次的队伍关系是 `alpha+beta`、`beta+gamma`、`gamma+alpha`。
- `rotation.daily` 是周期归一化后的日均值；121212 按 36h 分母计算，不是把 36h 产出直接当成 24h 产出。
- `maa.plans[]` 可以直接用于现有排班展示和 MAA 下载。
- `training_advice` 是本次排班自动附带的练卡结果；字段、枚举和消费规则以 [FRONTEND_CLI.md](FRONTEND_CLI.md#45-training_advice排班附带的练卡建议) §4.5 为准。不要额外调用 legacy `advice --player`。
- `training_room` 是可选响应字段；若存在，`schema_version` 为 `1`，`shifts` 与 `rotation.shifts` 按位置对应。没有训练任务时 `trainee` 为 `null`，没有协助位时 `trainer` 为 `null`。字段缺失不视为错误，且不升级总体 `plan_schema_version: 3`。
- 每个 plan 的 `description` 会包含本班时长和下一次相对间隔。
- `Fiammetta.enable` 最多每个休息班一次；没有合法目标时为 `false`，不能强行补齐三次。
- `rotation.warnings` 必须展示给用户，不能静默丢弃。
- `result.error` 和顶层 `error` 均缺失才表示本次排班可执行。非 assert 求解失败仍为 `ok:false`，但会在返回 JSON 的 `result.error` 中保留同一错误；若 core 已构造真实 rotation，则同时返回该 rotation，未生成的 profile/MAA/练卡字段不补默认值。

失败响应：

```json
{
  "id": 2,
  "ok": false,
  "elapsed_ms": 80,
  "solver": {},
  "error": {
    "code": "PLAN_FAILED",
    "stage": "plan.compute",
    "message": "具体失败原因"
  }
}
```

上面的顶层失败适用于严格 `assert_invariants=true`。非 assert 请求的求解、派生或结果阶段失败仍返回 `ok:false`，并在 `result` 内嵌同形状的 `error`；只有已经真实构造的 rotation 才会随 result 返回，报告产生前失败时 `rotation` 为 `null`。请求 schema/输入准入错误在非 assert 请求中同样附带该 result 错误对象。

## 4. 前端修改清单

1. `RotationProfile` 增加 `"abc_12_12_12"`。
2. 请求类型把 `schema_version: 1` 改为 `schema_version: 1 | 2 | 3`。
3. 根据 rotation 选择请求版本：只有 `abc_12_12_12` 发送 v2；只有需要 `fiammetta_enable` 时发送 v3；其余保持 v1。
4. capability 检查支持 `supported_plan_schema_versions`，不能把 ping 的兼容字段直接改成只接受 v2。
5. 响应校验允许 `result.schema_version` 为 1、2 或 3，但必须与请求版本相等。
6. 设置 UI 增加“ABC 三班 12/12/12”，说明“36h 周期、三班各 12h”；如需提供菲亚梅塔开关，发送 v3 并在 `options.fiammetta_enable` 中显式传 `false`。
7. 结果 UI 使用 `rotation.shifts[].duration_hours` 和 `maa.plans[].description`，不要根据 profile 名称硬编码时长。
8. 保存 solver 归因时使用本次 `plan.compute` 响应里的 `solver`，不要使用最近一次 ping 的构建信息。

> 说明：上述清单针对主站 beta 前端。**内部 Check 服务是独立接入方**，固定使用
> `schema_version: 4`（含 `fiammetta_enable` 与 `assert_invariants`），并显式传
> `fiammetta_enable`（默认 `false`），详见第 5 节「Check 服务调用约定」。

当前前端对应代码位置：

- `src/types.ts`：请求类型和 `RotationProfile`
- `src/server/plan-protocol.ts`：ping 能力判断和响应版本校验
- `src/server/infra.ts`：`plan.compute` 请求组装
- `src/rotation-result.ts`：rotation 结果归一化
- `src/components/RotationSettings.tsx`：轮换设置 UI

## 5. Check 服务调用约定（内部质量页）

独立的 Check 服务仓库（`ArknightsInfraCalc-check`）通过本 Worker 的 `plan.compute`
发起批量验证。它固定使用 **`schema_version: 4`**，并对菲亚梅塔使用**显式传参**，
不依赖默认值：

- Check 请求总是显式携带 `options.fiammetta_enable`，值为 `true` 或 `false`，绝不省略。
- Check 层默认值为 `false`（默认关闭菲亚梅塔回岗），与 Worker 侧默认 `true` 相反。
  因此 Check 必须显式传参，否则会得到与页面预期相反的排班。
- 手动 Check 页面与 `/api/quality/production-boxes` 输入使用 `fiammettaEnabled`（camelCase），
  由 runner 在组装 `plan.compute` 时映射为 `options.fiammetta_enable`。
- 选择 `fiammetta_8_8_4_4` 轮换时，Check 页面会强制启用菲亚梅塔（该 profile 本身就是菲亚事件班），
  不会发送 `fiammetta_enable: false`。
- Check 还会在需要时传入 `options.assert_invariants`（v4 新增），与 CLI `plan --assert-invariants`
  相同的 Rust invariant gate。

对接或排查 Check 请求时，可在存储目录 `v2/attempts/objects/<uuid>/serve-request.json` 查看实际
发出的请求，确认 `schema_version` 与 `options.fiammetta_enable` 是否符合预期。
