## 结论

主体复用了普通排班的 Plan、Peak、互斥备班、设施搜索和补位，没有重建实际换班事件或恢复模拟。最新 H1/H2 规则和挂件选人纠正已经接通。但“主力优先”存在明确的顺序偏差：备班中枢先占用人，之后才搜索主力生产岗位。性能差距主要来自新增自动准入在组合内反复重建全站状态，不是问题规模要求多搜几十倍。

模糊点的处理不是一律未经授权：禁令、1+1、菲亚、时长等经过问答；双中枢预算是 Agent 提出并在方案中披露后获得整体授权。没有清楚交代的，是为满足双中枢预算而调整主备分配优先级的代价，以及把有限建议问题实现成每候选全站检查、终态指数枚举的成本。

## 2. “主力优先”具体怎样被改变

当前次序：主中枢 → 备中枢 → 从主力候选中剔除备中枢成员 → 主力全部岗位 → 其余备班岗位。

`auto_rotation.rs:156` 的 `main_available = operbox.excluding(backup_seed.work_position_operator_names(...))` 是直接证据。主力尚未形成，备班已经拥有最多五个排他成员。后面的“主力冻结、替补不动主力”只能保证冻结之后，不保证最初的主力优先。

影响不局限于具备中枢技能的人：`pool/control.rs:78` 将真实无中枢技能成员也放入 filler，`search/control.rs:1126-1212` 最后从此池补位。例如 Castle-3 的运行时有制造技能、无中枢技能（`data/operator_instances.json:46`）；若它被备中枢当普通占位成员选走，就不会再进入主力制造候选。这是依据池、排序、排除链推导的可达结构，未运行具体Box，不能声称某个现有账号已经这样选。

这不是“不承诺全局最优”的同义词。heuristic 允许在既定优先级内近似搜索，不自动允许把替补席位放到主力生产之前。修复目标是兼顾两中枢预算和主力优先；但不能据此保证第一次选出的任意主力都存在兼容备中枢。实施阶段已静态证明c267固定玛恩纳主中枢及斥罪主办公室后，在当前模型中不存在能让斥罪撑满24小时的互斥备中枢；必要回选与保留主力报不可行之间的产品取舍，见[活动计划第8节](../../TODO/自动轮换主力优先与准入性能修复.md#8-u3静态冲突证据与待裁决2026-10-30)。该补充纠正审计阶段尚未证明的可行性前提，不以历史成功输出代替语义裁决。

## 4. 性能损耗：静态上能直接定位

### 4.1 每个候选都做全站准入

制造 `search/manufacture.rs:420-438` 在每个组合评分前进 `candidate_admitted`；贸易 `search/trade.rs:414-436,577`、发电 `search/power.rs:126` 有同类入口。普通模式在准入函数入口立即返回，自动模式在 `admission.rs@ef286fe:205-275` 做：

1. 深复制全部 `station_presence`，包括成员姓名、buff、tag；覆盖候选房。
2. 每个完整组合按两个中枢检查H；`station_fits_work_duration:146-176` 每次再次 clone 完整 LayoutContext 和站位，随后才调用实际 mood owner。
3. 调 `admitted` 重查整套成员关系。
4. mixed 检查重建另一态＋共享宿舍，再把候选与其余房的主/备状态逐对组合，每对再调 `admitted`。

18房/4宿舍蓝图在两份presence均覆盖全房时，普通非宿舍候选最多触发 `1次当前全态 + 1次另一全态 + 2×(14−1)次房对 = 28次 admitted`；提前拒绝时减少。这是静态调用上界，不是实测计数。其中“另一整态＋不变宿舍”在同一房搜索中甚至不依赖本次候选，却被每个候选重复验证。

### 4.2 OnceCell 只缓存一次检查内部

`admitted:666` 新建 OnceCell，遇到资源读取才调用 `resource_providers:431`，但函数返回后缓存就丢掉。下一候选、下一pair又从头算。

资源来源构建不仅扫标签：还 clone LayoutContext、重建实际成员集合和资源池、运行中枢带trace结算、发电结算、global atoms和转换来源传播。它正确复用原机制公式，却在组合热循环里重复执行了本可按固定环境和候选变更拆开的工作。

来源确实可能因候选变化，不能把上一候选的全部结果直接套用；可复用的是固定房事实、不受该候选影响的依赖与按真实变更失效的结果。先查不受影响部分、只重算受影响闭包，不需要删除候选或降低保证。

### 4.3 终态指数枚举重复两遍，空房还扩大4倍

`all_station_states_admitted:372-417` 为每个非宿舍房选择主/备，只要成员、依赖或H不同就分支；每叶再次全站准入、所有普通岗位ETA。`presence:61` 把H赋给所有蓝图房，包括空加工站和空训练室。因此24/12下即使两房都没人，也因H不同产生分支。

历史243蓝图14个非宿舍房：每次16,384叶，12个普通工作房共196,608次房间预算检查。空工坊和空训练室造成纯粹的4倍冗余，消掉这两个分支不改变任何人的合法性。

`schedule/auto_rotation.rs:242` 交付前执行一遍，`:371` 显式assert又执行一遍，所以开assert时共32,768叶、393,216次预算检查。不能把它误说成“每个候选都做2^R”：候选里主要是全态和房对检查，指数遍历在终态。

终态独立证明应保留；算法可以利用等价状态、按房及两中枢复用预算。资源阈值或组合条件的分解需证明覆盖，不能因当前数据简单就只保留任意两房测试并声称等价。

### 4.4 已排除的主因

- 不是反复展开大量自动中枢producer masks：`pipeline.rs:190` 的auto动态producer集合为空，mask只有1个。
- 不是单纯候选规模更大：已有同账号制造auto229,231个，三班1,107,390个，auto反而少约79%。
- 不是排序：auto制造排序/物化约0.049s，evaluate约34.393s。
- 不是普通resolve调用次数：auto59次约0.018s；这个计数不涵盖准入内部资源重建，不能拿它证明跨站计算很便宜。
- auto确实禁Bake，但比较中的普通两/三班也全部miss，故无法用Bake命中差解释这轮差距。请求级memo还在；没有“auto禁了全部cache”的证据。
