## 5. 调查问题与结论摘要

### 5.1 v3 单房求解与交接接口（workflow `wf_f3984508-f3f`，7 题全部完成；报告 `target/codex-runs/v3-room-api/`）

主代理已回原文核对的（标 ✔）与只采信报告的（标 ○）：

- ✔ v3 `room_search::search_room_combo(capacity, candidates, required, evaluate)` 是通用全量 C(n,k) DFS，只留最优，无剪枝、无查表；比较键 total → final_efficiency → tie_break（`v3 src/room_search.rs:50-144`）。
- ✔ 贸易调用时 `total` 和 `final_efficiency` 都填 `settlement.final_efficiency`（`v3 src/trade.rs:1703-1706`），所以贸易实际按 final_efficiency 比，再按 tie_break；与 ADR 0013 D3 不冲突。room_search.rs:22-23 注释说 total 不含倍率，与贸易实际用法不一致（注释问题）。
- ✔ v3 制造也用同一个 `search_room_combo`（`v3 src/compat.rs:968`），接口对两域通用。
- ✔ v3 上层逐房贪心：`fill_rooms_with_combo_search` 开头算一次 ctx（`compat.rs:2217`），按“金单贸易房在前”排房，逐房搜、满员才 `commit_searched_room`，整轮重复到无变化（`compat.rs:2218-2260`）。○ 杜林人数与外部虚拟线逐房读运行态、含已提交房；中枢在场、宿舍、金线不刷新（v3-outer-caller 第 5 条）。
- ○ v3 贸易核心：每类核心只产一个候选（但书/可露希尔用全两人对烘焙后取第一个可用；巫恋第三人 裁缝β→α→任意 先成功先停），再按 final_efficiency 比；`gold_core_chain` 无生产调用（v2-fixed-cores）。
- ○ v3 文档自述：`TradeRoomContext` 没建；多站顺序没实现；逐房顺序依赖没修（v6-docs）。
- ○ v3 身份层：`OperatorId=u16`、编译期 `build.rs` 生成定长表与函数指针；v2 全是字符串名 + 运行时 SkillTable，无 build.rs（v5-identity-data）。所以 v3 的“快”主要来自身份/生成层，搬 `room_search` 本身不带来性能。
- ○ v3 `data/baked/baked_manufacture.bin` 未跟踪、代码无引用（v4-manufacture-room）。
- ✔ v2 单房搜索也是全量 C(n,k)（`v2 search/trade.rs:376` `combinations_indices`），must-include 枚举后 retain；先经工具人白名单收窄、有回退全池；保存全部命中后排序取 best 与 top_k（`:429-443`）；bake 命中可跳过枚举（`:340-368`，规则路径实际 Disabled）。每组合调 `solve_trade_with_shift_prevalidated`（`:551`），结算读 LayoutContext 约 30 个字段（v7 报告表格）。

对搬迁的含义（主代理推断，待写进规格给用户审）：
1. v2 和 v3 的单房搜索算法形状相同（全枚举 + 完整结算），差别在接口：v3 是“候选 + 必含 + 结算闭包 → 最优”，外部事实显式传入；v2 是“池 + 过滤器 + LayoutContext → 排好序的全部命中”。
2. 第一步可以只搬接口形状：在 v2 建通用单房枚举 + 贸易结算闭包，外部事实收成一个显式结构；旧的 `search_trade_triples_filtered` 作对拍基准。
3. 需要先定的差异：v2 消费者用 top-K 列表（如 `pick_disjoint_from_report`），v3 只返回最优；v2 排序键 `trade_efficiency_sort_key` 与 v3 tie_break 分类不同。对拍阶段先保持 v2 排序键，行为一致后再议。
