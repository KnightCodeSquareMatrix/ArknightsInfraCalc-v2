## 2. 为什么重复检查、普通路径如何解决

### 2.1 问题来源是把“禁用组合”扩大成“每次重新证明全站无任何禁用关系”

普通选人用Plan给定required、排除和局部禁配，使用已过滤候选池评分，赢家提交时维护占用。自动复用这条路径后，又新增了`CandidateAdmission`：每个候选替换本房，再解释全站实际技能和来源；替补还配对另一态；Plan叶、支援设施/普通补位再用更宽的`assignment_admitted`；结束后精确枚举任意主备混搭。这些检查保护的主要是**禁用体系被关掉后，普通零散成员仍可能偶发触发同类协同**。

动态关系不是凭空重复：新增一个成员确实可能激活已选房技能；若坚持旧的“所有潜在混搭绝无违规”，只删调用会失去该保证。但用户当前明确优先简化并允许损失正确性，不能继续拿这个更强目标迫使求解器每层证明。最主要的错误是**我把当前昂贵实现的保证当作必须保留的目标**，提出少量精查而没有按普通路径删工作。

历史证据也能解释转向：ADR0014 §2.4原拟“分类在候选进入处过滤＋最终断言”；该文§五明确记录后来改成“Plan能力限制及运行时atom/委托/支援注册表来源准入”（`:147,238`）。当前`admission.rs:835-1088`继续细分实际成员、阈值、零净值资源、转换来源。用户没有要求逐候选执行这些算法；这些是Agent为覆盖边缘关系作出的实现选择，不应再用它证明“自动本来就复杂”。

### 3.1 最重要的乘法：1次或27次，而非“一个布尔检查”

`CandidateAdmission::admitted`普通在`:281`直接true。主力构造时另一态为空，auto每个完整候选先算预算再执行1次当前全站`admitted`。替补构造时，当前完整态1次，`mixed_candidate_pairs_admitted:404-435`再对当前态和主态其他非宿舍房分别检查。

在候选RoomId正确落到实际房间的生产入口，243蓝图18房，其中4宿舍、14非宿舍：候选自身房被排除，剩余最多`2×(14−1)=26`房对，因此一次备候选最多**27次admitted**，外加每次搜索首次1次“固定主态＋共享宿舍”检查。此26房对循环**没有过滤空房**，空工坊/训练室也在内。若候选房定位失败而走`candidate_<facility>`合成房fallback（`:304`），会多出一个房身份，以上27不是通用上界：可能28次；当前实际RoomId路径才按27计。与前轮28次不同，U1已缓存其中候选无关的另一整态；不能把被删除的那1次再算进当前每候选成本。

更重的是`assignment_admitted:121-133`：它调用`mixed_station_pairs_admitted:453-490`，遍历两态所有非空房状态的两两配对。12工作房各两态都有人时，共24房态，排除同房主备，配对数为`C(24,2)-12=264`。该外壳并不只在最后调用；会客室双人候选、Plan角色叶和普通补位也会调用。每候选可能支付1次当前整态＋1次主态＋264房对，而变化实际只在一个房。这解释了后备会客室/补位也明显变慢的结构原因。

这些pair用于保护额外的跨态协同保证。当前两整态合法不推出任意混搭合法；本轮按用户简化方向删除这层证明并公开该损失，不再为保留它设计缓存。

### 3.2 已选资源消费者让无关候选反复跑解释器

`admitted:845`的OnceCell只活一次admitted；`resource_reads:600`反复从atom创建并规范化资源名字。只要**任意已选房**有资源读取，当前候选即使没有资源技能也可能触发`resource_providers`。

具体已保存结果：高411最新主制造3是冬时/清流/温蒂，温蒂`manu_prod_spd&power[010]/[020]`使用`PowerStationCount`。`response_dependency.rs:1070-1092`把它视为读取virtual_power。备制造4是斑点/玛露西尔/苍苔，玛露西尔`manu_prod_spd_bd[400]`读取MonsterCuisine。后续检查全态时，这些固定消费者重复触发来源重建。

来源重建会恢复初始global、重算在岗/平台/精英设施统计，遍历所有技能写入，必要时执行`solve_control_with_trace:673`、`solve_power`、`orchestrate_global_atoms_with_writes:769`、`run_conversions_with_trace:801`，最后才判断有无禁用外部来源。它保护的是“实际上触发的跨站关系”，成本远高于名字集合查询；仅提前编译“是否读资源”不能自动省掉动态来源证明。

这并不说明所有候选都跑完整资源链：没有资源读取就不会触发；某个pair没带资源消费者也不会触发；先前拒绝会短路。这里是已证实的触发条件，而非虚构调用占比。

- `resolve.rs:188`把`BaseAssignment.auto_other_presence`深clone后装Arc，U1只让后续`LayoutContext.clone`共享；每次resolve入口仍复制这份Vec。
- 制造/贸易在调用admission前都构造候选成员String/buff/tag，即使普通模式最终直接true；这项分配是**共同残留成本**，不能全部归因auto，自动启用时则还继续上面检查。

这里记录的是旧实现内的重复工作。随全站证明删除的循环和解析直接消失；不再逐项缓存或另建依赖图。

## 4. 终态枚举到底还剩多少，取消会损失什么

当前U2已合并空非工作房的纯H差异；243的12个普通工作房在auto24/12下仍各有两态，因此每次交付检查最多**4096叶**，显式assert再4096叶。37份已保存成功产物均有这12房结构。空普通工作房即使两态都空，因H不同也仍分支；这还有等价去重空间。

每叶仍调用完整`admitted`，再统计深海人数、逐工作房查`BTreeMap`预算。**预算公式并非每叶重算**：非中枢最多各房两态×两中枢，中枢附加实际深海数；U2已缓存。同态重复协同/resource解释则没有类似缓存。直接去掉双中枢工时，不会自动省掉大量协同/resource成本。

候选不是每次做4096遍；指数枚举只在终态两处。已有日志主要时间在Peak候选，不能看到指数数字就把它当全部瓶颈。

便宜检查不等价的反例：中枢布丁需两个发电平台才激活制造+2。构造主态布丁＋只有power_1平台，备态普通中枢＋只有power_2平台：两个同步态都未激活；每个“布丁中枢＋单个发电房”pair也不到阈值，但独立混搭布丁＋两个平台会激活禁用跨站效果。这是基于`control_token_prod_spd[000]`及`admission:986`阈值的静态反例，不声称本轮实际solver会主动生成该组合。旧consumer `gate-final.rs:106-117`已验证1平台/2平台阈值语义，但未运行本轮构造。

当前方向直接删除这种协同穷举，并撤销“已证明所有混搭无禁用协同”的保证；不要求先实现规则可达性、保守资源上界或有限抽样检查来替代它。上面的反例用于诚实描述损失，不能再成为继续保留昂贵结构的理由。各房H与双中枢预算单独用§6.3的小规模检查保留。

## 5. 已排除或不能夸大的归因

1. **不是auto两份独立大排班之外又多一个轮换求解器**：主、备各走公共Peak，普通主备也两次。auto少了时间线、宿舍恢复、MAA/profile；dynamic producer masks为空（`pipeline:190`），甚至少做分支。
2. **不是auto独有全候选生成和排序**：制造/贸易两模式都枚举同域`C(n,k)`、完整评分后排序取K。auto取消≥12h负心情差身份过滤，可能多算部分候选，属于用户已裁定的机制处理；历史同盒auto候选反而少，不能当主要数量原因。
3. **调小现有top-K省不到主体**：`manufacture:469-497`、`trade:441-469`在全量准入/评分后才截取；只减少物化/输出/部分后续组合，不减少本次C个准入。
4. **Bake禁用属实，不等于本次差距来自Bake**：普通高411最新已有trace中制造10次、贸易8次全部live；制造layout不匹配、贸易layout/predicate miss。恢复auto入口也会被`bake.rs:3652`完整layout兼容拒绝；直接删除auto分支不足以提速。强用不兼容旧表则是额外评分近似，不应暗渡。
5. **memo没被全部关闭**：制造/贸易仍有请求内memo，auto完整站位键更严格；去掉站位键会跨依赖状态复用错误合法性。可把“排名候选缓存”和“实际准入”分开，但这是后续有证据再做的责任拆分，不是先删键。
6. **普通resolve计数不能代表资源证明次数**：`resource_providers`内部重演不经`resolve_base`同一统计入口；说“resolve仅几十毫秒所以跨站计算不贵”是错归因。
7. **中枢当前是逐层greedy**：不是auto额外全五人组合搜索；但它走全operbox无技能filler并且每前缀/完整候选有自动准入，完整回调还重新new准备对象（`control_fill:288-314`），比制造/贸易缓存生命周期更短。两个入口都选中枢，不能把auto的两次select_control都当纯新增工作。
8. **共享挂件的整域二次比较已删除**：`rules:1680`的`role.competitive && !optional_dorm_support`排除了自动挂件分支；不能因旁边还存在`score_completed_*`函数就认定旧问题未修。其它竞争角色的共同工作另算。

## 6. 当前实施方案：删掉额外层，回到受限的普通流水线

### 6.1 行为与状态顺序

输入仍是盒、蓝图、H1/H2。开始就得到本模式允许的规则/alternatives；禁用项根本不进入递归、完整组合补全或registry。主中枢按已有光环优先策略确定，主力沿公共Plan→execute→设施搜索→普通补位完成并冻结。替补排除全部主力工作成员、继承常驻宿舍，选择备中枢并检查固定主力H1，再沿同一流程形成H2的替补。备阶段失败报告固定主力下未找到兼容方案，绝不回选主力。

搜索内部只保留原有身份/容量/required/同房限制、原公式评分，以及**本房实际组合**的工作时长判断。它不接收全站技能关系待证明的任务，不计算候选房×其他房对，不对不变的房重演资源来源。支援设施和普通补位走相同原则。

结果仍是两套真实快照和逐站主备建议；不输出平均日收益。原`resolve`和设施solver用于结算实际选中的组合，不修改或屏蔽技能atom，不把禁用功能模拟成“游戏里不存在该技能”。发现零散成员意外触发协同是新的近似边界；不得为了抹平它又补回全站解释器。

### 6.3 时长不是全站合法性解释器

用户最新明确保留双中枢预算，所以不以提速为由放行c267式不足24小时结果。`mood/drain.rs::room_workable_hours_with_control`已有窄接口，不需要资源来源/协同判定。

- 主中枢及主房候选只按H1和实际主中枢试算；不预占备班成员。未补齐前缀不以临时ETA淘汰。
- 固定主力后，备中枢完整候选才检查自身H2与固定主房H1；与前缀协同校验分离。不要在每个普通备房候选重新复核全部主力。
- 备工作房仅对本房最终组合检查H2和实际两中枢；补位只复核改变的完整房间。
- 终态对各房两份名单×两套中枢检查，不枚举全部房组合。当前mood owner非中枢仅依赖本房/中枢；中枢额外读取外站深海人数（`drain.rs:156-194`）。需要保持任意混搭工时，按各非中枢非宿舍房主/备深海人数取max再求和即可得到此加耗项的最坏输入；两个中枢分别取自己的实际成员。当前`control_tag_drain`只按该数增加0.5/h，单调性明确。不用复制公式，仍传给原mood函数。未来新增其他外站心情依赖应在该owner处理，不能假定这个上界永远覆盖。
- 显式assert独立重建同一预算输入即可；正常运行交付H校验一次，调试/验收复核一次，成本不再乘候选数×全站协同。没有为了省微小公式开销改变H或暖机窗口。

这一预算分解是依据当前代码的实现事实；本轮没有变更游戏机制，因此不扩展心情资料审计或新增近似公式。

### 6.4 允许例外与近似代价的边界

宿舍1＋1仍沿原规则临时挂件环境和原设施搜索；受益者赢才提交已有anchor/dependency，落选整体回退。不新增全基建收益比较。共享挂件的显式角色不得同时被两个可共存工作房认领，可在Plan合并/角色提交时按已有实际依赖登记一次；同一房主备互斥仍能共享。该小表只管理**显式选中的角色**，不重新扫描所有成员的潜在buff，也不生成另一套资源图。

自动化只保留既有发电＋制造alternatives，去掉中枢森蚺；普通局部搜索、实际发电资源与效率照常结算。禁止规则不会因为散件缺人而恢复。禁组合不等于把组成者的所有其他设施身份删出盒；无需为弥补边缘情况维护干员姓名黑名单。

明确接受的损失是：普通散件可能意外激活某个被禁止的成员关系，多个独立主备切换也可能触发高阶效果；不再声称枚举证明了“任意混搭无禁用协同”。例如§4布丁＋两发电房平台的三房阈值反例，正是删这层保证的代价。单站候选排名、实际技能效率公式和主力冻结仍沿原owner；全局最优原本也未承诺。

静态目录只证明不主动搜索那些体系，**不证明其组成者永远不可能自然凑齐**。四赤金规则/完整核心搜索必须不可达；不要为了禁止其所有偶然激活再补资源trace。如果用户后续要求某一个例外必须严格禁止，单独在最早候选owner用现成的局部能力/组合约束表达，不把此报告再回退为普遍全站证明。

没有采用上一轮建议的L、近似评分或保守误杀整个能力类别。这样首先移除自动特有的乘法工作，而不额外缩小普通单站搜索或再创造一套搜索policy。

P1是安全删除当前不可成功的registry与只有单候选的比较外壳；生产填充顺序及Plan必须实际复核，不能为了抽函数引入第二套填充实现。P2/P3删除全协同证明属于明确的保证降级/approximation，不是结果等价优化。预算分解按当前mood依赖是等价/保守最坏输入计算，仍调用真实mood owner。

实施约束：

- `auto_rotation`同时控制H、制造负心情差政策和输出；不得靠设置false一次关掉所有新逻辑。
- 目录过滤前于Plan角色递归，禁止项不要进入fallback；贸易现fallback会清`hit_filter`（`trade_fill.rs:782-786`），不能把持久禁令塞在可清的role筛选中。
- `full_pool`仍来自基础受限池；临时挂件受益者必须能以真实身份参选，不能变must。
- 删除全站presence时，不删预算所需的实际两中枢、固定主力及H，也不删真实效率layout。memo键只随实际输入删除无消费者字段，不任意合并仍有结算差异的状态。
- 在P1处理固定主中枢的流水线入口时核对缺员中枢：Plan若增加同中枢成员，用实际最终名单建立后续预算。备中枢增加/补位后仅在状态真正变化的提交边界复核固定主力，不能把最终一次核对漏掉，也不能据此恢复每个生产候选重查全部主力。
- 不删除普通路径的终态检查、夜烟归属比较、单站正常搜索，不扩大为全求解器重构。它们不是被禁大体系，也不是本轮自动特有证明成本。

验证控制在静态闭环后一次完整release包；失败集中修完再重跑相应完整包：

1. 静态调用检查：`rg`所有旧准入/混搭入口，证明生产调用已归零或定义一并删除；核对auto registry不进入`plan_registry_system_detailed`、无动态producer多前缀包装；无需profile表。
2. 最小临时消费者覆盖：允许单站、1＋1、发电制造仍可进入；四赤金/红松/迷迭香大体系/中枢森蚺从Plan不可达；full_pool与缺员fallback不能重启被删组合。检查的是规则选择/搜索入口，不要求新近似模式通过已撤销的偶发协同断言。
3. 固定主力与预算：构造旧c267主名单/中枢的明确冲突，必须失败且未改人；普通完整auto输入的“第一次完成主力”等于最终主力。新搜索政策允许第一次主力与旧版本不同，不能强制真实c267永远选旧人；无论选谁都必须满足新H合同。补位后房内ETA、两中枢及最坏外站深海人数有合法/不合法两侧。
4. 结构与例外：重复工作成员、错Plan anchor、宿舍双可共存受益者、时长不足等变异被新gate拒绝；布丁三房阈值这类旧额外协同保证明确不再验收，不能继续把它当回归失败。
5. 一轮auto38持久盒release `--assert-invariants`，普通两/三班各一高盒完整产物对拍。按真实错误分类，不保证38全成功，也不删样本掩盖失败。运行上述门禁使用`arknights-invariant-gate`；不新增大批源码测试，不运行全库测试。
6. 最多一组同盒普通/auto时间对照及必要调用计数；只有实际测得才能说提速倍数。不测也能依据调用结构确认全站证明归零，但不能保证总耗时一定低于每一个普通输入。
7. 文档三检查、`cargo fmt --all`、diff检查。实施完成后按项目完成门禁交独立`arknights-intent-review`；用户另行要求的最终复审仍由后续新会话处理。前轮通过记录不能认证新保证变更。
