## 状态所有权

    BaseBlueprint + OperBox + Plan
      → BaseAssignment（岗位事实）
      → resolve_base / evaluate_base_assignment_efficiencies
      → TeamShiftResult（时长、动作、效率）
      → MaaSchedule（外部 JSON）

BaseAssignment 是房间和干员唯一 owner。ShiftEfficiencies 是快照，不修改岗位。MaaSchedule 是外部输出，不是第二份 solver 状态。

## BaseAssignment

字段包括 rooms[].room_id、rooms[].operators[].name/elite、training_assist、base_workforce 和可选 notes。缺省房间为空；同一 assignment 内同名干员不得占多岗位。跨班复用由 profile policy 决定。

## 效率快照

evaluate_base_assignment_efficiencies 先 resolve_base，再读取 trade/manufacture/power breakdown，聚合 ShiftEfficiencies 和 RoomEfficiencyLine，最后按班次时长得到 weighted 值。三类效率不混量纲。average_cycle_production 对全部班次按真实时长加权，再归一到 24h。

## MAA 写出

MaaSchedule.plans[i] 对应 TeamRotationReport.shifts[i]。房间按蓝图顺序生成，生产房带 product，功能房只带 operators。菲亚直接使用 shift.fiammetta；无人机用 shift.drone.room_id 映射制造 index；宿舍 warning 可设置 autofill，但不重选成员。planTimes 由 profile 决定，触发时刻由 MAA/人工执行者负责。

`rooms.recycle` 按 MAA 官方协议示例投影：每个蓝图回收站对应一个 `{ "operators": [...] }`，只读取同一最终 assignment 中该房间的成员；不生成 A/B、不在导出层补位。官方 schema 将 `recycle` 限制为最多一个通用 `roomConfig`，A/B 仅用于训练室；当前排班导出不扩展 MAA 读回能力。旧 A/B 草案与来源差异见 [回收站设计稿 §7](../TODO/回收站选人放人与轮换设计.md#7-plancompute-v6-契约)。

## MAA 读回

load_maa_schedule 读取、去 BOM、反序列化；assignment_from_maa_plan 只读取未 skip 的 trading/manufacture/power/dormitory/control，elite 从 OperBox 查询，缺省为 0。读回不恢复菲亚、无人机、meeting/hire/processing、profile、绑定或机制 dependency；调用方须显式 resolve/评估。

## 错误

JSON 解析、目录创建和写入失败都带路径返回。room_id 映射不到制造房时 export 使用 index=1，这只是输出兜底；跨班问题必须回到 rotation report。

## 外部岗位名与内部房间名

MAA 的 hire 对应内部 FacilityKind::Office，meeting 对应 MeetingRoom，processing 对应 Workshop。trading/manufacture/power 按蓝图房间数组顺序写出 index；control 只有存在中枢时输出一个 shared slot。文档或修复若混用 office/hire，先确认是在内部状态还是 MAA schema。

生产产品映射固定为：TradeOrderKind::Gold → LMD、Originium → Orundum；RecipeKind::BattleRecord → Battle Record、Gold/All → Pure Gold、Originium → Originium Shard。这个映射只在 export 层用于字段投影，不改变效率或求解目标。

## 为什么不能在 export 修复状态

MaaPlan 只保存岗位列表和执行动作，不保存 Plan owner、runtime bind、机制 dependency、ETA 或 profile policy。export 层新增成员会绕过 occupancy、capacity、resolve_base 和 invariant；删成员则可能使已确认的 producer/consumer 链失效。任何岗位错误都应回到 TeamShiftResult.assignment 和其 owner Plan。
