## 单站结算

```text
TradeRoomInput
 -> TradeContext::from_room
 -> collect_atoms + apply_trade_phases (L1)
 -> order_mechanic::resolve_order_mechanic (L2)
 -> shortcut::resolve_trade_shortcut (L3, 赤金且真实组合)
 -> unit_output + TradeEfficiency
 -> TradeResult / TradeProductionReport
```

`solve_trade_with_shift` 校验源石订单等级和同站互斥；搜索热路径使用已预筛的 prevalidated 入口。L1 按 `Phase::sort_key/phase_order` 处理 state、eff、limit、order tag、peer absorb 和 mood。L2 根据等级、订单标签、gold flow 和特殊订单生成分布与等效解释。赤金链从 `OperatorInstances` 的运行时 buff 读取真实线与全局虚拟线：绮良的门槛只按真实线取整，鸿雪按实际杜林在岗人数供线（至多四人），同房先扣自身供线再按进驻及 buff 顺序重放；源石贸易站在岗的供线者也会进入全局赤金线账本。L3 只在真实三人组、tier、互斥和 `GlobalInjectManifest` 均满足时命中；未命中回 L2。

shortcut 的 `mechanic_equivalent_efficiency` 是解释字段；`unit_output` 是实际产出锚。最终日产出由 `TradeProductionReport` 计算，CLI 不重算。

整体同站互斥在一次检查内复用已识别的但书、巫恋侧和佩佩特征，不在子判定中重复识别；独立佩佩互斥入口与整体检查共用同一效率人判定。规则、按 buff/tier 的身份来源、互斥计数位置与 prevalidated 求解边界保持。

## 2026-10-30 用户裁决：全局供线与进驻顺序

来源为本轮用户直接说明，优先于技能字面描述；按用户要求不另做游戏机制考据：绮良、鸿雪提供的赤金生产线都是全局的，三核心同站或分站不改变这条赤金线协同本身。此处的等价不包含更换队友造成的房间效率变化，也不把现有固定分房策略解释为技能的同房限制。

用户同时指出游戏内同站进驻顺序会影响结算，指定统一采用 **绮良 → 鸿雪 → 图耶**。搜索候选和单班收尾已有该顺序；公共排班 `finalize_timed_rotation` 在全部工作补位完成后、宿舍收尾及最终效率重算前，通过 `BaseAssignment::sort_trade_gold_flow_operators` 再规范贸易房顺序，宿舍候选及提示也读取这份已排序的工作名单。同房仅有其中两人时沿用相对顺序，其他设施尤其宿舍不参与这次排序；排序不改变房间成员、跨房分配或核心准入。MAA/报告忠实消费最终 assignment，`gold_flow_room_order` 终态断言检查实际金单贸易房的顺序。

本条落实进驻顺序约束，不修改现有结算公式，也不启动四赤金候选枚举重构。未来枚举不应把三核心同房/分房本身当作赤金线协同收益差异；分房仍可因队友搭配影响总收益。

## 搜索与跨站

特殊订单的单房候选比较使用 `TradeEfficiency::final_efficiency`：它把基础、技能和全局效率计入纸面总效率，再乘特殊订单单位产出倍率。`mechanic_equivalent_efficiency` 是机制解释值，不能再加一次。`search_trade_triples`、`role_pick` 和普通金贸鸿雪+图耶补入比较已在 breakdown 存在时读取 `final_efficiency`（`ddf5218`）；不能因 `total_efficiency` 字段仍存在于 wire/breakdown 就宣称其他消费者也已统一。排班逐房与周期汇总现在也沿用该 final；纸面 total、equivalent 解释和实际单位产出公式不变。`TradeSearchOrderMode::Stations` 分别求赤金/源石，再按站数加权复合；它不是单房 comparator 的直接复用。两条真实赤金线的金单域搜索会把同时在池中的鸿雪与图耶补入散件缩池，保留普通同房候选。`role_pick` 仅消费 Plan 声明的 core/role；`trade_fill` 在最新 resolve 快照和 `used` 下先填 required core，再补普通合法候选。

`pozyomka_durin` 是 Trade Core 候选中的专用跨站候选，不是独立排班模式或普通 `trade_core` 之外的另一套选择体系。它仅在四条真实赤金制造线、三核心均精二、四名杜林可兑现且赤金金单贸易站恰为两座或三座时准入。两站布局固定为绮良独站、鸿雪+图耶同站；三站布局固定三人分站。巫恋、龙舌兰、但书、可露希尔只作优先建议；缺失或建议固定填房失败时可省略，失败的建议干员重新进入普通 Trade 搜索。核心整体填房或中枢容量无法成立时回退普通贸易 Plan，不保留半套核心。旧同房三人 `single_trade_gold_flow` 已删除；普通 trade search 仍可按通常规则得到同房结果，但这不再是该成套核心。分类和候选关系见 [ADR 0013](../ADR/0013-four-gold-trade-core-candidate.md)。

建议失败的类型化重试接在 Peak 候选正常填房入口；后续夜烟双侧重算仍使用无建议来源的填房入口，并清空生产占用。当前没有四赤金与该重算同时触发的真实 witness，未证明该交叉路径的建议退回或核心保留，不能从普通入口矩阵推导为所有路径覆盖。

该核心的最终状态由 rotation invariant 从各班最终 assignment 验证：ABC 核心同组两上休一，其他 profile 按各自团队拓扑同上同下，宿舍不计工作；休班三人都不得出现在工作岗位，实际工作班分别符合所选两站/三站几何。当前 Plan 选择仍按优先级提交首个可行方案，没有把四赤金完整 assignment 与普通完整 Trade Plan 同场比较。用户 10-20 已明确单房最终比较字段为 `TradeEfficiency::final_efficiency`，即技能效率已计入纸面总效率、再乘特殊订单单位产出倍率；不得改用仅纸面 `total_efficiency`，也不得二次累加机制解释值。完整候选的比较时间窗（单次 Peak 或完整周期）、多贸易站聚合与并列裁决尚未唯一规定，见 [ADR 0013](../ADR/0013-four-gold-trade-core-candidate.md)；在这些规则裁决前，不声称该择优已实现。单房搜索 consumer 已改用该字段；排班逐房与周期汇总也已改用该字段，但动态 producer 的跨域 weighted policy 仍读取纸面口径。因此当前候选排序不能证明跨完整方案或全局最优。

## 失败定位

- 有人无技能：回输入→tier→instances→skill table→pool。
- 纸面效率对、产出错：查 order mechanic、shortcut、unit output 顺序。
- shortcut 误命中：查 `trade_station_exclusive_violation`、segment producer、manifest 和真实组合。
- 单房对、多房错：查 resolve snapshot、tag count 和跨站注入；不要先改 unit output。

核验：`infra-cli verify --case`、`trade yield`、`search trade`、`layout eval --explain-json`；机制常数回知识库桥接。

自动建议贸易候选通过共同模式准入检查实际跨站成员，gold_flow::reads_virtual_lines提供委托依赖；四赤金拒绝，普通同站组合保留。候选/快照使用自身窗口。宿舍1＋1竞争沿Plan角色完成调用既有trade填充，必须保留required。
## 喀兰身份与选人边界（2026-10-30）

锏两档实例具有 `cc.g.karlan`，身份沿 `operator_instances.json → instances::tags_for → TradeContext::seed_karlan_precision` 生效。固定知识库 `977b6ab0` 的《技能-控制中枢》谢拉格名册与《喀兰贸易组》121% / 精零孑峰值145%为来源，用户本日要求纠正旧结算。

`trade_ord_spd_variable3[000]` 冠军风采读取非负的干员净上限贡献，不含设施基础上限，也不含孑的效率压缩量；按每5个上限增加25%效率、最多100%。它必须先于市井之道压缩结算。运行时映射采用同一 `Limit` 阶段的显式顺序：上限增减（order≤40）→冠军风采效率写入 settled（50）→市井之道读取其他人 settled 压缩（60）；随后订单数/差值效率按最终上限结算。招商引资仍在后续 `LimitVar` 读取压缩后的净上限，不随冠军风采前移。L1 根据 action/selector/phase 解释，不按姓名补偿，编译 atom 与普通 atom 两条路径保持一致。

三级站灵知中枢＋银灰、孑、锏：干员上限净贡献为 `(4+6)+(-6+6)=10`，冠军风采提供50%；孑读取 `(20-15)+(25-15)+50=65%`，压缩6个订单，最终上限 `10+10-6=14`；技能效率 `5+10+50+14×4=121%`，含基础与三人进驻为2.24。旧141%来自冠军风采在孑压缩之后才生效，导致少压5个订单，多算20%。精零孑没有压缩，零订单峰值为145%；无灵知时上限净贡献为负，冠军风采提供0%，不产生负效率。该修正作用于实际房间结算与消费该结算的搜索/排班，不改变候选准入策略。

喀兰贸易 role 仍可供显式角色请求使用，但普通补位不再优先返回该角色；灵知的可选中枢分支不预占贸易成员，队友落选即淘汰。实际候选比较、上下班依赖与部分搜索边界见 [中枢编制](../CONTROL_CENTER_ASSIGNMENT.md#灵知可选协同2026-10-30)。

赤金终态断言比较赤金链执行前后的个人效率增量，隔离灵知等预置上下文；完整房间收益仍独立核对，合法喀兰预置不作为赤金链错误。

2026-10-31主分支整合后，生产release临时探针验证灵知＋孑＋银灰＋锏的精一121%/上限14、精零零订单145%/上限20，compiled/plain两条解释路径均通过。真实CLI固定编制精一121%；精零`order_count=None`沿既定空满平均为105%，与零订单峰值区分。证据见`target/codex-runs/main-integration-20261031/trade-order-probe.*`及`trade-order-cli/`，未新增源码测试。
