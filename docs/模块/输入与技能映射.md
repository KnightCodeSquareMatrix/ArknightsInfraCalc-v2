## 输入到运行时能力

```text
OperBox/OperatorProgress
  -> PromotionTier
  -> OperatorInstances facility binding
  -> buff_id(s)
  -> SkillTable::dense_id_of -> get_by_dense_id -> EffectAtom / L2 marker
  -> facility pool entry
  -> room input -> domain interpreter
```

`OperBox` 保存账号持有、精英、等级和潜能；`PromotionTier` 将进度压成 `tier_0` 或 `tier_up`。`tier_0` 对应上游 phase 0；`tier_up` 按星级取真实解锁阶段：1–2 星为 30 级，3–4 星为精一，5–6 星为精二，已精二一律为 `tier_up`，星级未知时按 5–6 星保守处理（`crates/infra-core/src/tier.rs`）。运行时只有这两档，机制、倍率和候选逻辑以档位及其解析出的 `buff_id` 为输入。`OperatorInstances` 按姓名、tier 和设施返回绑定，`resolve_buff_ids` 在 tier_up 时可合并 tier_0 的 stepwise binding。`SkillTable` 只把 buff id 映射到运行时定义，不裁决游戏原文。

加载每份 `SkillTable` 时，按文件顺序分配 `u16` 稠密 buff 编号，字符串索引只保存编号，技能定义只保留一份数组；`get` 冷接口仍返回同一份定义，`index_of` 为 O(1)。编号有效范围为 `0..skills.len()`，最多 65,536 项，超出即加载失败。`OperatorInstances` 按原始 `name@tier` 键建立姓名编号、姓名表和档位索引，`get` 不再每次格式化键；`id_of`、`name_of`、`get_by_id` 可直接按姓名编号访问。姓名编号同样最多 65,536 项，溢出加载失败。

这些编号只属于当前加载的表，不是跨版本持久化 ID，也不由 `build.rs` 固化。运行时数据目录和独立路径加载仍可替换两张表；`SkillTable::load` 不额外读取 instances。加载时为每个已定义技能缓存按 phase、phase_order、原始 seq 排序的 `Arc` 原子数组；整段有序 buff 序列首次编译后缓存，后续建池复用同一个 `Arc`。排序仍保留原有 `u16` seq 饱和语义。

当前数据含 326 个技能定义、451 个 instances 引用 buff，其中 126 个引用没有定义，另有 1 个定义未被 instances 引用。因此稠密编号覆盖 326 个已定义技能，并不表示 451 个引用全部建模；表外 buff 继续返回 `None`，编译时跳过、候选池按原有 `UnmodeledBuff` 拒绝，未提供空白高效技能。44 个已定义空技能仍拥有编号和空原子数组，制造池原有 L2 delegate 判定保持不变。以上数量是当前载体快照，替换运行时表后以加载结果为准。

缺失姓名、设施、tier 或 buff id 时，pool builder 记录 skip/error；不会创建白板高效技能。重复/非法输入由 CLI 输入层 fail-closed。`data/tags` 只供 Selector/Condition，不能替代 Plan admission 或组合优先级。

## 候选池

`build_trade_pool`、`build_manufacture_pool`、`build_control_pool`、`build_power_pool` 各自构造条目并附带 compiled atoms、tier、tags 与 skip reason。`filter_*_pool` 再应用 `used`、exclusion、设施能力和 `full_pool`。standalone pool 只由明确的独立搜索入口使用。

诊断“为什么未进池”应按：输入姓名 → tier → facility binding → buff_id → skill table → pool skip → Plan/used 排除；最后才看域内排序。

自动排班按主力/替补H分别冻结`OperBox`设施ETA资格；同一干员在一个设施不合格不删除其他设施资格。`with_auto_roster_eta`调用既有净心情消耗与预算公式，规则选人、设施roster及普通技能候选共同消费；办公室、会客室即时建池同样覆盖。`manufacture`实例设施键在消费资格时映射到心情模型的`factory`键，避免制造池绕过初始试算。同一设施多房的资格取各房试算交集，属于保守policy，不证明最优；原始owned保持完整供结算和随机Fallback使用；Fallback不查技能实例或ETA。

## 核验

2026-11-05：用户要求检查所有设施放人路径，随后明确“已有心情检查的不需要管”“保留 Fallback 例外，只修正常技能与体系选人路径”。正常单班、定时主备与ABC的非中枢候选补齐初始设施资格，复用自动排班已有公式。单班与主备用已有owner的`options.shift_hours`，ABC用已有Peak窗口`H1 + max(H2, H3)`；已有中枢检查与窗口保持原样。`with_roster_eta`只在尚未初筛时建立资格；`with_auto_roster_eta`仍按明确给定的H重建资格。过滤map保留空设施项，避免“无人被排除”被误认为“未初筛”。规则、legacy固定/PickOne、设施roster、锚点注入和体系producer共同消费资格。普通Fallback例外保留；本次属于候选范围policy修复，不改净耗公式、组合诊断或保证最优。

`SkillTable::validate_operator_refs` 当前仅检查trade/recycle的instances→table引用，不证明全设施覆盖；`infra-cli pool --trade/--manufacture` 输出池和跳过原因；`layout eval --explain-json` 验证端到端映射。技能数值和解锁规则回知识库引用，不能以 fixture 旧输出当真源。

## 缺失条目与委托的区分

缺SkillTable条目或空atom不能单独判定缺机制：办公室/会客室另有SupportRegistry，宿舍与指定中枢配对恢复由mood owner，空atom可明确委托。上文126缺引用、44空定义是载体数量，不是bug计数；须逐项核对设施、buff来源、delegate与pool skip，不由检索器拼接技能公式。原始记录用`query_runtime_data.py`保留两个tier、stepwise与JSON Pointer。
