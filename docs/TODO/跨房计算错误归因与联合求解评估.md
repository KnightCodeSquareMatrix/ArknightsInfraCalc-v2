# 跨房计算错误归因与联合求解评估

> 文档角色：active-change
> 生命周期状态：proposal
> 当前真源：docs/QUALITY_AND_AUDIT.md；docs/BASE_ASSIGNMENT.md；docs/CONTROL_CENTER_ASSIGNMENT.md；docs/ORCHESTRATION_LAYER.md
> 摘要：收集跨房错误样本，定位首次违规层，再判断局部修复或联合求解边界

## 1. 当前状态

用户准备整理一批跨房计算 bug。本任务先保存调查入口，不授权实现 CSP、CP-SAT、全局联合
求解或排班重构，也不把当前算法假设写成已确认根因。

当前已知实现事实是单班生产设施采用分阶段、逐房搜索；贸易和制造多房结果仍受具名有序
填房 policy 限制，不宣称全基建全局最优。每个具体 bug 仍须从用户预期、canonical 语义和
真实输入开始复现，不能从这项已知限制直接推断根因。

## 2. 调查目标

1. 收集用户可观察的错误结果及其完整输入。
2. 为每个 bug 构造稳定复现和尽可能小的相邻反例。
3. 定位第一次产生错误状态的责任层，而不是只定位最终错误输出。
4. 区分 owner-local bug、候选完整性问题、错误分解、具名 policy 限制和真实联合求解缺口。
5. 根据证据决定局部修复、conformance rebuild、恢复既有 exact-joint 任务，或明确维持
   `POLICY_OPTIMAL` / `BEST_FOUND` 保证。

## 3. Bug 记录模板

每个案例单独增加一个小节，至少填写：

```text
BUG-ID / 简称：
用户观察到的结果：
用户认为正确的结果及依据：
layout / operbox / assignment / policy：
真实入口和完整命令：
实际输出与产物：
是否稳定复现：
调换房间顺序是否改变结果：
关闭 Bake 后是否改变结果：
最小反例：
相邻反例：
固定 assignment 的正式结算是否正确：
首次违规层：待调查
保证等级：待调查
结论与 owner：待调查
```

用户尚未提供的字段保留为“待补”，不能用当前 top hit 或 Agent 推测代填。

## 4. 根因分类

调查时优先按下表分类；分类是诊断结果，不是预设答案。

| 类别 | 判定信号 | 首查 owner |
|---|---|---|
| 固定组合结算错误 | 给定完整 assignment 仍算错效率或作用域 | L1/L2/L3、`resolve_base`、数据 |
| 候选生成不完整 | 合法成员或组合未进入搜索 | pool、role/capability 扩池、search |
| Plan admission 错误 | required、alternative、排除或降级先错 | Rule/System → Plan → Execute |
| 人员互斥或提交错误 | 重复上岗、错误抢占、anchor 被覆盖 | `used`、commit、fill |
| 上下文可见性错误 | 前房看不到后房最终 workforce 或资源 | 跨房分解、candidate projection、resolve 时机 |
| 目标或比较器错误 | 候选都合法且结算正确，但 winner 口径错误 | scoring policy、tie-break |
| 条件签名错误 | 逐房分布、阈值或 presence 被错误聚合 | response dependency、effect signature |
| Cache/Bake 语义漂移 | live 与 Bake 的候选或 winner 不一致 | Bake gate、catalog、fallback |
| 仅排班或导出错误 | 单班 assignment 正确，Shift/MAA 才错误 | rotation、shift bind、export |

## 5. 当前待验证假设

以下只是可能解释 bug 的调查方向：

- 逐房 `resolve → search → commit` 使前房选择无法利用后房最终成员。
- 最终 snapshot refresh 只能重算已选组合，不能重新选择前房候选。
- 多房争抢同一干员时，局部最优可能阻止更优的合法组合。
- 可选 producer 与 consumer 互相影响时，独立选型可能漏掉共同胜出的候选。
- 聚合计数可能错误合并本应保留逐房向量的 response。
- standalone、结构化扩池、top-K 或 Bake 兼容门禁可能改变候选完整性。

每项假设必须由真实反例、关闭对应 reduction/policy 的差分或小规模 oracle 证实。没有证据时
不得把“跨房错误”统一归因于逐房贪心，也不得直接宣布 CSP 是必要修复。

## 6. 归因流程

1. 先确认用户预期是否已有 canonical 依据；没有时先请求领域裁决。
2. 对用户真实入口留存证据，再缩成最小 layout / operbox。
3. 固定最终 assignment 重算各房，先区分“结算错”与“选型错”。
4. 对选型错案例检查候选全集、Plan、`used`、room order 和上下文快照。
5. 对疑似分解问题建立小规模暴力 oracle，比较当前有序 fill 与完整合法 tuple。
6. 声明候选、剪枝、分解和结果的保证等级，并记录未覆盖空间。
7. 每个 bug 归入唯一实现 owner；不同根因拆成独立修复任务，不用一个 CSP 改造包兜底。

## 7. 与现有 TODO 的边界

- [动态 Producer A+](DYNAMIC_PRODUCER_BAKED_SEARCH_PLAN.md) 负责已经裁决的动态 producer 候选列、
  exact indexed join 和 winner dependency；只有 bug 证据命中其恢复条件时才恢复。
- [设施无关条件化响应 Bake](CONDITIONAL_ROOM_RESPONSE_BAKE_PLAN.md) 负责条件响应物化和缓存安全；
  Bake 不是跨房正确性的真源。
- [近期已知缺口修复清单](近期已知缺口修复清单.md) 第 4 项继续负责制造逐房贪心的既有
  solver-assurance 调查。
- 本文件只负责新 bug 的收集、归因和路由，不拥有机制公式、领域语义或最终求解器设计。

## 8. 进入设计或实现的门禁

只有完成相关 bug 的最小复现和首次违规层判断后，才选择改动形态：

| 证据结论 | 后续动作 |
|---|---|
| 固定 assignment 已算错 | 修复对应机制、数据或 resolve owner |
| 候选漏入但分解无关 | 修复 pool / eligibility / Plan owner |
| 房间顺序改变非等价 winner | 评估受影响闭包内的联合选择 |
| producer/consumer bootstrap 漏解 | 按现有 A+ 恢复条件评估 exact joint |
| live 正确、Bake 错误 | 独立处理 cache/Bake conformance |
| 仅超出具名 policy，但无产品 exact 要求 | 保持 policy 并准确报告结果状态 |

若最终需要联合求解，优先复用正式单房 solver，把房间合法组合表示为候选行，由约束层处理
人员互斥、容量、anchor 和跨房兼容；不能把技能公式复制进 CSP，也不能让可选 producer 变成
required admission。具体算法和后端必须在 bug 归因后另行冻结，不由本 proposal 预先裁决。

## 9. 完成标准

- 用户提供的每个 bug 都有真实入口、最小反例、相邻反例和证据路径。
- 每个 bug 都区分用户事实、canonical 规则、实现事实、Agent 推断和关键未知项。
- 每个错误都定位到首次违规层和唯一 owner，并声明搜索保证等级。
- 需要实现的事项已按根因拆分或恢复现有 TODO；不相关发现明确 deferred。
- 若调查结束后没有联合求解必要，也明确记录为什么局部修复或现有 policy 足够。

完成归因后，本文件吸收稳定调查结论并按文档生命周期归档；实际修复由各自任务关闭，不把
长期领域事实留在本 TODO 中。

## 10. 当前案例结论

### 10.1 194249 / 望与阿米娅注入冲突反馈

- **用户观察**：同一班中枢同时出现望与阿米娅，认为两人的 `+7%` 效果重复。
- **固定编制入口**：对反馈 bundle 当前重跑生成的第二班 assignment 执行
  `layout eval --explain-json`；本地证据为
  `target/codex-runs/control-feedback-classification/artifacts/194249-shift2-explain.json`。
- **实现事实**：该布局制造站多于贸易站与发电站之和，望的贸易 `+7%` 条件失败，制造
  `+2%` 进入 `manu_global_all` 并成为 winner；阿米娅的贸易 `+7%` 独立进入
  `trade_global_flat` 并成为 winner。二者目标设施与 family 不同，没有发生同族错误覆盖。
- **分类**：**非 bug（仅限本固定 assignment 的该项结算反馈）**。
- **未覆盖**：自动候选选择、其他班次、房间顺序敏感性和全局最优性；本结论不能外推为这些
  路径已经验收。

### 10.2 195034 / Passion 与赤金制造展示差异

- **用户观察**：房间技能效率为 `76%`、展示为 `82%`，界面差值看似 `+6%`；用户按
  初华与睦合计 `40 Passion -> +2%`、Mon3tr `+2%` 推断不应达到 `+6%`。
- **固定编制入口**：对反馈 bundle 当前重跑生成的第二班 assignment 执行
  `layout eval --explain-json`；本地证据为
  `target/codex-runs/control-feedback-classification/artifacts/195034-shift2-explain.json`。
- **实现事实**：trace 从零状态开始，三角初华按宿舍规划人数写入 `20 Passion`，若叶睦再写入
  `20 Passion`，最终为 `40`。当前数据使丰川祥子产生赤金固定 `+1%` 与
  `floor(40 / 20) * 1% = +2%`，Mon3tr 另提供全制造 `+2%`，因此固定编制的真实
  `global_efficiency` 为 `+5%`。制造展示值相对房内 `skill_efficiency` 多出的 `+6%` 则由
  三人进驻 `occupancy +3%`、祥子固定项 `+1%`、Passion 项 `+2%` 构成；该差值不能整体称为
  跨设施注入。
- **canonical 状态**：`EFFICIENCY_MODEL.md` 已裁决三人进驻 `+3%`；
  `EFFECT_ATOM_DESIGN.md` 与条件响应 Bake TODO 已记录 Passion consumer 和祥子 `/20` bucket。
  但祥子高阶技能是否还包含固定 `+1%`，当前只见于 generated registry 与运行时数据，尚无
  canonical Markdown 或用户裁决。
- **分类**：**实现分解已查明，领域语义待用户裁决，暂不判 bug / 非 bug**。
- **待裁决问题**：丰川祥子高阶「丰富工作经验」是否为“生产贵金属固定 `+1%`，并且每
  `20 Passion` 再 `+1%`”？裁决前不得修改公式；旧界面是否把 occupancy 差值误标为
  “跨设施”也需原始 UI 产物才能单独关闭。
