## 2. 结论与建议裁定

前轮5.2倍主要消掉的是深拷贝、候选无关另一态重查和终态重复ETA，不是取消昂贵算法。剩余核心差距仍在**每候选全站语义判定**，且低频外壳`assignment_admitted`实际上被会客室双人枚举、补位和Plan叶高频调用。自动模式候选不一定更多，而是对每个候选做了普通路径没有的完整证明。

用户允许牺牲正确性后，推荐先接受**有限候选导致漏解/少给选择**，再考虑保守拒绝少量合法跨站组合；无需先接受重复占人、错误效率、假装撑满H。最高价值路线是**先评分排序，再少量精查**。继续只做分配/缓存优化能改善，但仍保留“候选数×全站检查数”的乘法结构。

严格区分三类损失：

1. **找到的建议合法，但可能找不到已有解或漏掉更优组合**：限制精查数量、候选池或近似评分；本轮建议优先使用。
2. **扩大禁令，少放一些本来合法的组合**：保守依赖签名，忽略激活阈值/零净产出的放行情形；换取便宜、易预测的检查。
3. **成功输出也可能违反混搭协同或工时要求**：取消混搭/两中枢保证；这是可选的极限速度政策，不应把它写成前两类的同义词。

最新“第一次主力绝不改”继续保留。上述取舍允许改变最初的候选搜索政策，但第一次主力完成后仍不回选。全局最优原本就未保证，不能用一句“本来就是heuristic”掩盖新增的漏解边界。

### 3.1 最重要的乘法：1次或27次，而非“一个布尔检查”

`CandidateAdmission::admitted`普通在`:281`直接true。主力构造时另一态为空，auto每个完整候选先算预算再执行1次当前全站`admitted`。替补构造时，当前完整态1次，`mixed_candidate_pairs_admitted:404-435`再对当前态和主态其他非宿舍房分别检查。

在候选RoomId正确落到实际房间的生产入口，243蓝图18房，其中4宿舍、14非宿舍：候选自身房被排除，剩余最多`2×(14−1)=26`房对，因此一次备候选最多**27次admitted**，外加每次搜索首次1次“固定主态＋共享宿舍”检查。此26房对循环**没有过滤空房**，空工坊/训练室也在内。若候选房定位失败而走`candidate_<facility>`合成房fallback（`:304`），会多出一个房身份，以上27不是通用上界：可能28次；当前实际RoomId路径才按27计。与前轮28次不同，U1已缓存其中候选无关的另一整态；不能把被删除的那1次再算进当前每候选成本。

更重的是`assignment_admitted:121-133`：它调用`mixed_station_pairs_admitted:453-490`，遍历两态所有非空房状态的两两配对。12工作房各两态都有人时，共24房态，排除同房主备，配对数为`C(24,2)-12=264`。该外壳并不只在最后调用；会客室双人候选、Plan角色叶和普通补位也会调用。每候选可能支付1次当前整态＋1次主态＋264房对，而变化实际只在一个房。这解释了后备会客室/补位也明显变慢的结构原因。

不能未经条件证明直接删所有pair：当前全态与另一全态合法，不推出任意跨态可共存房都合法。但固定房之间的判定、候选对本态房的重复关系有可复用空间。

### 3.2 已选资源消费者让无关候选反复跑解释器

`admitted:845`的OnceCell只活一次admitted；`resource_reads:600`反复从atom创建并规范化资源名字。只要**任意已选房**有资源读取，当前候选即使没有资源技能也可能触发`resource_providers`。

具体已保存结果：高411最新主制造3是冬时/清流/温蒂，温蒂`manu_prod_spd&power[010]/[020]`使用`PowerStationCount`。`response_dependency.rs:1070-1092`把它视为读取virtual_power。备制造4是斑点/玛露西尔/苍苔，玛露西尔`manu_prod_spd_bd[400]`读取MonsterCuisine。后续检查全态时，这些固定消费者重复触发来源重建。

来源重建会恢复初始global、重算在岗/平台/精英设施统计，遍历所有技能写入，必要时执行`solve_control_with_trace:673`、`solve_power`、`orchestrate_global_atoms_with_writes:769`、`run_conversions_with_trace:801`，最后才判断有无禁用外部来源。它保护的是“实际上触发的跨站关系”，成本远高于名字集合查询；仅提前编译“是否读资源”不能自动省掉动态来源证明。

这并不说明所有候选都跑完整资源链：没有资源读取就不会触发；某个pair没带资源消费者也不会触发；先前拒绝会短路。这里是已证实的触发条件，而非虚构调用占比。

### 3.3 仍有可直接裁掉的循环与分配

- `admitted:973`在**每个atom**上统计外站平台数，然后才match是否PlatformCountGte/OtherPlatformInPower；无关普通atom也付出扫描。可以先按依赖类型分派，单次视图预统计，不损合法性。
- 既有固定房的buff、selector、condition、resource名称每次整态/房对重新解析；可按实际skill tier准备规则签名，但不能把“拥有跨站能力”误等于“当前触发”。
- `station_fits_work_duration:164`无论是否中枢都扫描外站深海人数，只有中枢预算实际读取；终态已规避部分key维度，候选入口仍扫。
- 每个预算构造中枢String名单，`mood/drain.rs:128`再构造本房String名单，通常同一房检查两次中枢；可借用或缓存两中枢按设施恢复项。`default_mood_model`已有OnceLock，不是每次读JSON。
- `resolve.rs:188`把`BaseAssignment.auto_other_presence`深clone后装Arc，U1只让后续`LayoutContext.clone`共享；每次resolve入口仍复制这份Vec。
- 制造/贸易在调用admission前都构造候选成员String/buff/tag，即使普通模式最终直接true；这项分配是**共同残留成本**，不能全部归因auto，自动启用时则还继续上面检查。

这些是低风险补充，价值排在消除候选乘法之后；不建议为它们先做大规模依赖图框架。

## 4. 终态枚举到底还剩多少，取消会损失什么

当前U2已合并空非工作房的纯H差异；243的12个普通工作房在auto24/12下仍各有两态，因此每次交付检查最多**4096叶**，显式assert再4096叶。37份已保存成功产物均有这12房结构。空普通工作房即使两态都空，因H不同也仍分支；这还有等价去重空间。

每叶仍调用完整`admitted`，再统计深海人数、逐工作房查`BTreeMap`预算。**预算公式并非每叶重算**：非中枢最多各房两态×两中枢，中枢附加实际深海数；U2已缓存。同态重复协同/resource解释则没有类似缓存。直接去掉双中枢工时，不会自动省掉大量协同/resource成本。

候选不是每次做4096遍；指数枚举只在终态两处。已有日志主要时间在Peak候选，不能看到指数数字就把它当全部瓶颈。

便宜检查不等价的反例：中枢布丁需两个发电平台才激活制造+2。构造主态布丁＋只有power_1平台，备态普通中枢＋只有power_2平台：两个同步态都未激活；每个“布丁中枢＋单个发电房”pair也不到阈值，但独立混搭布丁＋两个平台会激活禁用跨站效果。这是基于`control_token_prod_spd[000]`及`admission:986`阈值的静态反例，不声称本轮实际solver会主动生成该组合。旧consumer `gate-final.rs:106-117`已验证1平台/2平台阈值语义，但未运行本轮构造。

因此取消4096叶有三种明确方式：

- 保留精确来源规则，改成规则相关的可达性/阈值见证：可以等价，但实现证明成本较高。
- 采用保守规则：能跨房/跨态凑出潜在依赖就拒绝，阈值和净零不再精确区分。更快，可能误杀原本合法组合。
- 只查同步两态或有限混搭：最简单，允许上例漏检；必须把输出保证降级，不声称各房随意切都合法。若严格assert仍穷举，开发批量可能合法失败；不能为追求全绿悄悄删断言。

把同房主备并集当实际成员不是好替代：会让互斥人同时存在，虚构平台、人数、来源抵消和双受益者。若用于保守“潜在能力集合”，必须标明只是上界并证明不漏真实激活，不能拿合并后的普通结算直接判定。

## 5. 已排除或不能夸大的归因

1. **不是auto两份独立大排班之外又多一个轮换求解器**：主、备各走公共Peak，普通主备也两次。auto少了时间线、宿舍恢复、MAA/profile；dynamic producer masks为空（`pipeline:190`），甚至少做分支。
2. **不是auto独有全候选生成和排序**：制造/贸易两模式都枚举同域`C(n,k)`、完整评分后排序取K。auto取消≥12h负心情差身份过滤，可能多算部分候选，属于用户已裁定的机制处理；历史同盒auto候选反而少，不能当主要数量原因。
3. **调小现有top-K省不到主体**：`manufacture:469-497`、`trade:441-469`在全量准入/评分后才截取；只减少物化/输出/部分后续组合，不减少本次C个准入。
4. **Bake禁用属实，不等于本次差距来自Bake**：普通高411最新已有trace中制造10次、贸易8次全部live；制造layout不匹配、贸易layout/predicate miss。恢复auto入口也会被`bake.rs:3652`完整layout兼容拒绝；直接删除auto分支不足以提速。强用不兼容旧表则是额外评分近似，不应暗渡。
5. **memo没被全部关闭**：制造/贸易仍有请求内memo，auto完整站位键更严格；去掉站位键会跨依赖状态复用错误合法性。可把“排名候选缓存”和“实际准入”分开，但这是后续有证据再做的责任拆分，不是先删键。
6. **普通resolve计数不能代表资源证明次数**：`resource_providers`内部重演不经`resolve_base`同一统计入口；说“resolve仅几十毫秒所以跨站计算不贵”是错归因。
7. **中枢当前是逐层greedy**：不是auto额外全五人组合搜索；但它走全operbox无技能filler并且每前缀/完整候选有自动准入，完整回调还重新new准备对象（`control_fill:288-314`），比制造/贸易缓存生命周期更短。两个入口都选中枢，不能把auto的两次select_control都当纯新增工作。
8. **共享挂件的整域二次比较已删除**：`rules:1680`的`role.competitive && !optional_dorm_support`排除了自动挂件分支；不能因旁边还存在`score_completed_*`函数就认定旧问题未修。其它竞争角色的共同工作另算。

## 6. 可执行提速路线与正确性代价

### A. 首选：把完整准入从全量候选循环移到有序候选前缀

当前对C个候选逐一“预算→全态/房对→评分”。改为：保留廉价身份、必需成员、同房禁配和真实评分窗口，先生成评分候选，按原次序/比较器排好；从高到低执行现有完整准入，凑够所需合法`best/top`就停止。

设需返回K个合法候选，实际检查S个，主体从`C×(评分+准入)`变为`C×评分+S×准入`。通常希望S接近K，但非法高分项很多时S可等于C；而且会评分原来早早拒绝的项，所以**没有静态保证的加速倍数或最坏提速**。

在固定搜索环境、评分不修改环境、合法性不改变候选分数、原排序保序的前提下：`take_K(filter_valid(sort_score(C)))`与现结果`take_K(sort_score(filter_valid(C)))`返回相同合法best/top。这是可以不牺牲选中结果的算法换序。现有admission只返回bool，唯一准备缓存是候选无关的OnceLock；资源计算也在局部layout上重演。评分中的隐含panic/precondition仍须在实施时核对，不能直接令所有非法输入穿透机制solver。

具体owner：制造`search/manufacture.rs:416-546`、贸易`search/trade.rs:398-476,584-628`。不得用`layout.auto_rotation=false`来跳过准入，因为该位也决定窗口、制造≥12h政策与其他行为。拆开“同房/评分”与“auto admission”的本次调用责任即可，不做另一套机制公式。

关键兼容：

- 制造保留效率→仓库→姓名排序。贸易目前效率平分依赖原indexed枚举和稳定排序；不能换不稳定heap后随意改变平分顺序。
- `top_k=0`仍需返回至少1个合法best；先应用must/override、hit_filter和forbidden pairs再计数。未知有副作用的predicate不要换序。
- `evaluated`现在是全空间合法hit数。停止扫描后不知道该值，不能填成“全部评分数”继续冒充同一指标。调试/统计口径需明确“已评分/已精查/合法已发现”，或仅保留已知统计；auto不接Bake对账，普通和Bake保持原口径。此处是可接受但需公开记录的输出统计变化。
- memo仍按全部依赖身份缓存最终合法report；新近似policy/L若可配置，须进key。不能先缓存未检查top命中再当合法返回。

### B. 用户允许牺牲后优先加：精查数量上限L

A的扫描设置上限，首轮建议`L=max(64,4×max(K,1))`（K=20时L=80）。这是**未测的起始policy**，不是已证明最优参数，也不应加成到处可配置的产品开关。超过L不继续全量精查，不无界扩大重试。

损失具体是：若前L个高分组合都非法而第L+1个合法，会提早给出“候选预算内未找到合法组合”；不能说无解。已找到的合法best在原精确排序下仍是最高的合法项，找到不足K会减少后续选人可用分支；全局组合搜索可能因此少产出。若再用近似评分选前L，则还可能选中较差但合法的组。

主力阶段L耗尽按既有缺员/错误规则处理，不回溯已完成主力；备班耗尽继续保留固定主力错误上下文。不要通过重复返回原最差候选、缩H或跳过最终合法性掩盖耗尽。

**建议初步裁定**：接受漏解/少给top，不接受把未精查候选当成功结果；保留最终精确gate。这样把主要性能损失从C次完整证明降到有上限的L次，而无需先撤销双中枢。

### C. 必须配套处理高频支援/补位入口

只改制造/贸易会遗留会客室O(n²)候选上的`assignment_admitted`全房对检查。会客候选先原公式排序，再逐个查预算与协同，沿用并列和失败退回规则；办公室已有`rank_candidates`，补位按有序候选做到首个合法即停，复用同一试放presence，避免同trial两次全站构造。

候选只改变本房时，复用`CandidateAdmission`的本房投影与固定另一态准备。会客/办公室`StationPresence.support_dependencies`来自独立support registry，现CandidateAdmission构造候选时把它置空（`:332`），**不能机械替换**：需要携带该实际候选的support_dependencies，否则漏掉精英设施、中枢成员或资源依赖。原有完整终态检查继续从assignment重建，不消费“搜索通过”的标记。

中枢完整eligibility准备对象应在一次fill调用外建立并与前缀复用，不在每个完整候选new；固定主力两中枢H检查保留。发电按每实际目标房准备，提交成员后失效；不能跨房盲用旧视图。

### D. 仍要更快时：保守依赖签名，换掉大量动态来源解释

按真实`buff_id+tier+facility`在搜索开始准备“读哪些成员/标签/资源、允许例外、潜在producer/converter”集合；只检查本候选与受影响固定房的关系。宿舍挂件1+1、同房主备互斥、发电制造例外仍单独表达。没有相关依赖就直接通过，避免每个纯效率atom都扫平台/资源。

若要简化动态激活证明，可规定“出现潜在禁用外站依赖就拒绝”，不区分当前阈值未到、资源净零、某转换未激活。代价是误杀合法组合。例如布丁只有1个平台目前合法，保守策略会拒绝；絮雨一级办公室净碎片0时与黑键的某些组合目前不构成有效外站来源，保守策略也可能拒绝。不能按干员姓名维护白名单绕过，必须按真实能力类别。

这种策略能减少准入内解释器调用；但统一资源上界若把互斥主备、抵消、转换链简单相加，**不自动构成安全上界**。先保留最终精确检查作为回归证明，再逐类证明保守新规则拒绝集覆盖旧违规状态。工作量高于A/B，不作为先做大框架的理由。
