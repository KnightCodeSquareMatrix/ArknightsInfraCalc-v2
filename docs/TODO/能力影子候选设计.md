# 能力影子候选设计

> 文档角色：active-change
> 生命周期状态：ready-on-request
> 当前真源：docs/QUALITY_AND_AUDIT.md；docs/BASE_ASSIGNMENT.md；docs/MANUFACTURE_STATUS.md；docs/ORCHESTRATION_LAYER.md
> 摘要：通过延迟真实干员占用，解决跨设施、跨产物和同房组合的顺序抢占问题

> 当前实现事实（2026-09-01）：影子候选适用域已收窄为**仅夜烟**（用户裁决：
> 只有夜烟同时拥有贸易站订单效率与制造站赤金生产力，真实存在双侧边际竞争；
> 砾只有制造技能，不进入 trade pool，无此需求）。流水线在首个空贸易站与首个
> 空制造站的普通填充边界探测两侧实际 pick（不提交占用），仅当两侧 pick 都选中
> 夜烟时，才比较“夜烟进贸易、制造排除夜烟”与“夜烟进制造、贸易排除夜烟”两条
> 分支，使用 `TradeManufactureWeightedEfficiencyV1` 选择 winner，最后只提交 winner
> 的真实 assignment/used。Peak 模式下该比较只对最终选中的中枢 winner 执行一次
> （候选循环内不再重算）；Recovery 模式在填充边界执行。分支只 commit 首房 pick
> 并正常填充剩余房，不再克隆整套排班全量重算两遍；其他同名干员不再触发。
> 该路径不生成候选笛卡尔积，不把 shadow id 写入最终结果；多房间全局联合最优、
> rotation 联合优化、Bake/cache 和 state-only 冲突闭包仍未覆盖。

## 1. 定位

本方案解决一个独立的求解器问题：同一真实干员能够服务多个设施、产物或组合，但当前逐房流程在前序房间提交后立即写入 `used`，导致后序房间无法比较该干员是否在那里具有更高的边际收益。

当前制造流程按产物顺序逐房搜索，并在每房命中后提交成员：[制造排班](../../crates/infra-core/src/layout/assign/manufacture_fill.rs) 的 `assign_manufacture_lines`；当前提交通过真实姓名写入互斥集合：[提交逻辑](../../crates/infra-core/src/layout/assign/commit.rs) 的 `commit_operators_to_room`。这使设施顺序同时成为资源归属顺序。

本方案将“能力候选”和“真实干员占用”分开：候选阶段允许同一真实干员以多个能力视图参与比较，只有在候选冲突解决后才提交真实 assignment。

本方案不拥有：

- 挂件 receiver、SupportPool 或 SupportClaim 的业务语义；挂件体系另行设计；
- Bake、缓存或候选表的生成方式；候选可以来自实时 solver 或其他已授权的候选来源；
- hard 体系的 admission、required anchor、Plan 绑定和轮换政策；
- 技能公式和最终效率结算；这些仍由现有单房 solver 与 `resolve` 负责。

## 2. 核心模型

### 2.1 能力影子

能力影子不是新的干员，也不能进入最终 assignment。它是某个真实干员在一个具体候选中的能力视图：

```text
shadow_id: 夜烟#trade
physical_operator: 夜烟
capability: trade_order_speed
```

同一个真实干员可以同时生成多个影子：

```text
夜烟#trade
夜烟#manufacture_gold

至简#gold
至简#battle_record
至简#originium
```

影子的用途是让各房间先看见完整的潜在候选；`physical_operator` 才是最终唯一占用的资源身份。

### 2.2 候选行和组合候选

普通单人候选和同房组合使用同一个候选模型。一个候选至少包含：

```text
facility / room / recipe
operators or physical claims
capability shadows
final room efficiency
mechanic breakdown
response signature
resource reads / writes
```

组合候选是多个真实干员 claim 的原子候选，不先拆成独立干员再由后续房间补齐。例如：

```text
红云 + 酒神 + Miss.Christine
水月 + 标准化成员 A + 标准化成员 B
苍苔 + 金属工艺类技能成员
断罪者 + 食铁兽 + 酒神
```

队友保持开放。红云、水月、苍苔等响应核心提高的是候选展开和候选保留优先级，不是强制入驻优先级。

### 2.3 真实占用

候选阶段使用 provisional claims，不能直接改变最终 `used`。每个 claim 必须能在最终化前还原为真实的：

- 干员身份和练度层级；
- 房间、岗位和容量占用；
- 产物或订单约束；
- 工作心情与休息去向；
- 同房、同站、跨房和轮换关系；
- 读取或写入的跨房状态。

第一次正式 `resolve`、最终房间 solver、Team/Shift 构造和 export 前，所有 shadow 必须已经合并为真实身份。`resolve`、Workforce、跨房 atom、rotation 和 MAA 不消费 `shadow_id`。

## 3. 主路径

```text
Plan / hard systems
    -> 各房间生成完整候选行
    -> 候选暂存 physical claims，不提交真实 used
    -> 检查真实身份、房间资源和状态读写冲突
    -> 对冲突闭包联合重算并选择候选
    -> 真实身份合并与临时 assignment
    -> 统一 resolve 和最终房间结算
    -> 原子提交 winner
    -> 普通 fill、rotation、export 只消费已解析结果
```

Plan 仍然先处理 hard system、required anchor、`min_count`、exclusive branch 和必要绑定。影子候选只能表达已经允许进入比较的 optional candidate，不能激活体系、补足 required count、替换 hard anchor 或在 fill/rotation 阶段重新做 admission。

## 4. 冲突解析

### 4.1 触发条件

候选之间发生以下任一种关系时，进入同一个冲突组件：

1. 共享同一 `physical_operator`；
2. 共享同一房间、岗位、容量或挂件资源；
3. 一个候选读取另一个候选写入的全局状态；
4. 两个候选共同改变某个设施计数、标签计数、EffectKey 或 producer response；
5. 替代候选会改变已有候选的效率、合法性、依赖或轮换条件。

仅有相同真实干员的冲突检测不足以覆盖跨房状态。组件必须不断吸收受影响的候选，直到其外部输入保持不变，或明确降级为受限策略结果。

### 4.2 局部重算

发现冲突后，不做整个基建的笛卡尔积，而是在当前冲突组件内比较完整分支：

```text
保留候选 A，重新生成 B 的合法替代行
保留候选 B，重新生成 A 的合法替代行
必要时继续吸收替代方案引发的候选
对每个完整分支使用真实 assignment 统一 resolve
按具名 objective 选择 winner
```

“只回溯一次”只能作为常见路径的性能优化，不能作为正确性前提。替代方案可能继续争抢酒神、夜烟、标准化成员或跨房状态，必须允许组件递归扩大。

### 4.3 候选前沿

每个候选族不能只保留单房效率最高的一行。至少要按以下信息保留非支配候选：

- 不同 `physical_operator` 集合；
- 不同响应签名，例如标准化数量、仓容贡献、金属工艺数量；
- 不同产物和房间容量；
- 不同跨房状态读写集合；
- 不同组合分支。

如果一个候选在收益不低、资源占用不多、状态影响不差的前提下严格支配另一个候选，才可以安全删除被支配行。固定 `top_k`、当前 top hit 或干员白名单不能自动构成安全剪枝。

## 5. 既有问题的覆盖

### 5.1 夜烟：贸易与赤金

生成 `夜烟#trade` 与 `夜烟#manufacture_gold`。冲突时比较完整替代结果，而不是比较两个技能面板值：

```text
夜烟进贸易 + 其他候选进赤金
vs
夜烟进赤金 + 其他候选进贸易
```

如果贸易存在高质量替代者而赤金不存在，赤金分支自然胜出，不需要写死“制造优先”。

### 5.2 通用制造干员：赤金、经验、搓玉

同一干员可以同时进入多个产物候选。赤金、经验和搓玉的房间顺序只影响遍历，不再直接决定归属；最终由共享 physical claim 的冲突组件比较完整替代方案。

### 5.3 红云、水月、苍苔和其他同房组合

同房机制仍由正式制造 solver 结算。候选层把开放队友组合视为完整 row，保留不同响应签名和关键干员集合。组合优先级用于确保候选被展开和保留，不把队友固定成某一组姓名，也不强制组合入驻。

### 5.4 共享组合成员

例如以下候选都声明酒神的 physical claim：

```text
红云 + 酒神 + Miss.Christine
断罪者 + 食铁兽 + 酒神
```

两个组合可以同时进入候选，但最终只能选择不冲突的完整分支。组合候选不能先被一个房间提交，再让另一个房间只看到“酒神已使用”。

### 5.5 跨房状态

清流、动态 producer、阵营人数、精英设施数和 global resource 等没有共同干员的候选，也可能互相影响。它们必须通过显式状态读写签名进入冲突闭包；只靠 physical identity 冲突不能声称覆盖此类问题。

## 6. 单一责任边界

| 层 | 责任 |
|---|---|
| Plan / orchestration | hard admission、required anchor、exclusive branch、绑定声明和候选资格 |
| 单房 solver | 生成合法单房组合并结算正式房间效率 |
| 候选协调器 | 暂存 physical claims、构建冲突闭包、重搜替代行、比较完整分支 |
| resolve / Workforce | 对真实 assignment 结算全局状态、跨房效果和最终效率 |
| rotation | 消费已解析真实成员，验证班次、绑定、依赖和容量 |
| export | 忠实投影最终真实 assignment，不理解 shadow |

候选协调器不复制技能公式，也不承担 hard admission。`resolve` 不负责补救已经丢失的候选；如果候选选择依赖后续状态，必须在选择阶段进入同一闭包。

## 7. 保证等级

第一阶段默认结果状态为 `BEST_FOUND`。只有在以下范围内完整枚举候选并完成闭包比较，才能称 `POLICY_OPTIMAL`：

- 候选族和组合 row 的边界已明确；
- 所有合法候选均可恢复；
- physical claim 和状态读写闭包完整；
- 冲突组件内完整比较或使用已证明安全的 reduction；
- objective、tie-break、容量和轮换约束已纳入比较。

只有覆盖 canonical 全部合法候选、目标和跨房/跨班约束，并证明组件分解不会删除最优解，才能称 `EXACT_OPTIMAL`。

质量门禁来自 [质量与审计](../QUALITY_AND_AUDIT.md)：改变候选生成、分解、目标、剪枝或 top-K 必须声明保证等级；最终刷新已选组合不能代替联合选择。

## 8. 验收矩阵

| 层级 | 必须证明 |
|---|---|
| 单房 | 每个 shadow/组合 row 使用正式 solver；技能公式、配方和同房响应正确 |
| 物理占用 | 同一真实干员不能同时落位；组合 claim、房间容量和岗位约束不重复 |
| 跨设施 | 没有共同干员但共享状态的候选能进入同一闭包；最终 resolve 与候选比较一致 |
| 冲突 | 夜烟、通用制造、红云/水月/苍苔、酒神共享组合均能切换替代分支 |
| 顺序不变性 | 调换同类房间顺序不改变具名目标下的 winner，或明确报告顺序 policy |
| 完整性 | 关闭候选截断后，小规模 oracle 与协调器结果一致；被删候选有支配证明 |
| 最终化 | 首次正式 resolve、rotation 和 export 前没有 shadow；真实 assignment 唯一且可执行 |

## 9. 待裁决项

1. 跨房状态闭包的首期覆盖范围：全部登记状态，还是先覆盖已确认的 response dependency。
2. 候选前沿的完整性要求：首期允许 `BEST_FOUND`，还是限定候选宇宙后直接要求 `POLICY_OPTIMAL`。
3. 贸易、赤金、经验和搓玉之间采用何种具名 objective；不能由遍历顺序代替目标。
4. 组合候选的来源和实时回退策略；本文件不裁决是否使用 Bake。
5. 发生无法闭合的状态依赖时，是否 fail-closed、降级为普通候选，或标记 `UNKNOWN`。
