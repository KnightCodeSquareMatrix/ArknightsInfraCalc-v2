# 贸易订单期望值计算口径问题（2026-08-28）

> 文档角色：active-change
> 生命周期状态：ready-on-request
> 当前真源：docs/EFFICIENCY_MODEL.md
> 摘要：记录普通贸易订单期望日产出和赤金消耗节奏的正确口径、当前错误实现、影响链与后续修复边界。

## 1. 已裁决口径

对同一类普通赤金贸易订单，设订单档位为 `i`，概率为 `p_i`，每单龙门币收益为 `R_i`，耗时为 `T_i` 分钟，消耗赤金为 `G_i`。

先计算一笔随机订单的期望收益和期望时长，再换算每日产出：

```text
avg_lmd_per_order = sum(p_i * R_i)
avg_minutes_per_order = sum(p_i * T_i)

trade_lmd_per_day = 1440 * avg_lmd_per_order / avg_minutes_per_order
gold_per_day = 1440 * sum(p_i * G_i) / avg_minutes_per_order
minutes_per_gold = avg_minutes_per_order / sum(p_i * G_i)
```

不得使用下列两种“逐档先除后加权”的算法替代上述期望订单口径：

```text
wrong_trade_lmd_per_day = 1440 * sum(p_i * R_i / T_i)
wrong_minutes_per_gold = sum(p_i * T_i / G_i)
```

普通订单中 `R_i = 500 * G_i`，因此贸易龙门币产出和赤金消耗是一比一的物理链：

```text
trade_lmd_per_day = 500 * gold_per_day
```

`minutes_per_gold` 是贸易站订单流的赤金消耗节奏（每消耗一个赤金对应的平均订单时间），不是制造站指标，也不应作为普通站最终龙门币日产出的另一个独立计算来源。

## 2. 二级、三级验证

普通订单档位概率由 [效率模型](../EFFICIENCY_MODEL.md) §3.2 定义；订单时长和金额当前由 `trade/order_mechanic.rs::tier_params` 承载。

| 贸易站 | 概率分布 | 平均龙门币/单 | 平均分钟/单 | 正确龙门币/天 | 项目固定锚点 |
|---|---|---:|---:|---:|---:|
| 二级 | `2金 60% / 3金 40%` | `1200` | `170.4` | `10140.845` | `10141` |
| 三级 | `2金 30% / 3金 50% / 4金 20%` | `1450` | `203.4` | `10265.487` | `10265` |

三级具体为：

```text
1440 * (0.3*1000 + 0.5*1500 + 0.2*2000)
     / (0.3*144 + 0.5*210 + 0.2*276)
= 10265.487
```

这与当前社区单位日产出锚点的整数展示一致。此前出现的 `10229.814 / 10265 = 0.997`，来自错误算法，不代表普通三级站存在实际的 `0.997` 单位产出倍率。

## 3. 当前错误 owner 与影响链

### 3.1 直接错误的实现

`crates/infra-core/src/trade/order_mechanic.rs`：

| 函数 | 当前算法 | 应遵循的口径 | 直接用途 |
|---|---|---|---|
| `unit_per_slot_per_day` | `sum(p_i * R_i / T_i) * 1440`，并对赤金采用同构算法 | 平均收益/平均时长；赤金为平均赤金/平均时长 | L2 普通金订单的原始贸易/赤金单位日产出 |
| `weighted_minutes_per_gold` | `sum(p_i * T_i / G_i)` | `sum(p_i*T_i) / sum(p_i*G_i)` | L2 的 `minutes_per_gold` 与机制解释换算 |
| `baseline_unit_trade_lv3_regular` | 调用错误的 `unit_per_slot_per_day` | 应返回正确三级普通期望日产出 | 佩佩机制解释的普通三级基准 |

三级当前错误值与正确值：

```text
unit_per_slot_per_day: 10229.814, correct 10265.487
minutes_per_gold:      70.400, correct 70.137931
```

二级当前错误值与正确值：

```text
unit_per_slot_per_day: 10114.286, correct 10140.845
minutes_per_gold:      71.200, correct 71.000000
```

### 3.2 依赖 `unit_per_slot_per_day` 的路径

`trade/unit_output.rs::compute_unit_output` 对普通金订单读取该函数的贸易龙门币与赤金日产出。

随后 `trade/solver.rs::resolve_unit_output` 对贸易单位日产出存在三类分流：

1. 无特殊机制的普通二级、三级站，会以 `regular_trade_unit_output_per_day` 的固定社区锚点 `10141/10265` 覆盖贸易单位日产出。因此普通站的最终贸易龙门币日产出当前未使用错误的 `10229.814`。
2. 可露希尔、但书单走、巫恋/龙舌兰/裁缝等命中 L3 shortcut 的组合，会以 `trade_shortcuts.json` 的社区 `unit_output` 覆盖最终贸易单位日产出；其最终贸易收益不以 `minutes_per_gold` 结算。`mechanic_equivalent_efficiency` 仅作解释，不二次参与最终产出或排序，见 [评分口径](../SCORING_MODEL.md) §4。
3. 未命中上述固定社区单位产出锚点、但仍带普通金订单机制的 L2 路径，原始 `unit_per_slot_per_day` 会保留为最终 `TradeUnitOutput`。该范围需要在实施前按具体机制逐个列出和验证，不能假定所有 L2 机制都应继续由公式推导。

赤金侧与贸易单位产出是独立字段：`unit_per_slot_per_day` 同时生成 `unit_gold_per_day`，而 shortcut 仅在配置 `unit_gsl_gold_anchor` 时覆盖赤金字段。可露希尔等仅配置 `unit_output` 的 shortcut 不应被描述为“赤金单位产出来自社区锚点”。赤金物理量的最终使用范围不在本次记录中扩展，应在实施时按 `unit_gold_per_day`、`gold_consumption_per_day` 和无人机字段逐项验证。

### 3.3 依赖 `minutes_per_gold` 的路径

`resolve_order_mechanic` 将 `weighted_minutes_per_gold` 用于：

1. 普通订单分布与当前分布之比，生成 `mechanic_equivalent_efficiency`。
2. Eureka 固定两赤金订单相对普通订单的机制解释。
3. 可露希尔特别订单相对普通订单的机制解释。
4. `OrderMechanicResult.minutes_per_gold` 的诊断字段。

当前可直接确认的运行时消费仅限上述机制解释计算和 `OrderMechanicResult.minutes_per_gold` 字段的构造。`mechanic_equivalent_efficiency` 按当前规范不应二次乘入最终效率或实际产出；其数值仍应使用正确的期望订单口径，避免机制解释与实际物理量不一致。该字段是否进入任何具体导出或缓存产物，应在实施时按实际序列化路径另行核对。

## 4. Shortcut 中的同类写法

`crates/infra-core/src/trade/shortcut.rs::expected_from_dist` 也计算：

```text
sum(p_i * T_i / G_i)
```

它构造 shortcut 的 `OrderMechanicResult.minutes_per_gold`，但 shortcut 的 `mechanic_equivalent_efficiency` 来自已配置数据，最终贸易单位产出由社区 `unit_output` 决定。因此该处是重复的、可能错误的诊断计算，不是可露希尔、但书或巫恋/龙舌兰最终贸易收益的依据。赤金字段是否有社区锚点，必须按 `unit_gsl_gold_anchor` 是否存在分别判断。

当分布只有一个非零档位时，`p=1`，两种写法均退化为 `T/G`，不会产生数值差异。存在多个档位概率时才必须改为“期望时长 / 期望赤金”。

## 5. 后续修复指令边界

本任务只完成问题追溯与口径冻结，未修改 Rust、数据、fixture 或社区锚点。

后续获得实施授权时，应以 `trade/order_mechanic.rs` 为首次错误 owner，统一修复普通订单的期望单位日产出和 `minutes_per_gold`；不得在 CLI、排班展示、固定锚点或单个干员组合上加补偿。

实施前必须逐项确认：

1. 特殊订单、违约链、订单金额追加与订单分布变化的期望值输入如何归一化。
2. 未命中社区单位产出锚点的 L2 机制，最终贸易收益和赤金消耗是否应直接使用该统一期望公式。
3. `mechanic_equivalent_efficiency` 是否继续保留为纯诊断，以及实际序列化产物的允许变化范围。
4. 普通三级 `10265.487` 与固定社区锚点 `10265` 的整数/小数展示和比较规则。

验收至少包含二级、三级普通订单、单一订单档位退化情况、一个订单分布变化机制、一个固定社区单位产出 shortcut，以及贸易龙门币与赤金消耗一比一关系。
