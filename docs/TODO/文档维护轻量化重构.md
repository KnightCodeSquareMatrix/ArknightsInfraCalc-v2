# 文档维护轻量化重构

> 文档角色：active-change
> 生命周期状态：in-progress
> 当前真源：docs/文档生命周期.md；docs/INDEX.md；docs/PROJECT_MAP.md
> 摘要：降低高频求解器修复中的文档读取和更新成本，不改变领域语义

## 1. 目标

为当前以真实 operbox 反馈、代码追踪、最终状态复核和求解器部署为主的工作流建立轻量文档入口。保留领域事实、当前实现、AI 代码查询速览以及修复/讨论记录，但不要求每次维护都匹配一套大型文档格式。

## 2. 已确认约束

- `canonical` 仍是领域规则唯一 owner。
- `current-reference` 只描述当前实现、导航或工作流，不反向裁决领域语义。
- `TODO` 仍只保存跨会话的 active-change；完成时吸收事实、拆分开放项并归档。
- `ADR` 只记录需要长期追溯的决策，不保存普通修复进度。
- 不新增全仓 `docs-impact` manifest、第二套状态机或强制全量补充字段。
- 不为了通过检查擅自结束已有 `in-progress` 案件，不覆盖当前工作树中的用户改动。

## 3. 案件卡最小信息

案件卡只保留推动一次维护闭环所需的信息：

1. 现象、冻结输入和用户期望。
2. 既有文档路径、生命周期状态和领域 owner。
3. 首次违规层、当前实现事实和保证等级。
4. 验证入口、证据、下一步和非目标。

实现事实只能吸收到 `current-reference`；领域规范只有在已有用户裁决或明确授权下才更新 canonical。理论和实现冲突时，登记差异，不自动同步。

## 4. 首批范围

- 新增一个短的当前实现路由入口：[当前实现状态入口](../CURRENT_STATUS.md)。
- 收缩或补充代码导航：`PROJECT_MAP.md`、`ARCHITECTURE_TOUR.md`、`INTERNAL/README.md`，仅处理已核对的 owner 缺口。
- 试运行四个高频案件：08-212 贸易候选、2026-08-27 排班问题、发电效率重复、菲亚梅塔宿舍回岗。
- 其他活动任务只分类登记，不在本案件中全量重写。
- `INTERNAL/CROSS_FACILITY.md` 与 `resolve.rs` 的业务责任冲突单独 deferred，不在文档迁移中裁决。

## 5. 非目标

- 不迁移或重写全部 134 份 Markdown。
- 不改变 solver、候选、排班、Worker 或 export 行为。
- 不把当前代码事实升级为领域规范。
- 不立即新增项目 Skill；先用真实案件验证现有 lifecycle、quality 和 evidence 流程是否不足。
- 不新增、修改或运行源码测试。

## 6. 阶段和验收

1. 记录只读基线：metadata、生成索引、链接、现有状态和工作树变更。
2. 按案件绑定既有路径；机械漂移、状态未决和语义冲突分开处理。
3. 逐域维护短 current-reference 和代码查询路由，不复制 canonical。
4. 用首批案件验证读取路径是否减少，并保留未决差异。
5. 每批运行文档 inventory、链接和仓库事实检查；最终 fresh review。

`in-progress` 只在当前确有 writer 且案件范围仍冻结时保留。关闭本案件前必须把已确认事实吸收到对应 owner，拆分剩余开放项，更新生成索引并检查最终树。
