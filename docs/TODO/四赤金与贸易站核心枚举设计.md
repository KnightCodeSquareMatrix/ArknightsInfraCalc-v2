## 4. 模型

本节除明确写“用户 A#”“用户原话”外，都是 agent 设计建议，不是用户裁决；其中改变候选空间、目标或取舍的部分在 §8 标为保证等级。

### 4.1 决策与目标

每次 Peak 排班，对每间金单贸易站决定“放哪个核心、和谁同房”。这个决定是联合的：一个人只能出现一次，房间容量有限，且各贸易房的效率读取同一份全局状态，所以不能先把每间房独立打分再拼起来。

目标是金单贸易站（gold 订单、非源石）在完整结算后的 `final_efficiency` 之和。源石站不计入核心选择目标，另在 1d 单独比较（§4.5、§7.4）。用户已裁决求和口径（A30：“金单站效率求和”）。平手按固定候选顺序取第一个（用户 A22），顺序表见 §4.5。

### 4.2 候选

候选分两层：单房模式，以及四赤金跨房队友分配。所有候选最终都落成“每间金单站的人选”，再交给完整结算。

#### 4.2.1 单房模式

核心房只由本节产生；四赤金不产生核心房。

每间金单站可进入以下模式之一：

- 但书核心：但书必须在房内，其余座位由单房搜索在剩余人员里按效率找。但书去最低级金单站（`data/orchestration_rules.json:64` 的 `lowest_level`；用户 #0140 的 INV-TRADE-001）。
- 可露希尔核心：可露希尔必须在房内，其余座位按效率找；可露希尔去最高级金单站（`data/orchestration_rules.json:66`、`:169` 的 `highest_level`）。
- 巫恋+龙舌兰核心：两人必须在房内，其余座位按效率找；要求房间至少 3 级（`data/orchestration_rules.json:61-62`）。
- 无核心纯搜索：不放指定核心，直接在剩余人员里取效率最高的合法三人组。

这些模式内部的队友由现有单房搜索产生，包括企鹅、孑+银灰等已经有技能的变体；它们不是单独的核心类型。每个模式保留前 K 个队友组合，K=20（用户 A24），K 之外的组合不进入联合枚举。

#### 4.2.2 四赤金：跨房队友分配

四赤金三人（绮良、鸿雪、图耶）不是核心，是读全基建赤金线的效率队友（用户 A27）。赤金线数全基建统一，三人在哪间贸易站供线，各站读到的线数都一样，所以可以拆到不同房间。4 条真实赤金线时三人分别是 鸿雪 60%、图耶 95%、绮良 5%（知识库 `arknights-base-vault@977b6ab0` 的 `docs/3-组合库/跨设施体系/鸿雪杜林组.md#一句话结论`、`#成员与档位`）。

四赤金只做两件事（用户 A27）：

1. 确认全基建准入：4 条真实赤金制造线、4 名杜林支持者只放宿舍、三人精二（§4.3）。
2. 把三人作为队友分配进 §4.2.1 产生的核心房。

四赤金不再声明但书、可露希尔、巫恋、龙舌兰；这些是核心，由 §4.2.1 的核心选择产生（A27、A6、A8）。

用法全部作为完整结算候选，按金单站贸易总产出比较（用户 A28）：

1. 拆开：绮良进巫恋组第三席（巫恋+龙舌兰房的第三席）；鸿雪、图耶作为但书或可露希尔房间的队友。分配变体至少包括“鸿雪图耶同进一间核心房”和“鸿雪图耶分进两间核心房”，后者在三站时包含“可露希尔＋鸿雪、但书＋图耶”这一种。房间剩余座位按效率搜索（用户 A7）。
2. 三人同房：三人在同一间金单站，按 绮良→鸿雪→图耶 的进驻顺序，固定三人候选，任何站数的布局都可用（用户 A5）。进驻顺序不同终值不同，换班重进同此（知识库同页 `#同站满配`）。
3. 不启用：三人作为普通散件参与自然搜索，不用四赤金体系。
4. 源石站：只额外算一次三人同房，和纯搜索比（用户 A10），见 §7.4，写法不变。

09-28 原话“两贸易站就鸿雪图耶一起……三贸易站就分开各自带可露希尔、但书”和知识库的“跨站拆分（优先推荐）”分工都是建议/推荐，按 A28 降为候选之一，不写死（§1.2）。

禁同房：拆分变体保留绮良-鸿雪、绮良-图耶，以及鸿雪图耶分进两间时的鸿雪-图耶；“鸿雪图耶同进一间核心房”变体不带鸿雪-图耶禁令，否则这一对永远无法同房。三人同房候选不带这三条。黑键-巫恋的全局禁令不受影响。

拆分用法下没有巫恋组（未拥有或练度不足）时，绮良作为任意核心房的队友，与“绮良不上”一起当候选比较（用户 A29，§9.7）；知识库的分工把绮良放龙舌兰组第三席，同页 `#2/3 赤金双人档` 的口径是线数不足 4 条时一般不用绮良。

核心房的座位、禁同房与三人的房间分配都由核心选择结果表达，不再依赖 alternative 字符串（§5）。

#### 4.2.3 杜林支持

四赤金候选假定 4 名杜林支持者可兑现（数据候选 5 选 4，`data/orchestration_rules.json:68`、`:90`；用户 A19）。用户 A25 裁决：四名杜林只放宿舍；核实后按 §9.6 选项 A 实现。`durin_presence` 仍是 Plan 的编译期放置角色，但设施白名单只保留宿舍，放置由 Plan 的杜林放置规则完成；四赤金准入只要求“4 名杜林支持者可兑现”。比较阶段只假定，不实际占用；候选胜出后才把这 4 名杜林落位到宿舍，宿舍放不下时这个候选不可行。候选落选时不留下任何占用或状态。这是用户 L1416“延迟绑定杜林”的实现含义。统一挂件模块不在本轮。

### 4.3 约束

- 一人一处：所有候选共用同一已用人员集合；深度优先枚举时，选中的人从后续房间的候选池里移除。
- 房间容量：按房间等级 2 或 3 人；候选必须填满房间才有资格参与比较，填不满即候选不可行。
- 禁同房：黑键与巫恋全局禁止同房；四赤金拆分变体保留绮良-鸿雪、绮良-图耶，以及鸿雪图耶分进两间时的鸿雪-图耶；三人同房候选不带这三条，也不解除黑键-巫恋。
- 同上同下：四赤金三人在轮换中必须同组上下；ABC 是两上休一，其他 profile 按团队拓扑。现有绑定在 `data/orchestration_rules.json:75`、`:96`。
- 准入：至少 4 条真实赤金制造线；三人精二（绮良、鸿雪、图耶）；拆分变体需要至少一间可接收鸿雪/图耶的核心房（但书或可露希尔），绮良需要巫恋组第三席；三人同房任意站数；4 名杜林支持者可兑现且只放宿舍（用户 A19、A25；`data/orchestration_rules.json:57-58`、`:63-68`、`:90`）。
- 单房核心练度：可露希尔核心要求精二，但书任意练度，巫恋与龙舌兰核心要求精二（`data/orchestration_rules.json:61-62`、`:117`、`:134`、`:152`、`:170`）。
- 房间等级偏好：但书去最低级金单站（用户 A20），可露希尔去最高级，巫恋/龙舌兰要求 3 级房。核心进哪间房由这个偏好决定，不看效率；拆分变体之间的组合按总产出比较（A4 注、A28）。
- 中枢容量：用户 A23 裁定“四赤金和中枢无关”，中枢容量不作为四赤金候选的准入条件。轮换层 `ControlRotationRequiredAnchorsExceedCapacity` 时跳过四赤金分支（`team_rotation.rs:7766-7789`）属于错误归因的补偿，1b 删除；不把中枢超容并入“候选不可行”。

### 4.4 目标与跨房耦合

候选的分数是“把这份完整金单站编制交给完整结算后，所有金单贸易房 `final_efficiency` 的和”。`final_efficiency` 已含特殊订单单位产出倍率；不能再用 `mechanic_equivalent_efficiency` 解释值加一次，也不能用纸面 `total_efficiency` 替代（ADR 0013 D3；`crates/infra-core/src/trade/efficiency.rs:56-71`）。

这里的“完整结算”指对同一份编制运行现有 resolve 黑盒，而不是各房独立查表。跨房耦合至少包括：

- 贸易干员生成的虚拟赤金线进入全局账本，被所有赤金贸易房读取（`resolve.rs:298-321`；`trade/gold_flow.rs:52-60`）。
- 八幡海铃按各贸易站同房 tag 人数汇总（`types.rs:123`）。
- 凛御银灰按满足 tag 门槛的贸易站数量结算（`types.rs:131`）。
- 乌有、黑键按全基建宿舍人数结算（`context.rs:21`；`resolve.rs:684`）。
- 调查团的木天蓼依赖中枢 producer 与贸易/制造 consumer（`search/control.rs:24`、`:91`）。

Plan 编译阶段制造、发电、中枢还没有最终填满，所以评分时的布局只是当前 seed、已认领锚点、假定的 4 名杜林和候选贸易座位的组合；制造与中枢的最终状态可能改变全局账本。因此“对当前可见布局的完整贸易结算”是精确的，“对最终完整基建的排序”是近似。最终 Plan 填完后必须用完整 resolve 核对赢家合法性；本轮不在完整结算后重新排序（见 §8 的 approximation）。

### 4.5 求解

枚举加完整结算，按房深度优先：

1. 从 Plan 的初始已用集合出发（继承排除、注册表已认领锚点、预占房间等）。
2. 选一个金单站作为当前房。房间顺序固定，建议按蓝图 id 升序；顺序只影响枚举次序，不影响候选集合（agent 建议默认）。
3. 当前房先由 §4.2.1 生成核心与队友候选；四赤金拆分变体在核心房确定后把三人分配进去，再搜剩余座位；三人同房候选作为当前房的一种候选生成（任意站数，用户 A5）。
4. 对每个候选，检查一人一处、容量、禁同房、房间等级偏好和准入；不合法或填不满就拒绝该候选，继续下一个。
5. 选中候选后把该房人员加入已用集合，递归下一间房。深度优先时先排除已用人员，避免“各核心独立取 top-K 再组合”的抢人问题。
6. 所有金单站都有座位后，对这份完整金单站编制运行完整结算，得到各房 `final_efficiency` 并求和。
7. 保留总和最高的候选；总和相等的处理见下。枚举完所有分支后，把赢家作为 Plan 锚点提交。
8. 四赤金候选胜出后才落位 4 名杜林，只放宿舍（用户 A25；实现按 §9.6 选项 A：杜林放置规则只保留宿舍，宿舍放不下则该候选不可行）；落选候选连同其杜林假定一起丢弃。

平手：`Efficiency` 是整数（`crates/infra-core/src/efficiency.rs:9`），可以用精确相等判断，不需要浮点容差。用户裁决平手“按固定候选顺序取第一个”（用户 A22）：所有候选排成一个固定、显式、不依赖哈希或运行顺序的顺序表，平手取排在最前面的；不特别偏向普通/基线方案。顺序表如下（标 agent 建议默认，实现时固定为单一显式比较函数，不得靠遍历顺序碰巧决定）：

| 位次 | 候选类别 | 说明 |
|---|---|---|
| 1 | 四赤金拆分·鸿雪图耶同进一间核心房 | 拆分变体之一 |
| 2 | 四赤金拆分·鸿雪图耶分进两间核心房 | 拆分变体之一；三站时含“可露希尔＋鸿雪、但书＋图耶” |
| 3 | 四赤金三人同房 | 任意站数 |
| 4 | 但书核心 | 但书在最低级金单站 |
| 5 | 可露希尔核心 | 可露希尔在最高级金单站 |
| 6 | 巫恋+龙舌兰核心 | 3 级金单站 |
| 7 | 无核心纯搜索 | 纯效率三人组 |

类内顺序：房间按蓝图 id 升序；同一房间的队友组合按 `final_efficiency` 降序，再按干员实例 id 升序，超过 K=20 的组合不进入枚举。跨房的完整编制先按类别位次、再按逐房座位元组比较。顺序表只影响平手，不影响效率更高者的胜负。

复杂度：金单站只有 2 至 3 间，每间模式数量少，K=20 是唯一乘法因子；深度优先排除已用人员后，实际分支远小于模式数乘 K 的立方。若后续测量发现不可接受，再考虑上界剪枝；本轮不引入未证明安全的剪枝。

## 5. 分层：Plan 编译阶段作为唯一 owner

金单站核心准入放在 Plan 编译阶段，是唯一 owner，取代 `trade_core_selection` 互斥组和两条规则的优先级竞争；四赤金规则不再声明核心角色。具体行为：

- 在初始已用集合（继承排除、注册表认领、预占房间）确定后，编译先算出金单站核心选择结果：每个金单站的核心（或空）、全部座位、连续核心标记、四赤金用法（拆分/三人同房/不启用）与三人各在哪间房。杜林支持仍作为 Plan 的编译期放置角色，`durin_presence` 的设施白名单只保留宿舍（用户 A25；§9.6 选项 A）。这个结果写入 Plan 的锚点、约束、排除人员和选中的规则结果。
- 之后 Plan 继续编译其他体系规则；它们看到的已用人员已经包含核心选择占用的人，因此不能再抢核心房座位。
- `execute_plan` 只执行 Plan；补位只处理没有被锚点占满的房间和源石站；`resolve` 按最终编制结算。主路径仍是 `build_plan -> execute_plan -> fill -> resolve`。

为什么不算绕过 Plan（AGENTS.md 2.1 硬约束 5）：

> Layout 主路径是 `build_plan -> execute_plan -> fill -> resolve`，排班不绕过 Plan 修 admission。`shift_bind`、tag、priority、shortcut 只消费各自语义，不能代替 required admission。
> （`/home/knightcode/Projects/ArknightsInfraCalc-four-gold-trade-core-20261028/AGENTS.md:28`）

本设计没有在 `fill` 或 `resolve` 之后改写 assignment，也没有把核心准入塞进 `shift_bind`、tag、priority 或 shortcut。它替换的是 Plan 编译内部原本由互斥组和优先级做准入的那一段：候选在编译期决定，赢家以锚点形式进入 Plan，后续阶段只消费 Plan。评分的完整结算是对候选编制的只读试算，不是第二条排班路径；试算不提交、不导出、不被 fill 当作既成编制。

代价是编译期看不到制造、中枢、发电的最终状态（§4.4），所以这是有明示保证等级的近似，而不是“在 fill 阶段做事后补偿”。

## 8. 保证等级

按 AGENTS.md 2.1 硬约束 7，逐项声明。这里的“hard constraint”指违反即候选非法，不是“已证明全局最优”。

| 项目 | 等级 | 理由与边界 |
|---|---|---|
| 一人一处、房间容量、黑键-巫恋禁同房、核心准入（4 赤金线、三人精二、4 杜林、拆分变体的核心房与绮良的巫恋组第三席） | hard constraint | 违反即候选非法；来自现有数据与用户裁决 |
| 四赤金拆分变体的禁同房（绮良-鸿雪、绮良-图耶、分进两间时的鸿雪-图耶）；三人同房不带这三条 | hard constraint | 拆分变体的合法几何；“鸿雪图耶同进一间”与三人同房是用户 A5、A28 的具名例外 |
| 四赤金三人同上同下 | hard constraint | 轮换拓扑要求；现有 `bind_role_groups` |
| 深度优先时排除已用人员、拒绝填不满的候选 | safe reduction | 在同一候选空间内排除的只是不合法或不完整的组合，不删除合法完整解 |
| 在“声明的候选集合”内对完整结算取最高 | policy | 在该政策空间内枚举完候选后取最高；不代表候选集合外没有更优组合 |
| 每房每模式保留前 K 个队友组合，K=20（用户 A24） | heuristic | K 之外可能有效率更高的队友组合；K 默认 20、可配置，与 plan 入口一致 |
| 房间枚举顺序、候选遍历顺序 | heuristic | 只影响搜索顺序；平手键必须显式，不能靠顺序 |
| 四赤金拆分/三人同房/不启用与队友分配、核心房的房间等级偏好（但书最低级、可露希尔最高级）、剩余座位按效率搜索 | policy | 用户具名选择；只在政策范围内保证，不声称这些几何本身最优 |
| 四赤金拆分变体之间的比较 | policy（已枚举变体内精确） | 每个变体完整结算后按金单站总产出比较；已枚举变体之间的比较是精确的，候选集合之外不做完备性声明 |
| 四赤金不受中枢容量门禁，轮换层中枢超容跳过四赤金的分支删除（用户 A23） | policy | 四赤金和中枢无关；中枢超容不构成候选不可行的理由 |
| 四名杜林只放宿舍（用户 A25；§9.6 选项 A） | policy | 用户具名选择；白名单只保留宿舍，宿舍放不下时四赤金候选不可行；统一挂件模块不在本轮 |
| 单房核心集合（但书、可露希尔、巫恋+龙舌兰、无核心） | policy | 用户口述的核心清单；不证明没有其他核心 |
| 目标只算金单站贸易 `final_efficiency` 之和 | policy | 用户“总分只看贸易”；源石站另算，不并入 |
| Plan 编译期用当前可见布局评分，制造/中枢/发电未最终填满 | approximation | 全局账本可能随最终填房变化；最终完整结算只核对，不重排 |
| 候选集合没有证明完备性 | approximation | 不从 top hit、规则清单或历史输出反推全局最优 |
| 平手键：按 §4.5 的固定候选顺序取第一个（用户 A22；顺序表为 agent 建议默认、实现时固定） | policy | 顺序只影响平手，不影响效率更高者的胜负；不得依赖哈希或遍历顺序 |

整体结论：本设计对“声明的候选集合 + 明示 policy + 当前可见布局”给出可复现的最好解，属于 `BEST_FOUND` 语义；不得声称 `EXACT_OPTIMAL` 或全局最优。

### 11.3 联合搜索必须保留的责任边界
