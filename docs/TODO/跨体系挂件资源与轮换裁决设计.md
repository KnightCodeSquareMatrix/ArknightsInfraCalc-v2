# 跨体系挂件资源与轮换裁决设计

> 文档角色：active-change
> 生命周期状态：ready-on-request
> 当前真源：docs/MODELLED_OPERATORS.md；docs/公孙长乐的体系分析文档/RHINE_LAB_CHAIN.md；docs/FRONTEND_CLI.md
> 摘要：统一裁决跨设施主角色、挂件容量、宿主、超额收益和多班轮换的后续实现任务

> 2026-08-29 范围裁决：当前实现单元只包含所有定时排班共用的最终宿舍路径、菲亚梅塔修复，以及深巡 + 乌尔比安的基建内存在关系。深巡不再在单班 producer 阶段预占乌尔比安宿舍；最终班次组装仅在深巡实际工作且乌尔比安不在其他正常基建房间时使用空床满足 presence。赫德雷、伊内丝、W、维什戴尔及通用挂件容量账本仍为延期 proposal。本次新增的莱茵生命主动挂件仅提供显式开关：默认关闭，开启时沿用既有 `rhine_support` 编排；它不实现下文的统一容量账本、跨体系 package 或收益优化模型。

## 1. 任务定位

当前各体系可以分别识别 receiver 和 support，但挂件资源没有统一容量账本。后处理按先后顺序追加角色时，后来者可能占用先入者的挂件位置，造成 receiver 与实际 support 脱节。

典型反例是 `44-353-operbox.json`：

```text
深巡需要乌尔比安；缪尔赛思需要莱茵生命挂件。
后来处理的莱茵挂件路径占用共享位置后，输出中看不到乌尔比安。
```

本任务的目标是建立有限挂件资源的统一裁决，不把每个新技能实现成跨模块姓名 `if`，也不对全部角色、房间和体系做无界穷举。

## 2. 已确认规则

### 2.1 挂件宿主容量

每个班次先按策略预留以下挂件宿主上限：

| 宿主 | 挂件位上限 | 说明 |
|---|---:|---|
| 宿舍 | 4 | 宿舍同时承担心情恢复，必须先扣除必休 / 恢复保留位 |
| 加工站 | 1 | 允许低价值角色或已有加工技能角色进入 |
| 会客室 | 1 | 允许已有会客技能角色进入；不能假设会客室为零价值 |
| 训练室 | 1 | 即使当前没有训练任务，也保留 1 个策略挂件位 |

这些是策略上限，不是无条件可用容量。实际容量必须扣除当前班次的固定占用、高价值岗位和宿舍心情恢复需求。

### 2.2 宿主候选资格

- 角色已有的加工站、会客室或训练室技能，保留为对应设施的合法挂件备选。
- 所有角色都可以作为加工站和训练室的策略性挂件备选。
- 加工站和训练室中，持有对应技能的角色优先于无技能角色。
- 除赫德雷关系中的伊内丝、W 外，其余挂件角色均可进入宿舍备选。
- 伊内丝、W 作为赫德雷挂件时不得进入宿舍；可使用会客室、加工站或训练室。
- 上述伊内丝 / W 宿舍限制只约束“作为赫德雷挂件”的关系，不改变其作为普通角色或其他体系 support 的独立资格。
- 训练室的 `training_room` 响应协议另见 [训练室输出与 plan.compute 协议](训练室输出与plan.compute协议.md)。

### 2.3 挂件必须跟随主角色

挂件收益按班次实际 presence 计算，不跨班继承：

```text
主角色上班 -> 同一班次的 required / selected 挂件实际存在
主角色下班 -> 挂件不再为该主角色提供收益
```

挂件自身可以在不同班次切换状态：

- `support_active`：为主角色提供收益；
- `dorm_rest`：进入宿舍恢复心情；
- `off_duty`：不工作，也不占用宿舍恢复位。

会客室挂件存在心情消耗，主角色下班后不能继续留在会客室并被计作 active support。加工站挂件随主角色下班离开工作位。宿舍挂件可以在休息班进入宿舍，但不能继续计算为主角色挂件。

### 2.4 常见体系

| 主角色 / receiver | 挂件 | 关系类型 |
|---|---|---|
| 深巡 | 乌尔比安 | 硬依赖；缺少时深巡 package 无效 |
| 赫德雷 | 伊内丝、W | 硬依赖；伊内丝和 W 作为该关系挂件不得进宿舍 |
| 缪尔赛思 | 莱茵生命角色 | 可选 / 分段收益；读取基建内除自身外的莱茵生命干员数，每名 +3%，最多 5 名（另有 +10% 基础）；会客室使用者与训练副手不计入 |
| 娜斯提 | 莱茵生命角色 | 可选 / 分段收益；读取基建内含自身的莱茵生命干员数，每名 +3%，最多 5 名；会客室使用者与训练副手不计入 |
| 凯尔希·思衡托 | 最终编制中实际进驻精英干员的设施 | 办公室基础联络速度 `+30%`；每间精英设施额外 `+4%`，最多 5 间；不是指定姓名挂件组合 |

凯尔希·思衡托读取同一班次最终真实编制中的精英设施数：同一实际设施内有多名精英干员只计 1 间，副手和活动室不计入。该机制不要求求解器主动选择指定姓名的挂件，也不进入通用挂件宿主容量竞争。

## 3. 收益计算口径

挂件的价值不是主角色触发后的完整效率，而是相对最佳替代方案的超额收益。

```text
package_excess
  = 启用 receiver + support 后的目标效率
  - 不启用 receiver 时的最佳替代效率
```

还要扣除挂件离开原岗位、原岗位替补和宿主占用的机会成本：

```text
net_support_value
  = package_excess
  - support_source_room_loss
  - replacement_loss
  - host_cost
```

例：深巡精二技能本身为 `+30%`，乌尔比安在基建内额外为 `+10%`，如果最佳非深巡贸易替代为能天使 `+35%`，则：

```text
深巡 + 乌尔比安 = 40%
最佳替代 = 35%
package_excess = 5% 贸易
```

不能把乌尔比安的价值记成 40%，也不能把深巡的基础 30% 归给挂件。

赫德雷若需要伊内丝、W 两名挂件才能从 35% 替代提升到 40%，则 package 超额收益为 5%，单位挂件收益为：

```text
5% / 2 = 2.5% 贸易 / 挂件
```

因此在容量有限时，深巡应优先于赫德雷。

缪尔赛思和娜斯提也必须先与各自设施的最佳非 receiver 替代比较，再进行跨设施折算。跨设施比较采用用户已裁决的具名 policy：`2% 发电 = 1% 制造 / 贸易`。该折算只用于候选比较，不改变各设施机制公式和分域效率输出。

## 4. 推荐数据模型

### 4.1 `SupportDemand`

每个体系只声明需求，不直接抢角色：

```text
SupportDemand {
  demand_id
  receiver
  native_facility
  required_count
  optional_count
  candidate_rules
  allowed_hosts
  benefit_curve
  same_presence
  share_policy
}
```

### 4.2 `SupportCapacityLedger`

按班次记录实际资源：

```text
SupportCapacityLedger {
  dormitory_available
  workshop_available
  meeting_available
  training_available
  reserved_rest
  occupied_high_value_slots
}
```

容量先满足硬依赖，再按剩余容量分配可选挂件。不能因某一体系先执行就永久占用全部宿舍或 support 资源。

### 4.3 `ReceiverPackageCandidate`

主角色和挂件应作为原子候选包：

```text
ReceiverPackageCandidate {
  receiver
  receiver_assignment
  support_members
  support_hosts
  required_dependencies
  source_room_changes
  presence_pattern
  package_excess
  opportunity_cost
  normalized_value
}
```

如果 package 被淘汰，必须整体撤销 receiver、挂件和依赖，再回填 receiver 的原工位。

## 5. 推荐求解阶段

保持现有主路径，不让挂件改变中枢、贸易和制造的领域 owner：

```text
registry / hard anchor
  -> 中枢 / producer
  -> 发电、贸易、制造生成 receiver 候选
  -> 生成每班 must_work / must_rest / free 骨架
  -> 计算宿舍、加工、会客、训练挂件容量
  -> 生成 receiver package
  -> 统一裁决 hard / optional package
  -> 回填被移动角色的原工位
  -> resolve 受影响房间与全局状态
  -> 普通办公室、会客室、宿舍补位
  -> 生成最终 rotation presence
  -> 逐班验证容量、心情、依赖和空位
```

不能在 receiver 各自的领域阶段直接提交 support，也不能等普通补位全部完成后才计算挂件容量。

### 5.1 主角色替代方案

每个 receiver 至少需要一个 enabled / disabled 对照：

```text
enabled: receiver + support package
disabled: 原设施的最佳普通 / 其他体系替代，不占 support 容量
```

如果 support 容量不足、机会成本为负或硬依赖无法满足，选择 disabled alternative，并重新求解 receiver 原工位。不能只删除 receiver 留下空位、旧 support 或 dangling dependency。

### 5.2 挂件分配优先级

1. 硬依赖：深巡的乌尔比安、赫德雷的伊内丝和 W。
2. 主流程已经选中且不产生额外岗位损失的角色：例如已经进入制造的迷迭香、已经进入发电的烛煌。
3. `net_support_value` 高、且宿主机会成本低的可选挂件。
4. 同效率时选择占用更少挂件位的 package。

搓玉玩法是思衡托的特殊 policy：布局包含源石碎片制造或合成玉贸易时，只要思衡托 package 可行且不破坏硬生产体系，应优先启用；普通玩法仍按完整净收益和机会成本比较。

## 6. 多班轮换

轮换不是把 peak 班的挂件集合复制到所有班次。每个班次都要保存：

```text
receiver_presence
support_presence
support_host
rest_state
worked_hours
```

示例：

```text
S1: 深巡 + 乌尔比安 active
S2: 深巡休息，乌尔比安 dorm_rest 或 off_duty
S3: 深巡 + 乌尔比安 active
```

主角色下班时，挂件不得继续为该主角色计收益。挂件自身必须通过当前班次最长工作时长和本轮累计工作时长检查，避免挂件三班无休。

宿舍容量计算必须先保留 `must_rest` / `dorm_rest` 需求，再给可选挂件分配宿舍位。未上班不自动等于进入宿舍；`off_duty` 不占宿舍恢复位。

## 7. 冲突处理：44-353

深巡和缪尔赛思必须同时进入同一轮统一裁决：

```text
深巡 package: 深巡 + 乌尔比安
缪尔赛思 package: 缪尔赛思 + 莱茵挂件
```

规则：

- 乌尔比安作为深巡硬依赖先保留，但不能靠执行顺序保证；它必须作为深巡 package 的原子资源声明。
- 缪尔赛思应优先尝试其他莱茵角色和其他合法宿主。
- 缪尔赛思只能使用容量账本中的剩余资源。
- 若缪尔赛思最低可行 package 与深巡发生冲突，应降低缪尔赛思挂件数量、切换宿主，或淘汰缪尔赛思 package。
- 不允许后来者静默移除乌尔比安后仍保留深巡 receiver 或旧 dependency。

## 8. 性能策略

不做所有 receiver、角色、房间和班次的笛卡尔积。建议：

- 每个 receiver 只生成有限数量 enabled / disabled package；
- 先按 hard dependency、容量和候选资格过滤；
- 可选挂件按 `net_support_value` 排序；
- 只保留每个 receiver 的前 K 个 package；
- 冲突只尝试有限长度的角色 / 宿主交换；
- 只重算受影响的原房间和跨设施快照；
- 结果保证声明为 hard constraints + bounded heuristic，不声称全局最优。

## 8A. 延迟绑定、收益量化与候选前沿

本问题不采用全基建动态规划。现有分设施求解仍是主路径；高级算法只处理共享真实干员、宿主容量或条件状态形成的局部冲突组件。

### 8A.1 延迟真实绑定

能力影子候选可以保留同一真实干员的多个能力视图，例如伊内丝留在原岗位、满足赫德雷的基建内存在条件，或进入会客室触发维什戴尔条件。候选阶段只登记相同的真实身份 claim，不立即写入最终 `used`；冲突分支比较完成后才提交真实 assignment。

延迟绑定只解决“候选被房间顺序提前删除”，不直接给出收益。它与挂件的 receiver、宿主和业务关系是两个层次：影子负责候选生命周期，挂件模型负责合法关系与组合边界。

### 8A.2 完整分支差分

挂件价值不能使用主体触发后的完整面板值，也不能只计算目标房间的局部增量。收益统一按完整可执行分支差分：

```text
组合净收益
  = 启用主体与挂件后的最终分支结果
  - 不启用该组合时的最佳替代分支结果
```

每条分支必须重求被移动成员的原房间，并在真实临时 assignment 上统一 `resolve`。差分因此包含主体替代、挂件原岗位损失、替补损失、宿主机会成本和受影响的跨房状态。跨设施比较若启用，当前用户裁决采用 `2%` 发电等价于 `1%` 贸易或制造；该折算只属于具名比较 policy，不是机制公式。

### 8A.3 候选前沿与局部搜索

发生跨房竞争的候选不能只保留当前单房最高效率行。候选前沿至少区分：

- 真实干员集合；
- 房间与宿主占用；
- 条件响应签名；
- 全局状态读写；
- 分域收益和被移动成员的原岗位。

只有一个候选在收益不低、资源占用不多、后续可见状态不差且组合兼容性不弱时，才能安全支配另一个候选。求解时先按真实身份、宿主容量和状态读写构建局部冲突闭包，再有限枚举完整分支。当前实现单元不采用任何动态规划、Pareto 搜索或分支限界；未来只有在已构造的局部冲突闭包内，且状态完备性已有证明时，才可把 Pareto 前沿、局部动态规划或带可信上界的分支限界作为独立优化任务。完整局部枚举仍是正确性基线。

### 8A.4 赫德雷链的后续试点

赫德雷、伊内丝、W、维什戴尔适合作为后续局部冲突组件试点，但不属于当前实现单元。至少需要区分：伊内丝和 W 的基建内存在、伊内丝是否实际位于会客室、赫德雷所在的具体贸易房、维什戴尔是否在当前中枢状态，以及对应房间订单上限和全局心情恢复。

实施该试点前必须先统一两项当前缺口：W 的合法运行时设施映射，以及赫德雷技能的“基建内存在”机制与额外“同班跟随”排班 policy 是否分开。不得从通用挂件提案反推游戏机制必须同房或同班工作。

请求参数 `support_combinations_enable` 缺省 `false`（旧请求未传同样关闭），CLI 使用 `--enable-support-combinations`。开启沿用当前主动挂件编排；关闭禁止受控 receiver 主动补挂件，哪怕只补 1–2 人，但保留主角色的普通竞争及每班真实编制读取。深巡与鸿雪豁免，普通同房不受影响，思衡托自然读取精英设施数不关闭；结城理尚无现有主动候选，本次不新增技能或组合。当前受控声明是莱茵 `rhine_support`，通过 `proactive_support` 标记；开关不是人数阈值检查，不新增通用容量、收益或轮换优化。参数合同唯一 owner 见 [输入输出与兼容](../接口/输入输出与兼容.md)。本文件其他未完成项保持开放。
