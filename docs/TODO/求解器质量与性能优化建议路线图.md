# 求解器质量与性能优化建议路线图

> 文档角色：active-change
> 生命周期状态：proposal
> 当前真源：docs/QUALITY_AND_AUDIT.md；docs/BASE_ASSIGNMENT.md；docs/PERFORMANCE_ENGINEERING.md；docs/SCORING_MODEL.md
> 摘要：以证据门禁协调求解质量、联合选择和热路径性能优化建议

## 1. 文档定位

本文是一份跨求解器的建议组合与决策路线图，不是已经授权的实现计划，也不改变当前产品
保证。它只负责：

- 说明建议先后顺序、依赖和进入实现前的证据门禁；
- 把正确性、求解质量、safe reduction、cache 和纯性能工程分开；
- 将已有事项路由给唯一 active-change owner；
- 为尚无 owner 的建议声明何时值得拆成独立任务。

本文不拥有业务机制、候选准入、评分公式、跨房 bug 归因、动态 producer、Bake schema、制造
联合保证或排班模式。现有 owner 的算法、实施步骤和验收只在其 active change 中维护，本文
不建立平行 checklist。

任何建议获得用户授权后都必须拆成一个主要意图明确的任务，由对应 owner 建立 writer；不能
把整份路线图标为 `in-progress` 后同时修改多个责任边界。

## 2. 为什么值得保留这份建议

当前实现使用领域分解控制组合爆炸：Rule/System 先生成 Plan，单房在当前候选池中组合搜索，
多房按稳定顺序 `resolve -> search -> commit`，少量动态 producer 做 presence 候选比较，兼容
查询可使用 Bake。这个方向适合当前机制复杂、房间容量小且要求解释结果的产品。

仍有三类跨任务问题需要一个轻量路由页：

1. 当前缺少统一的成本基线，无法判断时间主要花在组合生成、真实 solver、重复 resolve、
   producer prefix、rotation 复算还是 cache miss。
2. 当前逐房路径不保证全局最优，但跨房 bug、制造贪心、动态 producer bootstrap 和普通 policy
   限制分别属于不同 owner，不能用一个“上 CSP”方案混修。
3. `top_k`、standalone、Bake、memo、并行和候选完整性容易被混为同一种“优化”，实际保证
   和证明义务不同。

当前规模、候选池和 Bake 门禁见[性能工程](../PERFORMANCE_ENGINEERING.md)；搜索保证与结果状态
见[质量与审计](../QUALITY_AND_AUDIT.md)。

## 3. 质量任务契约

| 项目 | 本路线图建议 |
|---|---|
| 唯一质量不变量 | 优化不能静默改变合法候选集合、正式 objective 或最终机制结算；改变搜索空间时必须显式报告保证等级和结果状态 |
| 当前基线 | `build_plan -> execute_plan -> fill -> resolve`、逐房提交、producer presence 比较和兼容 Bake/live fallback |
| 当前默认结果状态 | 多房逐房路径默认为 `BEST_FOUND`；只有对明确候选宇宙和具名 policy 已证明最优时，才能使用 `POLICY_OPTIMAL` |
| 预期收益 | 先量化成本与结果边界，再以最小风险减少重复求值；只有证据和产品要求命中时才恢复 exact joint 或条件化 Bake |
| 迁移边界 | 保留 Rule/Plan、正式单房 solver、`resolve_base` 和评分 canonical；优化任务只改变已授权的候选生成、遍历、联合选择或缓存方式 |
| 最低证明 | 小规模 oracle、开关 differential、候选完整性、pruning on/off、live/Bake 一致、真实入口和分阶段性能证据中与风险匹配的子集 |
| 停止条件 | 达到用户确认的质量/性能预算，或证据表明剩余收益不值得复杂度；不得因“还能更快”继续扩张 |

## 4. 唯一 Owner 路由

| 事项 | 唯一 active-change owner | 恢复或处理条件 |
|---|---|---|
| 用户报告的跨房错误、最小反例、首次违规层和后续 owner | [跨房计算错误归因与联合求解评估](跨房计算错误归因与联合求解评估.md) | 用户提供错误样本；先区分结算、候选、Plan、提交、上下文、比较器和 cache |
| 制造逐房贪心的 oracle 与保证评估 | [近期已知缺口修复清单](近期已知缺口修复清单.md) 第 4 项 | 独立授权 solver assurance 调查；不预设必须联合搜索 |
| 动态 producer 候选列、exact indexed Join、winner commit 和 dependency | [动态 Producer A+](DYNAMIC_PRODUCER_BAKED_SEARCH_PLAN.md) | 归因命中 producer bootstrap/response affected closure，或产品要求其 exact 多房保证 |
| 条件化单房 response、分片、校验、原子发布和 runtime query | [设施无关条件化响应 Bake](CONDITIONAL_ROOM_RESPONSE_BAKE_PLAN.md) | live 语义稳定、用户确认预算且 profile 证明 cache 有收益 |
| 业务 objective、权重和跨域可比性 | [评分口径](../SCORING_MODEL.md) | 任何新比较器或跨域邻域开始前先获得 canonical 裁决 |
| 单班当前保证和落位生命周期 | [单班编制](../BASE_ASSIGNMENT.md) | 实现完成后吸收已确认的当前事实 |

路由规则：

- 固定 assignment 已算错时进入 maintenance 的机制/data/resolve owner，不恢复联合求解。
- 合法候选未进入搜索时修 pool/capability/Plan owner，不用更大 Top-K 碰运气。
- 只有动态 producer bootstrap 或其 response 闭包产生错误 winner 时才恢复 A+；普通制造或普通
  多房冲突不能塞入 A+。
- 现有 owner 没有覆盖的独立性能或接口建议，在获得授权时新建 active change；不在本文直接
  实施。

## 5. 保证分类门禁

任何建议拆成实施任务前必须先选择保证等级：

| 等级 | 允许的典型用途 | 最低证明 |
|---|---|---|
| `hard_constraint` | `used`、capacity、required anchor、forbid、tier/operbox 可用性 | 激活、拒绝、边界反例和最终可行性 |
| `safe_reduction` | 对完整 objective、全部约束和下游身份影响均已证明等价的中枢无技能 filler；同构房对称去重；可采纳上界 | 关闭缩减 differential、小实例 oracle 或等价证明 |
| `search_heuristic` | 只改变访问顺序或资源分配，且实际保留可恢复的完整 exact 路径 | exact 路径 differential、停止与 fallback |
| `policy_restriction` | standalone 候选宇宙、具名房间顺序、用户选择的速度模式 | 输出 policy 范围，不能冒充 canonical 全空间最优 |
| `approximation` | 固定预算、候选截断、只搜索有限邻域且不恢复完整空间 | 显式预算、停止原因、恢复路径和 `BEST_FOUND`/`TIME_LIMIT` |
| `cache` | Bake、充分 signature memo、预编译静态贡献 | fresh-vs-cache、失效门禁、miss 只变慢和损坏 fallback |

有限 2-opt/两房邻域如果没有继续恢复完整搜索，默认属于 `approximation`，不是
`search_heuristic`。即使某个两房闭包完整枚举，也只能声明该闭包 exact，不能推广为全基建
exact。

`top_k` 默认只是结果保留策略。实时搜索若先求值全部合法组合再截断，不得把减小 K 报告成
求值次数下降；下游需要完整候选行时也不得复用固定 Top-K 列。

## 6. 推荐方向与依赖

以下是建议组合，不是本文拥有的实施阶段。

### 6.1 建议 A：先建立跨求解器成本基线

这是建议优先拆出的独立 quality task。它只测量成本，不拥有跨房正确性 oracle 或算法裁决。

建议记录：

- 固定机器、构建模式、layout、operbox、policy、预热方式和重复次数；
- 每个设施的候选池人数、`C(n,k)`、evaluated、solver 调用数和拒绝原因；
- producer 数、presence subset、上界剪枝、完整 prefix 和 `resolve_base` 次数；
- Bake compatibility miss、row/response hit、加载时间、内存和 live fallback；
- peak、gamma、最终评分和完整 rotation 的分阶段耗时；
- release cold/warm 分布，而不是单个 debug 样例。

启动门禁：用户授权独立性能调查。

交付：task-scoped evidence、机器可读计数和一页热点结论。该任务不得据性能日志直接改变
候选、objective 或结果状态。

### 6.2 建议 B：建立结果保证可观察性

这是建议独立授权的接口/质量任务，不由本文直接修改 API。

建议内部 report 至少能表达：

- `EXACT_OPTIMAL`、`POLICY_OPTIMAL`、`BEST_FOUND`、`UNKNOWN/TIME_LIMIT`；
- `INFEASIBLE` 与 `NO_CANDIDATE_UNDER_POLICY` 的区别；
- 候选宇宙：full pool、standalone、capability expansion、Plan-constrained；
- 启用的 reduction、heuristic、policy、approximation、cache 和 fallback；
- objective 名称、版本、分量、显式权重和 tie-break。

启动门禁：当前调用方无法判断结果保证，并且用户授权新增内部字段或对外契约。对外暴露时
必须另行审计 CLI/前端兼容，不在质量任务中顺手改 wire schema。

验收：只增加观察能力时 winner 完全不变；逐房路径不会被误报为 `POLICY_OPTIMAL` 或
`INFEASIBLE`。

### 6.3 建议 C：按 Profile 拆分单房热路径任务

只有建议 A 证明具体热点后，才从下表选择一个 owner-local 任务：

| 候选优化 | 分类 | 前提 | 核心证明 |
|---|---|---|---|
| required anchor 直接生成 `C(n-m,k-m)` | `safe_reduction` | 当前入口先生成全部组合再过滤 anchor | 多 anchor、缺 anchor、capacity、禁配和旧/new winner differential |
| worker-local bounded Top-K heap | 行为保持型性能优化 | 该 API 的下游只消费 Top-K | 完整 Top-K、best、stable tie-break 与旧全量排序一致 |
| 组合 rank/unrank 或分块 indexed iterator | 行为保持型性能优化 | 组合物化或调度是实际热点 | release benchmark、峰值内存和确定性合并 |
| 静态 atom/tag/variant 编译结果复用 | `cache` | 重复编译是实际热点且 key 可完整 fingerprint | 动态 context 排除、fingerprint miss 和 fresh/cache differential |
| 充分 response signature 下的 resolve memo | `cache` | profile 证明同一充分状态重复 resolve | signature 充分性、memo on/off、winner live resolve |

限制：

- complete-row API 和 Top-K report API 必须保持不同契约；联合选择不能消费被截断的调试列。
- 不因出现第二个调用点就强制建立通用抽象；只有真实重复语义或证明责任更清楚时才提取。
- 热点消失或达到用户预算后停止，不为了技术新颖性重写所有设施。

### 6.4 建议 D：用归因证据决定多房质量改进

多房质量工作必须从现有归因 owner 开始：

1. 固定最终 assignment 重算，先区分结算错与选型错。
2. 检查候选全集、Plan、`used`、房间顺序和上下文快照。
3. 只有疑似分解问题才建立对应域的小规模完整 tuple oracle。
4. 按首次违规层路由局部修复、制造 assurance、动态 A+ 或新的普通联合选择任务。

如果证据只证明同一具名 comparator 域内存在有价值的顺序冲突，可以另行提议有限邻域优化；
该任务默认是 `approximation`，必须报告预算、停止原因和 `BEST_FOUND`。跨贸易/制造或其他域的
邻域不能使用匿名加权；必须先由评分 canonical 裁决。动态 producer 场景直接消费 A+ 已确认的
具名 comparator，不在本文复制。

如果产品要求受影响闭包 exact，则由相应 owner 冻结候选行、充分 response signature、正式
objective、完整临时 assignment resolve 和终止证明。普通跨房问题没有既有 owner 时，应在归因
完成后新建独立 proposal，而不是扩大动态 Producer A+。

### 6.5 建议 E：Exact Join 只在对应 Owner 中恢复

动态 producer 的候选行、logical mask、indexed Join、winner 一次 commit 和回归矩阵已经由
[动态 Producer A+](DYNAMIC_PRODUCER_BAKED_SEARCH_PLAN.md)拥有。本文只保留三个通用提醒：

- 当前按 index vector 返回首个不冲突 tuple 的 helper 不等于按总 objective 最优；
- 固定 Top-K 不能证明完整 Join；
- winner 必须写入完整临时 `BaseAssignment` 后统一 `resolve_base`。

算法选择仍由 A+ 在恢复时根据其 Phase 0/2 证据裁决。若未来普通多房新任务评估 CP-SAT/MILP，
只允许在“真实 solver 已生成的候选行选择层”建模每房一行、人员互斥和已确认约束；不得复制
EffectAtom、L2/L3 或 required admission。

### 6.6 建议 F：Producer 压缩与 Bake 不重复立项

Producer effect signature、candidate catalog、resolve memo 和安全上界属于动态 Producer A+。
条件 response 物化、分片、checksum、原子发布和 runtime query 属于条件化 Bake。恢复顺序应为：

```text
live 候选语义与 comparator 稳定
  -> 用户确认预算
  -> profile 证明重复求值/cache miss 是热点
  -> 恢复对应 owner
  -> live/Bake differential 后启用
```

Cache miss、损坏、未知 variant 或不兼容只能进入同语义 live 路径，不能缩小候选集合、降低
保证或恢复旧 Top-K/per-producer pipeline。

### 6.7 建议 G：排班优化保持 Deferred

单班选择边界和保证未稳定前，不建议把问题扩为连续时间全局优化。未来只有出现独立证据和
授权时，才新建排班质量任务评估：

- peak 候选与 H1/H2/γ 可行性的机会成本；
- 固定 timed profile 内的小规模 cohort 选择；
- profile-specific 构造和共享 capacity/bind/feasibility validator 的责任边界。

该任务不能改变已确认班次时长或 hard profile。涉及 Team/Shift、bind 或导出时必须附加 system
audit，并用真实 `plan` 与 MAA 证明 fidelity。本建议不恢复心情预算或连续时间优化。

## 7. 建议目标边界

如果对应 owner 最终证明候选行抽象有价值，长期接口可以区分：

```text
Rule / Plan / hard admission
        |
        v
enumerate_complete_rows(context, constraints)
        |
        +----> search_top_k(...)          # 单房报告/调试
        |
        +----> select_disjoint_rows(...)  # 已授权的受影响闭包
                         |
                         v
              temporary assignment
                         |
                         v
                 resolve_base + real solvers
```

这是责任边界建议，不是本文批准的新模块。候选层只可携带房间、logical mask、variant/effect
signature、具名 objective 分量和稳定 id；跨房上下文必须证明是充分签名后才能用于索引或 memo。

## 8. 决策表

| 观察结果 | 优先动作 | 不应做的事 |
|---|---|---|
| 固定 assignment 结算错误 | maintenance 修正式 solver/data/resolve owner | 建联合搜索掩盖机制错误 |
| 合法候选未入池 | 修 pool/capability/Plan eligibility | 用更大 Top-K 碰运气 |
| 单房生成/排序占主要耗时 | 从建议 C 拆一个 owner-local 任务 | 先加人员白名单 |
| 相同充分 signature 重复 resolve | 恢复对应 owner 的精确 memo 工作 | 用不充分 context hash 缓存永久分数 |
| 制造两房 oracle 优于 greedy | 恢复已知缺口第 4 项并等待其裁决 | 直接扩大动态 Producer A+ |
| 动态 producer bootstrap 错误 winner | 恢复动态 Producer A+ | 新建 per-producer pipeline |
| 普通同域多房存在重要 gap | 归因完成后新建独立 proposal | 未裁决 comparator 就做跨域 2-opt |
| live 正确、Bake 错或 miss 成本高 | 恢复条件化 Bake/发布安全 owner | 让 miss 走旧 Top-K 路径 |
| 已达用户预算且 gap 可接受 | 停止优化并记录保证 | 为技术新颖性引入 DP/Pareto/CP-SAT |

## 10. 通用验收要求

### 10.1 候选与合法性

- full pool、standalone、capability expansion、mixed tier 和缺成员；
- anchor、capacity、`used`、forbid 和逻辑干员 variant 去重；
- 不同 operator mask 共享 response 时仍保留各自兼容性。

### 10.2 Objective 与状态

- objective 分量、显式权重、词典序、稳定 tie-break 和等价最优；
- `BEST_FOUND`、policy-limited、budget-stopped、no-candidate 和 proven infeasible；
- 跨域比较只有 canonical 已裁决时才存在。

### 10.3 Reduction、Cache 与性能

- reduction/memo/cache on/off winner differential；
- 与风险匹配的小实例 oracle；
- cold/warm、hit/miss、损坏、旧 schema、未知 variant 和非标准 layout；
- release 阶段耗时、峰值内存、solver/resolve 调用数和重复运行分布。

### 10.4 单班、Rotation 与导出

- 单班容量、全局无重复、required anchor 和最终 snapshot；
- producer/consumer presence、休息班效果关闭和中枢满编；
- profile、stdout 和 MAA 消费同一 rotation 结果，不在导出层重新选型。

具体验收矩阵由对应 owner 按改动风险细化；本文的通用列表不能替代 A+、Bake、制造 assurance
或 system audit 的专门证明。

## 11. 风险清单

| 风险 | 控制措施 |
|---|---|
| 第二份 active-change 重复拥有实现 | 本文只记录优先级和路由；已有事项不重复 checklist |
| 把局部 exact 误报为全局 exact | 结果状态携带候选宇宙、闭包和 policy；当前逐房默认 `BEST_FOUND` |
| 把有限邻域误标为 heuristic | 无 exact fallback 时统一按 `approximation` 验收 |
| 固定 Top-K 删除唯一可兼容行 | complete-row 契约不截 K；联合 owner 证明停止条件 |
| 不充分 signature 复用错误分数 | winner live resolve；不一致拒绝 memo/catalog |
| CP-SAT 形成第二套机制真源 | 只消费正式 solver 候选行，不编码技能公式 |
| 匿名跨域目标进入局部优化 | 同一具名 comparator 域门禁；跨域先由评分 canonical 裁决 |
| 只优化 debug 样例 | 同机器 release 基线、多个 operbox/layout 和重复分布 |
| 并行化破坏确定性 | worker 私有结果、统一稳定合并和等价最优测试 |
| 过度通用化拖慢当前任务 | 每个抽象要求真实重复语义或更清晰证明义务 |

## 12. 明确不建议

- 不把整个 EffectAtom、L2/L3 和排班一次性重写成 MILP/SAT。
- 不对所有房间、班次和心情时刻做全基建笛卡尔积。
- 不继续增加按干员名维护的 standalone 特判来解决性能问题。
- 不靠降低 `top_k` 宣称减少实时 solver 调用。
- 不 Bake 当前 winner、固定攻略套餐或完整 operbox/`used` 状态。
- 不在缺少 profile、oracle 和用户预算时提前建设通用 DP、Pareto 或 B&B 框架。
- 不让 cache、shortcut、priority 或 tag 接管 required admission。
- 不自动恢复 Mower 动态换班、完整心情优化或匿名跨域总分。
