# 菲亚梅塔宿舍回岗可用性缺口

> 文档角色：active-change
> 生命周期状态：proposal
> 当前真源：docs/菲亚梅塔使用规则.md；docs/定时换班.md
> 摘要：记录定时换班中菲亚梅塔使用后未由排班与 MAA 产物强制回宿舍，因而无法证明跨周期持续可用的缺口

## 1. 当前事实

`44-353-operbox.json` 拥有 E1 80 级菲亚梅塔，使用 `main_backup_12_12` 与 243 布局。当前 `schedule_main_backup_12_12` 在两个 12h 班次开始分别选择合法菲亚目标，但两个 `RotationStateSpec` 都设为 `dorm_rest: None`。

MAA 导出只映射已决定的 `Fiammetta.enable`、`target` 与 `order`。普通宿舍填充仅消费当前 assignment 中已有宿舍成员和 resting team；菲亚梅塔不属于其中任一集合，因此不会写入宿舍槽位。

这不是 `44-353` 的深巡 -> 乌尔比安挂件冲突。后者由《跨体系挂件资源与轮换裁决设计》单独跟踪，不得混合修复。

## 2. 已确认边界

[定时换班](../定时换班.md) 已裁决：菲亚梅塔使用后返回宿舍、实际拖动及宿舍一号位由 MAA 或人工执行者负责；InfraCalc 不声明或强制宿舍槽位。菲亚规则也明确不扩展为完整实时心情曲线、跨周期永续排班或宿舍槽位模拟。

因此，当前输出可表达“本班执行菲亚动作”，不能证明“菲亚已回宿舍并在下一次固定使用前恢复满心情”。`main_backup_12_12` 的相邻动作间隔为 12h；菲亚在宿舍每小时固定恢复 2 点，执行侧立即送回宿舍时可恢复满心情，但该条件不受当前产物或最终状态 gate 验证。

## 3. 后续修复前提与责任边界

若产品要求求解器保证菲亚跨周期持续可用，先裁决是否将“菲亚使用后回宿舍”从执行建议升级为排班输出契约。未经该裁决，不得在单个 operbox、房号、Shift 下标或 MAA JSON 上添加补偿特判。

获授权后的单一实现单元应：

1. 由 schedule 为每个菲亚动作声明可验证的回宿舍状态，而非让 export 推断。
2. 由 MAA export 忠实投影该状态；若 MAA 契约无法表达，则明确保留执行侧责任，不能伪造保证。
3. 在 Rust 最终状态上验证菲亚动作后的休息、恢复间隔与下一次 ready 条件；Python 仅批量调用 Rust gate。
4. 使用 `main_backup_12_12` 的 `44-353` 与至少一个无合法菲亚目标的反例，检查动作、宿舍状态和 MAA 产物的一致性。

## 4. 非目标

- 不把定时换班扩展为 Mower 动态换班、完整心情曲线或全局心情最优。
- 不改变菲亚动作次数、固定时机或目标优先级。
- 不处理深巡、乌尔比安、缪尔赛思的跨体系挂件容量冲突。

只读检查已完成；未修改代码、canonical 或 MAA 产物。该任务等待用户对输出契约范围的裁决后再恢复。
