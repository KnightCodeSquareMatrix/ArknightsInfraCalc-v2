# 菲亚梅塔宿舍回岗可用性缺口

> 文档角色：active-change
> 生命周期状态：proposal
> 当前真源：docs/菲亚梅塔使用规则.md；docs/定时换班.md
> 摘要：记录定时换班菲亚梅塔动作未由排班与 MAA 产物强制回宿舍，因而无法证明跨周期持续可用的缺口

> 当前范围补充（2026-10-19）：独立 `fiammetta_witch_12_12` profile 已由用户裁决删除，不再是产品模式或本缺口的覆盖目标；普通菲亚动作 profile 仍按下述宿舍责任边界处理。

## 1. 当前事实

`44-353-operbox.json` 拥有 E1 80 级菲亚梅塔，使用 `main_backup_12_12` 与 243 布局。当前各类定时换班 profile 生成 `FiammettaShiftAction` 后，均没有为该动作生成对应的菲亚梅塔宿舍休息状态；`main_backup_12_12` 的两个 `RotationStateSpec` 只是已确认的直接例子，均设为 `dorm_rest: None`。

当前需要覆盖的 profile 包括：`abc_12_6_6`、`abc_12_12_12`、`main_backup_12_12`、`fiammetta_8_8_4_4`，以及后续任何包含菲亚梅塔动作的 profile。统一不变量应为：

```text
shift.fiammetta.is_some() => shift.dorm_rest 必须包含菲亚梅塔
```

MAA 导出只映射已决定的 `Fiammetta.enable`、`target` 与 `order`。普通宿舍填充仅消费当前 assignment 中已有宿舍成员和 resting team；菲亚梅塔不属于其中任一集合，因此不会写入宿舍槽位。

这不是 `44-353` 的深巡 -> 乌尔比安挂件冲突。后者由《跨体系挂件资源与轮换裁决设计》单独跟踪，不得混合修复。

## 2. 已确认边界

[定时换班](../定时换班.md) 已裁决：菲亚梅塔使用后返回宿舍、实际拖动及宿舍一号位由 MAA 或人工执行者负责；InfraCalc 不声明或强制宿舍槽位。菲亚规则也明确不扩展为完整实时心情曲线、跨周期永续排班或宿舍槽位模拟。

因此，当前输出可表达“本班执行菲亚动作”，不能证明“菲亚已回宿舍并在下一次固定使用前恢复满心情”。不同 profile 的动作间隔和状态结构不同，不能只用 `main_backup_12_12` 的 12h 间隔作为证明；每个 profile 都必须按自身动作时机验证恢复时间和下一次 ready 条件。菲亚在宿舍每小时固定恢复 2 点，执行侧立即送回宿舍时才可能满足恢复条件，但该条件不受当前产物或最终状态 gate 验证。

## 3. 当前需要修复的位置

修复应由 schedule 统一负责，不在单个 profile 或 MAA export 中分别补偿：

| 位置 | 当前问题 | 修复方向 |
|---|---|---|
| `crates/infra-core/src/schedule/team_rotation.rs` 各 profile 构造 | 只生成 `FiammettaShiftAction`，未生成对应宿舍事实；部分状态显式为 `dorm_rest: None` | 在状态组装完成后统一扫描所有 `fiammetta` 动作，为每个动作附加菲亚梅塔 `dorm_rest`；覆盖普通班次与 `FiammettaOnly` 事件态 |
| schedule 的 `RotationStateSpec` / `DormRestPlan` 类型与 finalization 路径 | 当前状态模型无法表达“菲亚动作后固定回宿舍第一位” | 优先扩展现有宿舍计划结构，由 schedule 决定宿舍、固定置前成员和容量预留，不让 export 推断 |
| `crates/infra-core/src/export/maa.rs:567-602` `build_dorm_slots` | 只消费 assignment 和 resting team，菲亚不在候选输入中 | 忠实投影 schedule 已决定的菲亚宿舍事实；先放菲亚，再放硬性休息成员和普通补位，保持去重与容量限制 |
| `crates/infra-core/src/export/maa.rs:267-296` `build_plan` | 菲亚动作与宿舍列表没有可验证的关联 | 确保同一计划中的菲亚动作和宿舍状态保持一致；若 MAA 无法表达动作后的执行顺序，先扩展输出契约或明确 warning，不能静默声称保证 |
| Rust 最终 rotation invariant gate | 当前已有目标跨班在岗等菲亚断言，但没有回宿舍、第一位置和恢复间隔断言 | 增加 profile 无关的最终状态断言，并覆盖合法动作、无目标、容量不足和 `FiammettaOnly` 反例 |

宿舍容量顺序必须是：菲亚梅塔固定占位 -> `must_rest` / 已确定的 `dorm_rest` -> 普通休息成员 -> 可选挂件和普通补位。容量不足时只能减少可选成员、转为 `off_duty` 或使 profile 明确失败，不能静默丢弃菲亚或挤掉硬性休息成员。

## 4. 后续修复前提与责任边界

若产品要求求解器保证菲亚跨周期持续可用，先裁决是否将“菲亚使用后回宿舍”从执行建议升级为排班输出契约。未经该裁决，不得在单个 operbox、房号、Shift 下标或 MAA JSON 上添加补偿特判。

获授权后的单一实现单元应：

1. 由 schedule 为所有 profile 的每个菲亚动作声明可验证的回宿舍状态，而非让 export 推断。
2. 由 MAA export 忠实投影该状态，并默认将菲亚梅塔放在目标宿舍第一位；若 MAA 契约无法表达动作后的回宿舍顺序，则先扩展契约，不能伪造保证。
3. 在 Rust 最终状态上按 profile 验证菲亚动作后的休息、恢复间隔与下一次 ready 条件；Python 仅批量调用 Rust gate。
4. 使用 `44-353` 覆盖 `main_backup_12_12`，并补充 ABC、菲亚四班、巫恋二班、无合法目标和宿舍容量不足反例，检查动作、宿舍状态和 MAA 产物的一致性。

## 5. 非目标

- 不把定时换班扩展为 Mower 动态换班、完整心情曲线或全局心情最优。
- 不改变菲亚动作次数、固定时机或目标优先级。
- 不处理深巡、乌尔比安、缪尔赛思的跨体系挂件容量冲突。
