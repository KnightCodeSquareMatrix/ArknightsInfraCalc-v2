# 发电效率共享基础重复计算分析（2026-08-27）

> 文档角色：active-change
> 生命周期状态：proposal
> 当前真源：docs/DRONES.md
> 摘要：记录排班求解中发电效率按电站重复计算的现象、根因和 shell 验证结果

## 1. 问题描述

排班求解结果中，每个物理发电站的 `final_efficiency` 都包含 `1.000` 基础效率，随后排班汇总把各发电站的结果直接相加。因此有两个或三个发电站时，输出会把全基建共享的基础 100% 重复计算。

这不是轮班时间加权或前端格式化问题。时间加权发生在错误的跨站总和之后，无法消除重复基础。

## 2. 领域不变量

根据 [DRONES.md](../DRONES.md) §2、[EFFICIENCY_MODEL.md](../EFFICIENCY_MODEL.md) §3.4 和 [ADR 0009](../ADR/0009-drone-efficiency-conversion-and-production-accounting.md) D1：

```text
power_efficiency
  = 1.000
  + sum(有效发电干员技能效率)
  + sum(有效发电干员进驻效率)
  + 其他已裁决的发电增量
```

`1.000` 属于全基建共享，只计算一次。发电站数量只增加可用岗位；零心情干员仍可占位或满足明确联动，但不贡献技能效率和进驻效率。

## 3. 实际复现

复现入口为固定编制结算：

```text
cargo run -q -p infra-cli -- layout eval \
  --layout data/layout/252.json \
  --operbox data/fixtures/243/operbox_full_e2.json \
  --assignment data/schedule_243/assignment_automation_trio_e2.json \
  --explain-json
```

修复前输出的关键值：

| 电站 | 单站 `final_efficiency` | 单站 `base_efficiency` | 单站技能增量 |
|---|---:|---:|---:|
| `power_1` | 1.135 | 1.000 | 0.135 |
| `power_2` | 1.200 | 1.000 | 0.200 |
| 合计 | 2.335 | 重复两次 | 0.335 |

按 canonical，正确总效率应为：

```text
1.000 + 0.135 + 0.200 = 1.335
```

三电站入口复核使用：

```text
cargo run -q -p infra-cli -- layout eval \
  --layout data/layout/243.json \
  --operbox data/fixtures/243/operbox_full_e2.json \
  --assignment data/schedule_243/assignment_0_12H第一班.json \
  --explain-json
```

当前关键值为 `1.135`、`1.200`、`1.200`，报告合计 `3.535`。修正后应为：

```text
1.000 + 0.135 + 0.200 + 0.200 = 1.535
```

shell 计算验证采用：

```text
corrected = reported - (active_station_count - 1) × 1.000
```

两组实际结果分别得到 `1.335` 和 `1.535`，与共享基础只计算一次的公式一致。

## 4. 根因与首次违规位置

首次允许错误状态的位置是：

```text
crates/infra-core/src/power/solver.rs:88-100
```

`solve_power` 每次接收一个 `PowerRoomInput`，在非零心情时无条件返回：

```rust
base_efficiency: Efficiency::ONE,
final_efficiency: Efficiency::ONE + skill_efficiency + ramp_efficiency,
```

这个单站结算没有表达共享范围，导致每个站的结果都携带一份 `1.000`。单站展示本身并非问题；问题在于该站级值被当成可直接跨站相加的全局值。

## 5. 错误传播路径

1. `search/power.rs:156` 将每个命中站的 `final_efficiency` 加入搜索报告总值。
2. `layout/assign/commit.rs:133-139` 将单站 `final_efficiency` 保存到 `power_final_efficiency` 快照。
3. `schedule/base_rotation.rs:292-320` 逐站读取或重新结算，并在第 312 行直接累加。
4. `schedule/team_rotation.rs:5034-5038` 对班次加权结果求日汇总。
5. `crates/infra-cli/src/commands/layout.rs:645-719` 的解释性结算也逐站直接相加。

因此不能只修 `team_rotation` 的时间权重，也不能修前端输出；至少所有跨站总效率聚合都必须消费同一套全局基础规则。

## 6. 验证结论

在不修改代码的前提下，shell 对当前真实 CLI 输出执行“扣除多余共享基础”的等价计算，得到 canonical 预期值。由此确认：

- 本 bug 的数值修正方式在当前复现上有效；
- 修正量是 `(有效电站数 - 1) × 1.000`，不是固定扣除 1.000 或按物理站数盲目处理；
- 零心情电站不应被计入有效基础站数，因其当前 `final_efficiency` 为零；
- 单站 `PowerResult` 必须只表示岗位增量，跨站总效率由统一聚合器注入共享基础。

这只是候选修复的 shell 验证，不代表源码已经修复，也没有改变当前工作树中的 Rust、数据或测试文件。

## 7. 建议修复方式

建立唯一的跨站发电效率聚合 owner，统一计算：

```text
global_power_efficiency
  = 1.000
  + sum(each active station's non-base increments)
```

最小实现方向可以是：保留单站 `PowerResult` 的展示分解，但跨站汇总不再直接求和包含基础的 `final_efficiency`；改为共享基础只注入一次，再累加各站技能、进驻和爬升等有效增量。搜索报告、排班快照投影、轮换汇总和 CLI 解释输出必须使用同一聚合语义，不能各自补偿。

## 8. 验收要求

- 2 电站反例：`1.135 + 1.200` 的报告值修正为 `1.335`。
- 3 电站反例：`1.135 + 1.200 + 1.200` 的报告值修正为 `1.535`。
- 单站有效技能、进驻和爬升增量保持不变。
- 零心情占位站不贡献基础、技能或进驻效率，但保留明确允许的跨设施联动。
- 排班班次加权、日汇总、搜索报告、快照和 `layout eval --explain-json` 结果使用同一全局发电效率。
- 不使用布局编号、房间编号、班次下标或干员姓名特判。
