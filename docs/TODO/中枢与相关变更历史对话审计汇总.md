## 8. 效率口径与每日产出

```text
中枢加成 = 中枢全局制造/贸易效果
技能效率 = 生产房干员组合的技能结果
总效率   = 基础效率 + 中枢加成 + 技能效率
```

```text
完整周期产出 = 所有班次、所有房间产出相加
```


必须遵守：

- 龙门币订单只贡献 `lmd`。
- 龙门币订单交付所需赤金不进入最终产物汇总。
- 不返回 `gold_consumption`，后端不计算每日赤金净值。
- `orundum` 只来自贸易站开采协力合成玉订单。
- `originium_shards` 只来自制造站源石碎片产线。
- `12/12/12` 按 36h 总周期归一到 24h，而不是直接把三班当成三天。
- 汇总器可以遍历任意已生成的班次数量和时长，但当时 `TimedRotationProfile` 仍是闭集，入口不支持任意自定义班次数组。

## 9. 排班、办公室和会客室

### 9.1 普通排班 profile

用户特别要求区分：

- 歌蕾蒂娅使用 `7/5/7/5`，不能被普通中枢规则替代。
- 显式 profile 不应静默降级。

### 9.2 办公室和会客室复用

用户纠正了“每班使用不同办公室角色”的旧理解：

- 无额外心情消耗时，`12/12/12` 和 `12/6/6` 都可以使用两个不同角色做 `AAB`。
- A 可以工作两个 12h 班、休息一个 12h 班；B 工作一个 12h 班。
- 只要 A 的心情能够支持，不应为了形式上的每班换人而拆成更多角色。
- 有额外消耗时，必须检查单班最长工作时间和整个周期累计工作时间。
- 地灵 E1 办公室 `+2/h`，约 `8.72h` 上限，因此不能进入 12h 办公室班。
- 见行者 E2 会客室同理，不能进入 12h 会客室班。
- 斥罪约 `19.2h` 累计上限，不能作为 `12/12/12` 的 24h 主力，但可能作为只工作一个 12h 班的替补。
- 绑定角色仍必须跟随消费方同上同下；少换人策略不能破坏绑定。

### 9.3 办公室策略

用户要求办公室选人时考虑完整价值：

- 先比较凯尔希·思衡托带挂件后的办公室效率与其他候选。
- 若办公室效率相同，优先普通角色，减少挂件位置和轮换依赖。
- 若思衡托 package 有更高的完整全域收益，才启用；不能只看办公室单项数值。
- 对搓玉制造或贸易类布局，可在不降低核心生产结果的前提下优先最高效率办公室角色。

## 10. 凯尔希·思衡托与挂件设计

### 10.1 用户确认的挂件名单

用户补充：凯尔希·思衡托需要指定精英干员在不同设施中作为挂件，名单为：

```text
迷迭香、煌、逻各斯、烛煌、电弧、真言、机械师
```

用户要求：

- 只有名单内、实际进驻、满足精英条件的干员才计数。
- 支持角色可以进入任意一间合法设施，但要计算原岗位机会成本。
- 思衡托和挂件必须同班，不能读取休息班挂件。
- 同一物理设施房间内多名指定角色只计一个设施。
- 最多计 5 个不同设施房间。
- 迷迭香、烛煌或机械师如果本来已经因生产/发电被选中，可以作为低额外成本的机会性挂件。

### 10.2 用户对挂件选择的核心要求

用户提出的选择逻辑是：

1. 先计算当前 box 下思衡托能达到的办公室效率。
2. 如果思衡托 package 明显高于其他候选则启用；同效率时优先不占挂件的普通角色。
3. 再计算需要多少挂件；烛煌、机械师等本身有基建生产技能时，在机会成本相近时提高优先级。
4. 挂件不足时，允许有对应技能的角色进入加工站、会客室，最后才考虑宿舍补位。
5. 多个 receiver 同时需要挂件时必须统一处理资源冲突。

用户给出的 44-353 反例：

- 深巡进入贸易站，需要乌尔比安挂件。
- 缪尔赛思进入发电站，也可能需要乌尔比安。
- 缪尔赛思的挂件选择覆盖了深巡的挂件，导致宿舍中看不到乌尔比安。

### 10.3 推荐但未完成的通用抽象

历史对话建议使用通用资源分配，而不是每个技能写一套 if：

```text
SupportDemand
SupportCandidate
SupportPlacement
PresencePattern
```

需求应声明 owner、最小/最大数量、候选 tag、允许设施、是否同班、共享策略、优先级和单位收益；候选应包含实际房间、设施、Team/presence vector、当前 owner 和机会成本。

核心比较应是：

```text
挂件边际收益 - 离开原设施造成的机会成本
```

建议流程：

```text
完整 baseline
→ 生成 receiver + 挂件候选
→ 处理实际房间和班次冲突
→ 抽走挂件后重新补原岗位
→ 重新 resolve
→ 与 baseline 比较
→ 只提交完整收益更高的方案
```

用户在讨论复杂挂件设计时明确要求避免穷举和大量 if，以免拖慢运算并阻塞未来技能更新。该设计仍是提案，不能当作当前代码能力。
