# 菲亚梅塔 Shadow Candidate 收益比较讨论记录

> 文档角色：active-change
> 生命周期状态：proposal
> 当前真源：docs/菲亚梅塔使用规则.md；docs/定时换班.md；docs/QUALITY_AND_AUDIT.md
> 摘要：记录菲亚梅塔两类贸易策略的 Shadow Candidate 讨论、插入时机约束和完整收益比较未决项

## 1. 讨论背景

2026-08-28 15:01:32 至 19:01:32 UTC 的 feedback annotations 中有四条
菲亚梅塔 critical 反馈：

- 菲亚梅塔轮换了但书，但但书没有在对应后续班次上班；
- 未使用菲亚梅塔，导致贸易角色较齐全时仍有非核心角色上岗；
- 使用菲亚梅塔后，菲亚梅塔没有进入宿舍休息；
- 已有成型巫恋组时，菲亚后重排仍选择了低收益的但书队友组合。

本次讨论只使用 annotations 建立问题背景，没有使用反馈内的求解结果或 operbox
裁决语义。当前代码调查确认：常规 ABC 路径先尝试但书、可露希尔等单核心
菲亚重排；单核心成功后会跳过巫恋组路径。该流程能生成合法局部房间，但没有
形成两个完整策略之间的日收益比较。

## 2. 用户已确认的业务模型

菲亚梅塔贸易策略实际只比较两类候选：

```text
候选 A：菲亚梅塔一天服务但书 + 可露希尔
候选 B：菲亚梅塔一天服务巫恋 + 龙舌兰
```

候选 B 是一个组合 Shadow Candidate。巫恋、龙舌兰和合法第三人的组合不能拆成
三个独立普通候选；第三人只使用项目已经登记的裁缝 β、裁缝 α或白板档位，且
对应贸易单位产出、赤金单位产出和适用练度均已有定值。因此候选 B 的局部贸易
收益不需要重新展开通用组合搜索。

候选 A 不是两个固定效率数字。但书和可露希尔各自的合法房间、队友和跨设施
影响仍由现有正式求解路径决定。两个候选都只是提交前的能力视图；最终
assignment、rotation、resolve 和 export 只能消费胜出分支物理化后的真实干员。

## 3. Shadow Candidate 的统一语义

本案沿用《能力影子候选设计》的核心语义：候选阶段允许同一真实资源以不同能力
视图参与比较，只有冲突和收益比较完成后才提交 physical claims。

该语义同时覆盖两个典型问题：

```text
夜烟#trade                 vs 夜烟#manufacture_gold
巫恋龙舌兰#fiammetta_trade vs 但书可露希尔#fiammetta_trade
```

两者的候选生成成本不同：夜烟需要正式贸易和制造 solver 生成替代行；巫恋龙舌兰
可以从已登记的少量固定档位生成。但两者都要求延迟真实占用、保留 physical claim
冲突，并在 winner 提交前消除所有 shadow 身份。

## 4. 插入时机的两侧约束

### 4.1 不能插入太晚

但书、可露希尔的队友会影响其他设施和体系。典型反例是迷迭香体系中的黑键：
黑键既影响贸易房候选，也与迷迭香及全局感知状态关联。如果先提交但书、可露希尔
房间和队友，再在菲亚后处理阶段插入巫恋龙舌兰候选，后者看到的是已经被前序
physical `used` 和全局状态裁剪过的候选空间，无法计算真实机会成本。

因此巫恋龙舌兰 Shadow Candidate 必须早于相关贸易队友和真实 `used` 的最终提交，
并让会被其替换影响的候选进入同一比较边界。rotation 不能重新做该 admission。

### 4.2 不能插入太早

Plan 和具名体系必须先确认 hard admission、required anchor、reservation 和必要
关系。典型反例是深巡需要乌尔比安最终位于基建宿舍：乌尔比安是深巡机制读取的
基建内角色，不应在普通候选尚未识别该 reservation 时被早期贸易策略静默占用或
淘汰。

因此 Shadow Candidate 不能在 Plan/hard system 之前生成，也不能把 reservation
直接等同于最终 `used`。候选协调器需要读取已经确认的 hard facts，同时保留尚未
物理化的可选资源。

当前候选窗口暂定为：

```text
Plan / hard admission / reservation
  -> 生成相关设施和组合候选
  -> 构建 Shadow Candidate 冲突边界
  -> 分支物理化并完成必要后续编排
  -> resolve、可行性与收益评估
  -> 原子提交 winner
  -> rotation / export 只消费真实结果
```

这里描述责任顺序，不裁决具体函数、模块或数据结构。

## 5. 当前无法回答“谁更赚”的原因

“但书 + 可露希尔和几个固定数字比较”只足以计算巫恋组的局部贸易收益，尚不足以
证明完整策略收益。至少还存在以下传播：

1. 候选 A 的正式队友选择可能占用黑键或其他跨设施成员，并改变感知等全局状态；
2. 候选 B 的第三人虽然效率固定，但该真实干员离开其他设施仍有机会成本；
3. hard reservation、宿舍成员和 `OperatorInBase` 读取会改变分支合法性或结算；
4. 菲亚动作时机、目标持续在岗、菲亚自身恢复和宿舍回岗会决定分支是否可执行；
5. 当前流水线没有一个成熟入口能从相同 hard facts 出发，分别完成两条受限分支并
   使用同一 objective 比较完整日结果。

Shadow Candidate 解决的是“候选不要被顺序提前删除”，不是收益函数本身。若只在
目标贸易房比较固定效率，本案最多得到局部 policy 结果，不能声称哪种完整日排班
更优。

## 6. 已确认与未决事项

## 6A. 问题分层

本轮四条反馈不应作为一个同等规模的重构处理。除“两个贸易策略谁更赚”之外，
其余问题已有明确 owner 和修复方向：

1. **但书动作后未在后续班次上岗**：由 schedule 的菲亚动作验证和最终状态构造
   修复。动作的 `target`、`room_id`、动作所在班次及后续持续工作状态必须一致；
   不需要引入新的候选搜索。
2. **菲亚使用后未进入宿舍**：由 schedule 统一生成回宿舍事实，由 MAA 忠实投影；
   增加容量、顺序和动作关联验证。这是状态模型/输出契约修复，不是收益策略搜索。
3. **贸易角色齐全却未使用菲亚**：由已确认的目标候选和动作槽位检查修复，确保
   合法目标存在时动作不会被普通角色选择路径吞掉；不改变两个收益候选的定义。
4. **已有巫恋组时仍选择但书组合**：这是本案唯一需要 Shadow Candidate 和完整
   日收益比较的核心问题，不能用固定优先级或局部重排补丁解决。

因此实施顺序应为：先修复前三项并用最终状态断言证明，再单独实现第四项的受限
双候选收益评估。前三项的修复不能改变候选生成顺序、贸易策略或其他布局语义。

### 已确认

- 菲亚贸易比较只包含上述 A、B 两类业务策略，不扩张为所有菲亚目标的笛卡尔积；
- 巫恋龙舌兰候选是原子组合 Shadow Candidate，第三人使用已有固定效率档；
- Shadow Candidate 必须晚于 hard admission，早于会丢失相关候选的 physical commit；
- winner 提交前必须物理化真实干员并统一 resolve；rotation 和 export 不理解 shadow；
- 菲亚使用后回宿舍升级为需要由 schedule 表达、由 MAA 忠实投影的可验证输出契约。
- 前三类状态一致性/动作准入问题与第四类收益策略问题分开实施；前三类不需要
  Shadow Candidate。

### 尚未裁决

- 两条分支需要重算到何种边界，才能覆盖黑键、迷迭香、宿舍 reservation 和其他
  实际受影响状态，同时避免退化为全基建笛卡尔积；
- 如何表示 reservation 与 provisional physical claims，使乌尔比安类资源既不被
  提前抢占，也不被错误视为已经最终落位；
- 完整日收益使用哪一个具名 objective，以及 LMD、赤金、经验和其他产物之间如何
  比较；
- 结果保证等级是限定候选宇宙内的 `POLICY_OPTIMAL`，还是首期仅为 `BEST_FOUND`；
- 现有前缀 shadow 分支能否扩展，还是需要更高层的有界分支评估入口。

## 7. 下一轮调查目标

下一轮不应直接实现菲亚 winner 选择。先冻结一个最小可审计评估合同：

1. 明确 A、B 两类候选各自携带的 physical claims、状态读写和 reservation；
2. 从同一份 Plan/hard facts 构造两个隔离分支；
3. 列出每条分支必须重跑的最小阶段及可以安全复用的稳定输入；
4. 定义具名日收益 objective、不可行原因和结果保证等级；
5. 用黑键/迷迭香与深巡/乌尔比安分别证明“不能太晚”和“不能太早”的边界。

在该合同完成前，不把现有固定目标优先级替换为未经证明的局部数字比较，也不在
schedule 或 MAA 层添加按 operbox、房号或班次下标的补偿特判。
