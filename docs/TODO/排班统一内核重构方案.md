## 2026-10-21 当前实现单元范围

用户已裁决普通二班/三班接受输入的有序时长序列，周期由前端限制为 24/36/48h 并负责排除不合法组合；8/8/4/4 菲亚和深海 7/5/7/5 等四班特殊路径本轮不泛型化。泡泡/火神源石组合在本范围内所有普通二/三班排班全局强制，按用户既有决定属于 α 队并跟随最长时段。完整 decision、MAA、warning 与验收边界见 [ADR 0011](../ADR/0011-generic-two-three-shift-rotation.md)。

本实现单元可以偿还直接阻碍该行为的时长分派、重复收尾、状态检查和 MAA 派生债务；不得把“统一内核”解释成必须在本单元迁移四班专用逻辑、改变既有菲亚/24h策略或清理全部历史 TODO。§7 是整个长期 active-change 的累计关闭条件，不得因为 ADR 0011 完成而宣称整个 active-change 已关闭；反之也不得以 §7 尚未全部完成阻塞本单元的独立二/三班工作。

### ADR 0011 裁决吸收（2026-10-21）

- 普通泛型二/三班周期由前端限制为 24h、36h 或 48h；本轮不新增后端时长业务校验。泛型班次超过 12h 时该班最多生成一次菲亚动作，仍走 ready、去重和最终 assignment 核对。
- ABC 并列最长时休班相位放在较短班，尽量覆盖全部可覆盖的并列最长班；完全等长保留旧相位。
- 24/24 named 与泛型长班统一按实际 ETA/心情准入；删除 24/24 姓名黑名单。泛型超过 24h 使用实际输入班长，不继承 named 24/24 的姓名策略。
- 该裁决已进入 `docs/定时换班.md`、`docs/排班模式.md`、`docs/菲亚梅塔使用规则.md`、`docs/接口/输入输出与兼容.md` 与 ADR 0011；四班专用路径仍不变。验证和审阅完成前，ADR 的实现状态不得被当作全仓 active-change 已关闭。

## 1. 目标与硬边界

### 1.1 目标

把以下共同责任收敛到一个周期执行模型：

- 从 `Box + Layout + profile policy` 得到完整周期的最终 `BaseAssignment` 序列；
- 按实际班次时长、续班关系和边界事件结算效率与心情；
- 统一处理办公室、会客室、回收站等辅助岗位的 admission；
- 统一处理菲亚梅塔 ready、目标去重、动作落位和动作后结算；
- 把 24/24 的长班 ETA、控制室长班窗口和制造心情落差作为候选策略接入主路径；
- 最终只保留一个权威报告生成、周期结算和 final-state 验证 owner；
- 让项目文档按入口、状态、责任、合同、证据和未决项可检索地组织，适合 RAG 分片读取。

### 1.2 行为等价定义

无人值守阶段只允许以下类型的改动：

1. 文件拆分、类型移动、模块可见性调整和纯函数提取；
2. 合并同一责任的重复实现，且 old/new 对相同输入的可观察结果相同；
3. 把已经存在的候选准入、事件和终态检查移动到共同 owner，不能扩大或缩小其适用集合；
4. 在不改变既有字段、顺序、错误前缀和 warning 文案的前提下改调用链；回收站 MAA `rooms.recycle` 是本轮明确纳入的新增投影，名单字段按已核对的当前上游协议使用普通 `operators`，不再沿用旧 A/B 草案；
5. 保持行为等价的策略可以继续作为显式拓扑/policy；但用户已于 2026-10-21 授权普通二/三班接受外部时长序列，不能再把“固定 profile、禁止任意时长”作为本轮硬边界。四班特例仍留在原路径。

以下情况暂停依赖该裁决的实现单元并向用户提问，不自行选择；其余不依赖该问题的工作继续：

- 候选集合、排序、tie-break、top-K、剪枝或无解状态变化；
- 心情恢复近似、菲亚目标顺序、动作槽位、跨状态复用规则变化；
- 回收站的轮换拓扑、挂件来源或网站过滤变化；
- 未经确认的 warning/error 等级、错误传播、既有 `plan.compute` schema、Worker 版本变化；本轮已确认的回收站 MAA 字段不属于此项；
- 深海拓扑、方案 C、全局最优保证或新的自动换班行为变化。外部任意时长仅对普通二/三班开放，四班特殊路径仍不开放。

用户已明确授权的行为校正不再触发等待裁决：所有 profile 的菲亚动作必须 ready；普通工作设施空位尽量 fallback 填充；宿舍不由本层分配；训练室/加工站不纳入普通 fallback。相关输出差异要记录为已授权行为变化，不能伪装成等价迁移。

2026-10-19 用户再次纠正拒绝输出边界：质量问题不能升级为求解错误。已有完整或部分排班须保留并诊断；缺人、专用组合不成立时应尽力生成原 profile 班数/时长的普通排班，明确缺失的专用能力，不静默换 profile。菲亚不 ready 时不写动作，但不因此丢弃整份排班。此前“既有失败”仅是差分分类，不能作为保留拒绝输出的豁免；需要同时验证正常产品输出与显式 invariant gate，两者不可混报。

## 3. 目标责任分层

目标不是把所有机制塞进一个配置 DSL，而是让每层只有一个责任。

### 3.1 类型层

建议从 `team_rotation.rs` 提取 `rotation_types.rs`，先移动不含业务选择的共享类型：

- `TimedRotationProfile`；
- `ShiftTransition`；
- `TeamLabel`、`TeamAssignment`；
- `FiammettaShiftAction`；
- `DormRestPlan`、`DroneAction`；
- `TeamShiftResult`、`DailyTotals`、`DailyProduction`、`TeamRotationReport`；
- `FacilityHalf` 以及后续的时间窗/状态引用类型。

`cycle_mood.rs`、`dorm_finalizer.rs`、`shift_bind.rs` 只依赖类型模块，不再通过
`super::team_rotation` 反向拿类型。`schedule/mod.rs` 维持现有公共 re-export，避免改变外部 Rust API。

### 3.2 时间轴与周期执行层

新增内部 `RotationTimeline`/`CycleExecutor`（名称可调整）承载：

- 状态顺序和实际 `duration_hours`；
- `continuation_of`、累计窗口起止点和局部 transition；
- 当前 assignment、已占用集合、bind 闭包、心情/ETA 快照；
- 每段 admission、动作、评分、状态推进的固定顺序；
- 周期尾到首的环形检查。

执行器不选择 ABC 半区、主备 owner、龙巫核心或深海四人组合；这些属于策略提供者。执行器也不让 MAA 重新选择岗位。

### 3.3 Candidate strategy 层

profile 只提供候选策略、时间轴预设和 hard claims：

- `AbcStrategy`：半区切分、gamma 候选和既有有界 retry；
- `MainBackupStrategy`：完整 owner 求解和主备互斥；
- `LongShiftCandidatePolicy`：24h ETA、控制室工作窗口和制造心情落差准入；
- `WitchGroupStrategy`：菲亚支撑的巫恋/龙舌兰跨状态 claim 与裁缝轮换；
- `SplitShiftStrategy`：8/8/4/4 的局部事件和续班窗口；
- `AbyssalStrategy`：深海 producer/consumer、四人枚举和显式宿舍恢复；
- 普通房间 admission：所有设施（包括回收站）共用候选排除、容量、ETA、Team/Shift 和提交路径；回收站只提供自己的容量、技能和效率参数。

策略可以做候选 oracle 和局部比较，但不能自己生成第二份完整报告、第二套心情推进或第二个 finalizer。

菲亚事件不是一个整体不可分的“回岗算法”。当前行为至少有三层，迁移要分别证明：候选/动作策略（选谁、在哪班交换、是否 ready）、交换后 assignment 是否改变（是否要跨班重填目标房）、以及每个实际时间窗的效率/周期加权结算。名字相近的 ABC 巫恋组 fallback 不等于独立 `fiammetta_witch_12_12` 龙巫 profile；不得因两者都使用巫恋和龙舌兰就把动作策略合并。

### 3.4 Admission 层

2026-10-19 用户补充：所有工作场所的空位都要使用 fallback 补充，宿舍入住由后续模块或网站安排。这里的职责是从合法候选中尽量填满实际工作岗位，不是只输出带技能者，也不是让 MAA 临时自动选人代替求解器补位。fallback 属于同一 admission，仍消费当前裁剪后的候选与占用、心情、绑定、容量约束；不能在 finalizer 重新读取原始 roster 绕过前置限制。该裁决授权将尚未补满的工作房接入公共 fallback；它不是对当前所有房间已经满编的事实声明，也不授权为填满而拆绑定或重复使用干员。具体候选耗尽后的旧 warning/error 策略先保留，若需要改等级则另问用户。

宿舍不属于工作空位补齐目标。现有特殊恢复组、菲亚住所和普通宿舍 finalizer 先保留，本次不因满编裁决删除宿舍模块或关闭周期心情检查；后续宿舍模块仍可以消费最终在岗/离岗事实。

**与当前实现的差距（调查事实）**：办公室和会客室虽有各自的逐班补位，但当前合格候选用尽/被 ETA、Team 或 reserved 条件排除时会停止，最终房间仍可低于容量；回收站只在周期 finalizer 用单独的 roster fallback，并自行回放心情，不是普通 room admission；训练室与加工站只有 Plan anchor/shared 等显式占位路径，没有“技能选人后通用普通人补位”owner。中枢、贸易、制造、发电已有各自设施池与 filler/剩余池，仍须核实它们的 fallback 候选是不是用户所说的通用普通候选，不能因为它们“报满员错误”就说所有空位已有公共 fallback。上述差异要按同一个行为要求接入，而不是逐房间加不相关补丁。

统一补位的可观察逻辑应是：每个已由 Plan/核心策略确定的工作房仍优先保留其专属技能、required 与已绑定成员；对剩余空座位从当前周期/班次允许的剩余人员中试放普通候选；试放必须遵循同一占用唯一性、容量、班次归属和心情/ETA 资格，再提交到最终 assignment。若候选池耗尽，才留下真实空位；不能因补位方便重新读取全 Box 或从宿舍恢复组抢人。用户已明确**不**把没有显式训练任务的训练室、没有加工任务的加工站列入普通 fallback；它们只消费 Plan 明确安排的成员，其余岗位保持空置。

统一 admission 顺序应由周期执行器掌握，策略只提供约束：

```text
Plan / required / bind
  -> production and control claims
  -> office / meeting claims
  -> recycle admission
  -> profile-specific named claims
  -> capacity and final assignment commit
```

回收站按普通房间进入通用 admission，不建立独立的 `RecycleAdmissionStrategy`。当前 dirty 的构造阶段补位和 finalizer fallback 是同一房间逻辑的重复 owner，必须合并到公共房间补位路径，删除 finalizer 的二次扩池/补人。当前六个产品 profile 都消费同一普通房间逻辑；技能候选、普通候选、容量、ETA、Team/Shift 和心情由公共路径处理。回收站的专属代码只保留设施容量、运行时技能映射、效率公式和 MAA 字段映射。

### 3.5 Fiammetta event 层

菲亚梅塔不再作为多个 profile 的完整调度器，而是统一事件执行器消费的策略输入：

- action slots；
- legal target predicate；
- ready 计算；
- target uniqueness；
- target continuation claim；
- 局部房间 transition；
- 事件前后评分窗口。

ABC N/A/B、普通单核心、龙巫和 8/8/4/4 可以保留不同策略，但 ready、目标去重、动作写入、动作后重算和最终校验只能有一个公共 owner。

### 3.6 Finalization 和 invariant 层

只保留一个报告 finalizer：

- 从最终 assignment 一次性重算效率和周期权重；
- 生成宿舍、warnings 和 daily；
- 调用公共 cycle mood、bind、capacity、菲亚和回收站验证；
- 调用具名 profile predicate；
- 维护既有错误前缀和 warning 降级策略。

具名 predicate 可以存在，但不得再产生独立报告或重新决定岗位。

## 4. 推荐切分顺序

### 阶段 A：只移动类型和纯公共 helper

允许行为等价的范围：

- `rotation_types.rs`；
- `FacilityHalf::contains`；
- `swap_in_pool` 等 bind 内部纯 helper；
- MAA slot 构造器的纯结构复用；
- 排序去重与保序去重分别命名，不能错误合并。

先运行编译、格式和受影响单测；不改变排班算法。

### 阶段 A 当前进度

公共轮换类型已先移入 `schedule/rotation_types.rs`，并通过 release 编译、文档索引和 dirty baseline 的定向测试差分。结算快照类型 `RoomEfficiencyLine`/`ShiftEfficiencies` 与绑定类型 `RuntimeShiftBind` 已一并下沉，类型模块不再反向依赖算法模块；本阶段没有实施 helper 抽取，也没有改变排班行为。证据见 `target/codex-runs/rotation-unification-20261018/phase-a-report.md`。

### 阶段 A 后续：菲亚动作后完整班次重算

**逻辑变化范围**：只把菲亚相关路径中重复的“assignment 已改变后，重新计算普通完整班次”的步骤收在一起。每个班次仍按该班实际时长读取整房布局并结算贸易、制造、发电；再将该班贡献按“班次时长 ÷ 完整周期时长”折算，分别累加三类每日平均效率。例：24 小时周期中的 12 小时班效率为 2、另 12 小时效率为 1，周期结果是 `2×12/24 + 1×12/24 = 1.5`。贸易、制造、发电各自统计，不把三种量纲相加。此分数用于报告各班与完整周期的收益，不负责选择菲亚目标或比较 N/A/B。

以下策略说明记录普通重评分单元完成时、ready 校正前的基线，不代表后续单元完成后的当前实现；当前事实见 §6.3 和模块页。

**菲亚普通目标补入（ready 校正前）**：先依 profile 可用动作位的顺序尝试合法目标。目标必须能定位到生产房，并且可以在该目标缺席的班次重新补入；目标房原有多成员绑定若不能安全替换，整个目标尝试放弃。当时该路径没有执行与 ABC N/A/B 相同的 ready 试算，只依据槽位、目标可补入和跨班连续性等条件接受动作。接受后写入该动作位，并更新改变过的班次及整周期产出。该路径不等同于只改一个 `fiammetta` 字段：它可能重填目标房，因此需要对所有班次重新评分。

**ABC 巫恋组后备路径**：只有 ABC 的普通目标路径没有接受动作时，才尝试已具备巫恋+龙舌兰的三级金单房。先比较合法 β 裁缝在目标房的候选得分，至少有两名可用才继续；随后按 ABC 班次把裁缝写进各班，并将巫恋、龙舌兰分别放在前两个动作位。两个目标各自必须在对应时点满足当前 ready 试算，且通过终态约束后才接受。这里的“巫恋组后备路径”是 ABC profile 内的策略，不是独立的龙巫 12/12 profile。

**独立龙巫 12/12 profile**：它单独构造主、替两个完整 owner；在两个 owner 中复用巫恋和龙舌兰，但要求两名不同的 β 裁缝各自进入一个 owner，主班动作目标固定巫恋，替班固定龙舌兰。该路径没有使用上段 ABC 巫恋组后备策略，也没有显式调用同一段 ready 试算；当前终验检查动作位、唯一性、目标合法和目标仍在工作房，但不检查 ready 试算结果。这是当前实现与 canonical 菲亚 ready 口径之间需要单独复核的行为差异，本阶段没有替用户裁决或改写。

**其他 profile 的加权现状**：ABC N/A/B、主备 12/12、主备 24/24、独立龙巫、8/8/4/4、深海 7/5/7/5 最终都由公共轮换 finalizer 重算最终 assignment，再以实际班时/完整周期小时得到三类独立加权值。profile 内部还会有初步评分，菲亚动作路径也会在公共 finalizer 前做一次动作后重算。此次提取只统一菲亚策略里的普通完整班次重算步骤，并未建立跨 profile 的唯一 scoring/finalization owner；因此不应汇报成“菲亚普通回岗与龙巫动作已合并”或“所有排班方式已有唯一结算实现”。
