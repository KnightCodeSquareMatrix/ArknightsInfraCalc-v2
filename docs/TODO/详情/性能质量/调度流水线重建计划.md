# 调度流水线重建会议纪要

> 文档角色：active-change
> 生命周期状态：ready-on-request
> 当前真源：docs/架构/ORCHESTRATION_LAYER.md
> 摘要：记录调度主线重建的已裁决方向、迁移原则和后续实施边界
> 所属工作流：docs/TODO/性能质量.md

## 1. 会议结论

项目不需要为了“代码膨胀”做机械拆文件，也不需要把全部按名称的特判消灭。
效率和领域机制的基本骨架仍可靠；当前长期维护风险集中在历史调度路径、阶段
状态推进、重复 owner，以及无法可靠发现用户可见编排错误的测试形态。

下一轮独立质量工作是在单独 branch 上重建一条从用户请求到完整排班结果的
确定性调度流水线。旧 `team_rotation`、单班 `pipeline` 和相关机制代码不进入
新架构作为依赖，只在迁移期提供行为对照；稳定后删除旧路径。

## 2. 健康检查结论

### 当前健康状态

当前判断为黄灯，不是失控状态。

- 核心效率结算和机制解释整体可靠，风险没有随机散落到全仓。
- `Plan -> execute -> fill -> resolve` 仍提供了可定位的主骨架；多数问题能被
  归因到具体阶段，而不是只能从最终效率猜测。
- Ledger、原子效果、稳定 ID、部分 fail-closed 约束已经阻止了大量机制规则
  在各层无序复制。
- 代码规模主要集中在少数历史大文件；`team_rotation.rs` 还混合了大量测试，
  文件行数不等同于生产逻辑规模。

### 本次确认的结构风险

1. `team_rotation` 与 `pipeline` 都能推进 assignment、resolve、dependency 或
   跨班状态。单班与跨班不是一条连续状态流，而是多个历史调用方式的组合。
2. 已发现或需在迁移中消除的顺序缺口：Recovery shadow winner 提交后可能继续
   使用旧 layout；公共 assignment facade 返回未解析 dependency，调用者需要
   自己补跑；gamma half 未完整消费 Plan constraints。
3. `resolve.rs` 的“遗留 apply_*”说法需要修正：文件中没有残留 `fn apply_*`
   定义。真正需要重判 owner 的是全局资源扣回、Selector 求值与跨设施解释器
   的重复面，以及已失准 baseline fallback。
4. 中枢 buff 分类分散在多个位置维护，是明确的单一 owner 重建候选。

### 不应误判为债务的内容

- 琴柳条件效果目前需要特判。换成技能 ID 不会减少特判本身；重点是避免同一
  条件在多个阶段各自重新裁决。
- 令/夕名字判断关联迷迭香感知语义。现有 tag 不是该规则的完整语义替代，按名
  表达可以更清楚。
- 菲亚梅塔的高价值目标名单是有意的固定周期策略。完整动态评估会引入换班后
  队友效率和跨班依赖问题；名单不是临时补偿。

结论：合法具名特判可以保留。需要消除的是没有单一语义 owner、跨阶段重复
裁决或以旧状态继续推进的特判路径。

## 3. 为什么不以现有测试为重构中心

现有测试并非完全无价值：局部机制、ledger、shortcut、部分差分搜索和终态验证
已有作用。但它们不能作为项目整体正确性的主要证据。

- 用户实际看到的问题多为候选、编排顺序、跨房依赖、跨班状态和最终导出的
  组合错误，不是单个公式函数的返回值错误。
- 固定 fixture、CSV anchor、快照或实现细节测试即使全绿，也可能没有覆盖新
  roster、布局、依赖组合和策略顺序。
- 人工审阅与既有批量验收页面才是当前发现完整排班差异的有效工具。

迁移时不保留大量服务于旧函数结构的 `team_rotation` / `pipeline` 测试。只保留
不可接受终态的约束测试：人员去重、容量、required placement、Team/Shift bind、
依赖闭合、休息和心情边界、profile 特有终态，以及导出与同一次求解结果同源。

批量验收页面和人工审阅负责判断完整结果、策略合理性与用户可见差异；自动化
测试不得伪装成全局排班质量证明。

## 4. 已裁决的目标模型

### 4.1 范围

新主线从用户请求开始，到完整可审计结果结束：

```text
用户请求
  -> 标准化请求与数据快照
  -> 编译调度目标、硬约束和具名策略
  -> 对每个 Shift：求解房间并提交当前 assignment
  -> resolve 当前完整 layout
  -> 校验人员、容量、绑定、心情和 profile 终态
  -> 推进休息、心情、依赖与下一 Shift 可用性
  -> 汇总整轮结果与阶段 trace
  -> CLI / Worker / MAA / JSON 投影
```

一次执行只产生一份完整结果，至少包含全轮 assignment、效率、心情/休息、依赖、
MAA/export 投影和阶段 trace。任何导出仅投影该结果，不再次求解。

### 4.2 代码组织原则

代码按实际求解流程、房间和具名特殊机制组织，而不是继承
`team_rotation.rs` 与 `pipeline.rs` 的历史边界。

“特殊机制由谁执行”不是需要人为切开的权限问题。房间求解、菲亚梅塔、深海、
岁等都属于同一条流水线的工作；关键约束是它们读写同一份当前排班状态，并且
提交后任何后续步骤都读取更新状态。不能再出现某个机制已经改人、后续发电或
跨房结算却读取改人前 layout 的情况。

新核心仍保留在一个求解器 crate 中。不存在值得独立发布的“效率库”：效率计算
高度依赖完整布局、人员互斥、跨房依赖和排班状态，除了求解器本身没有独立消费
效率计算的现实需求。

### 4.3 求解口径

继续使用阶段式、按房间的具名 policy。新主线不把全基建和全班次改成单一全局
优化器，也不宣称全局最优。每个策略限制、候选取舍与阶段结果必须可追溯。

## 5. 迁移裁决

### 保持不变

- 当前领域效率语义、机制公式和已裁决特殊策略的含义。
- `plan`、`plan.compute`、Worker/serve、CLI 的请求与返回契约。
- 当前阶段式求解的保证等级。
- 既有批量验收页面及其完整结果对照职责。

`plan`、`plan.compute` 和 Worker 现阶段不做协议清理。它们在迁移期只是输入/输出
适配器，内部切换到新核心后再单独裁决 legacy 接口删除。

### 同步重写

新主线、房间求解和机制计算同步重写。旧实现只作为行为 oracle，不允许以“先
复用旧房间 solver”为名把旧责任边界带入新主线，也不进行逐行翻译式搬迁。

这是有意接受的迁移风险：差异可能来自调度、房间求解或机制迁移任一侧。对应
的控制手段不是局部兼容层，而是批量验收页面对完整确定性输出的严格对照。

### 对照标准

迁移范围内要求完整输出完全一致，包括 JSON、MAA、数值和稳定排序。项目已有
按名称排序的确定性基础，因此不接受“人员集合相同即可”、容差、更新快照、
未知 fixture fallback 或类似方式吞掉差异。每一处差异都必须先解释并修正。

不为本任务额外建立单一 operbox golden 或第二套本地 oracle；批量验收页面已是
专用的完整验收入口，迁移不应重复建设其职责。

## 6. 实施顺序

1. 创建独立 branch，冻结当前外部接口和批量验收入口。
2. 建立标准化请求、数据快照、完整 result/trace 和导出投影的同源骨架。
3. 以新的 Shift 状态流同步重写 Plan、房间求解、提交、resolve、终态验证与
   跨班状态推进；逐段接入中枢、贸易、制造、电站、办公室、会客室和宿舍。
4. 接入菲亚梅塔、深海、岁和其他具名特殊机制，删除其绕过主状态流的旧路径。
5. 每迁移一段就通过批量验收页面比较完整输出；完成差异归因与修正后才进入
   下一段。
6. 全量一致后删除旧 `team_rotation`、`pipeline`、无消费者 baseline/probe 和
   重复 owner，更新 current architecture 文档并归档本任务。

## 7. 暂不裁决

- 新流水线最终的文件名、类型名和目录细节。它们应从实际状态流和迁移代码中
  推导，不在会议纪要中预设。
- 外部接口何时合并或删除 legacy `plan` 路径。当前先保持契约不变。
- 是否以及何时把中枢 buff 分类改为数据化 inventory。方向已确认，但具体数据
  表和 fail-closed 边界应在对应实现单元单独裁决。
- 完整跨周期心情最优化、Mower 动态换班和其他未恢复历史 TODO，不随本任务
  自动恢复。

## 8. 完成标准

1. 新主线覆盖当前支持的布局、profile 和具名特殊机制。
2. 批量验收页面对迁移范围内的完整输出完全一致。
3. 每份结果可追溯到输入快照、Shift 阶段、房间提交、resolve 结果与策略限制。
4. 旧编排路径、失准 fallback、无消费者 probe 和重复 owner 已删除，而非仅被
   新路径绕过。
5. 当前架构真源吸收新事实；本任务移出 `docs/TODO/` 并按生命周期归档。
