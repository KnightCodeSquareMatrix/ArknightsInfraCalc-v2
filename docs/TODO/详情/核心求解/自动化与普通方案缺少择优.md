# 自动化与普通方案缺少择优

> 文档角色：active-change
> 生命周期状态：ready-on-request
> 当前真源：docs/架构/ORCHESTRATION_LAYER.md；docs/排班/排班模式.md
> 摘要：记录自动化体系只按准入条件和优先级启用、不与普通方案比较效率，少数盒子因此选到更差方案的已知偏差
> 所属工作流：docs/TODO/核心求解.md

## 1. 当前事实

`automation_group` 是编排规则，是否启用只看门槛条件和优先级，不比较启用后与不启用的总效率。整班择优分支（`compare_automation`）已由用户裁决删除：它使制造搜索慢 3 到 8 倍，属于设计问题；择优留到 DFS 阶段。

因此当前存在一个已知偏差：自动化可启用时总会启用，即使不启用更好。

## 2. 实测范围

测量时间 2026-10-11，提交 `b5e6810`。方法：对同一份 operbox，把 `automation_group` 各备选的门槛改成不可满足（通过 `ARKNIGHTS_INFRA_DATA_DIR` 指向改过的数据副本，仓库文件未改），其余不变，比较 `rotation` 的日均效率。

- 范围：`--rotation 3`（`abc_12_6_6`），representative 28 盒 + high-owned 10 盒，其中 14 盒启用了自动化。
- 11 盒启用后制造效率更高，高出约 0.15 到 0.32。
- 3 盒启用后反而更低：`high-owned/b-073-415` 低 0.072，`high-owned/b-174-382` 低 0.068，`representative/c-267-353-box` 低 0.090。
- 贸易和发电效率在两种情况下相同，差别只在制造。

未覆盖：其他轮换 profile；同时关闭多个体系的组合；量化“少选几个干员”的情形。

## 3. 边界

- 这是已接受的缺口，不是回归：偏差来自择优被删除的裁决，不是后来的改动。
- 不得靠给 `automation_group` 加效率阈值之类的补丁规避；择优应按整班结算比较，在 DFS 阶段统一做。
- 清零房（自动化类技能把房间效率清零的制造站）的搜索本身不是性能瓶颈：同一盒保留 5 名相关干员耗时 17.6 秒，去掉后 23 秒。放开 v3 式“允许缺员”会放大枚举，需先测候选数再决定。

## 4. 验收

择优实现后，上述 3 盒的制造效率应不低于关闭自动化的结果，且 11 个受益盒保持不变；同时记录搜索耗时变化。
