# 中枢可用阶段重构方案

> 文档角色：active-change
> 生命周期状态：ready-on-request
> 当前真源：docs/机制/CONTROL_CENTER_ASSIGNMENT.md
> 摘要：先收敛为可解释、不一眼错误的中枢编制；不在本阶段承诺全局最优或跨设施交换搜索。
> 所属工作流：docs/TODO/核心求解.md

## 1. 目标与非目标

本阶段的用户场景是：在既有账号、蓝图和已启用体系下，求解器输出一个满 5 人的中枢；已被文档确认的体系成员不被普通补位替换，其余席位遵守既定的效果区和心情补位顺序，且同一班不出现已明确互斥的效果 owner。

可观察输出为最终 assignment、control trace、每班中枢成员和 `--assert-invariants` 结果。成员来源的结构化解释字段尚未在本阶段新增，不能把现有输出描述为已经完整解释了选位原因。

本阶段不是：

- 全账号的中枢、贸易、制造联合最优；
- 任意中枢成员和生产房成员的回溯交换；
- 全量中枢组合 Bake、上下文无关组合缓存或新的通用 DP/Pareto 引擎；
- 新增未在 canonical 支持的体系、概率/倾向机制或心情公式；
- 改变动态 producer 的既有联合 resolve owner、跨班 bind 政策或生产设施的有序填房 policy restriction。

这是一个 `conformance-rebuild` 的准备阶段，而不是以 `ControlInjectRawSumV0` 声称全局最优的优化工作。

## 2. 当前阶段的规则模型

中枢决策分为两个层次。

### 2.1 体系提交

红松林、人间烟火、感知及其他 canonical/Plan 已解析的体系，目标是不要作为普通中枢候选重新比较。当前代码通过 `build_plan -> execute_plan`、兼容 registry claims 和 producer fill 的多条路径承载这些事实；本阶段只冻结这一目标边界，不宣称所有 legacy 路径已经完成统一收敛。普通 fill 原则上只可使用体系提交后的剩余席位。

具体地：

- required anchor 是 hard constraint；
- `min_count` 是候选组 hard constraint，不提前固化成没有依据的单个干员；
- `PickOne` / `OptionalFixed` 的解析归 Plan；execute、fill 和 rotation 不得从 owned roster 二次选择未解析事实；
- 已提交成员可自然贡献其他有效 atom；当前实现仍需继续清理 legacy producer/rotation 路径，才能完全保证后续普通选位不得替换或重复解释这些事实。

### 2.2 剩余席位的有界规则选位

在 Plan 已提交成员和当前班可用候选构成的有限集合内，普通中枢只按下列顺序填位：

```text
有效产能/解锁入口
→ 体系外效率散件
→ 心情去重补位
→ 无技能普通角色补满
```

同类效果的值与 `Winner` / `TiedWinner` / `Suppressed` 身份由中枢结算决定；普通选位不得再次根据干员名、`buff_id` 前缀或人工权重重新定义该语义。文档已声明的贸易、制造、训练、办公室、会客室效果区仍按其先后顺序处理；不同区不强行折算为同一分数。

本阶段允许既有有限组合枚举作为实现手段，但它必须服从上述 hard constraint 与顺序，不以 `ControlInjectRawSumV0`、`mood * 0.01` 等跨区数值作为业务规则。现有实现尚未完全满足这一点，因此只能定义为过渡实现。

## 3. 冻结的输入与输出边界

### 3.1 输入

中枢结算输入保持为：

```text
ControlRoomInput {
  operators,
  mood,
  layout_context
}
```

其中 `layout_context` 是中枢之外已提交设施形成的当前班快照；它提供中枢条件读取所需的全局资源、办公室、发电、训练和已落位 workforce 事实。

中枢选位还消费：

```text
ControlAdmissionInput {
  resolved_plan_facts,
  available_control_candidates,
  used_or_excluded_operators,
  current_shift_availability,
  layout_context
}
```

`resolved_plan_facts` 只能包含已解析 required、候选组最低命中数、排除项和已有绑定事实；它不传递可被 rotation 重新解释的原始体系候选。

### 3.2 输出

每个最终中枢状态必须产生一次冻结结算：

```text
ControlSettlement {
  selected_members,
  effect_ledger,
  global_resource_projection,
  global_inject_projection,
  mood_projection,
  resolved_producer_facts,
  trace_or_diagnostic
}
```

`ControlEffectLedger` 是同类效果 winner/suppression 的唯一 owner；`GlobalInjectManifest`、办公室/会客室投影、trace 和 dependency 只能消费已冻结事实。本阶段现有 ledger 仍未覆盖心情、训练和全部 target context，因此这些领域在完成统一账本前由其现有 owner 维持，并以最终状态 invariant 防止已确认的冲突。

## 4. 单一责任边界

| 层 | 唯一职责 | 不得负责 |
|---|---|---|
| Plan | 体系选择、required admission、已解析 choice 与绑定声明 | 用中枢收益分数选择普通 filler |
| Control settlement | 给定成员的 atom 条件、聚合、winner/suppression 和投影 | 选择谁入驻 |
| Control admission/fill | 消费 Plan 事实与冻结结算，在剩余席位执行既定顺序 | 重新解释 atom 公式或改写体系 |
| Rotation | 在每班可用闭包中消费已解析事实，校验容量/绑定/最终状态 | 从账号全池重新选体系或以注入覆盖替换成员 |
| Trade/Manufacture | 在中枢已冻结投影下结算实际房间 | 反向创建普通中枢 admission 或绑定 |

当前首次允许非法状态的位置是 `search/control.rs` 的旧式候选排序和 `schedule/team_rotation.rs` 的补位/coverage 替换：两者会用独立排序或分类再次裁决成员。当前修正仅将“设施全局恢复 owner 不能同班重复”接入 search、fill、rotation 与最终 invariant；它不是上述单一责任边界的最终实现。

## 5. 当前提交的可用性保证

本提交实现和验证的硬约束限于：

1. 设施全局恢复族（玛恩纳、维什戴尔、重岳）在同一中枢状态最多一个 active owner；其他可叠加心情来源不受影响。
2. 已满且 pinned 的中枢、普通组合搜索、体系 producer 追加、rotation coverage 替换、ABC 普通补位和最终 invariant 都检查该约束。
3. 最终 invariant 同时检查 runtime trade skill 引用是否均可解析，防止修正后的排班依赖未解析的运行时技能数据。

这属于 hard constraint，不是 heuristic。它不证明中枢总体最优，也不把同类效果的一般性重复全部降为硬排除。

## 6. 验收与延期

本阶段验收需要：

- Rust 最终 assignment gate 对代表性/high-owned operbox 批量通过；
- 对合法与非法恢复 owner witness 分别证明接受/拒绝；
- 真实 `plan` 或 `layout team-rotation` 产物中每班中枢满员、无重复成员，已解析 bind 保持；
- 对当前 diff 完成独立 Terra 复审。

延期项：

- 完整 `EffectKey`（scope、target、selector scope、unit、aggregation）和所有中枢 inventory；
- 去除 `search/control.rs` 中的姓名、前缀、`ControlInjectRawSumV0` 和人工 bonus 过渡逻辑；
- 普通 `12/12` 中枢与 ABC 生产轮换的最终模型统一；
- 动态 producer exact joint、全设施交换搜索，以及 context-aware control/trade/manufacture 组合 Bake；
- 未处理条件从当前 fail-open 迁移为 explicit `Unsupported`。

这些项只有在本阶段规则行为稳定、有冻结反例和独立授权时才继续，不在本提交中顺带扩张。红松林、人间烟火、感知的所有 legacy registry/rotation 路径统一，以及普通选位的结构化来源解释，属于后续实现单元，不是本阶段已完成事实。

## 7. 后续实施顺序

1. 冻结本阶段 current 行为、代表性输入和非法 witness。
2. 将 Plan 已解析的中枢事实收敛成显式 admission input，删除 rotation 对未解析 choice 的二次选择。
3. 将普通中枢 fill 改写为规则阶段，而非跨区加权排序；保留 live settlement 作为唯一求值器。
4. 扩充 ledger/inventory，并将 mood、training、target context 纳入结构化 owner。
5. 仅在上述语义稳定后，评估候选 signature Bake；缓存键必须覆盖 policy、effect manifest、roster/tier、Plan、layout 与全部条件上下文，不完整时回退 live。
