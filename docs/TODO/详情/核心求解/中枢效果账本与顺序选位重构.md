# 中枢效果账本与顺序选位重构

> 文档角色：active-change
> 生命周期状态：ready-on-request
> 当前真源：docs/机制/CONTROL_CENTER_ASSIGNMENT.md；docs/机制/EFFECT_ATOM_DESIGN.md；docs/排班/SCHEDULE_ROTATION.md
> 摘要：以原子级效果账本和顺序选位统一控制中枢同种效果取最高、技能盘点与轮换事实
> 所属工作流：docs/TODO/核心求解.md

## 1. 授权目标

本任务是独立的中枢 conformance rebuild。它解决多个阶段分别解释“同种效果取最高”、候选层按
`buff_id` 重复奖励、以及 rotation 二次解释 Plan 中枢候选的问题。

本任务不设计贸易、制造、办公室、会客室和训练室之间的综合评分函数。不同域不是可换算的竞争
关系；中枢按用户裁定的顺序选位。

### 当前实施阶段：稳定 atom 身份

本阶段只实现稳定 atom 身份迁移，作为后续中枢账本完善的基础结构：

- `EffectAtom` 增加稳定 `atom_id`；JSON 继续使用现有的 `id` 字段。
- 控制中枢所有非空 atom 必须有非空且同一技能内唯一的 `atom_id`。
- ledger、control trace 和 response-dependency 中的持久/解释性 atom 来源使用
  `source_buff_id + atom_id`。
- `CompiledAtom.seq` 只保留为当前运行时排序信息，不承担持久身份。
- 不根据数组下标、技能名、干员名或 `seq` 自动生成稳定 ID。

本阶段不扩大为完整中枢技能审计：不建立 inventory，不补空 atom，不修复缺失的
`operator_instances` control buff，也不改变 `atoms: []` 的委托语义。

## 2. 已确认不变量

- 中枢目标容量为 5 人；合法可用角色足够时必须填满。
- Plan required anchor、原子体系和 `min_count` 是 hard constraint，不能由效果分数、tag、
  `shift_bind` 或 shortcut 代替。
- L1 interpreter 只认 `buff_id`，不按干员名判断机制。
- 同类效果是否取最高由结构化效果键和显式聚合器决定，不由技能名称、`buff_id` 前缀或数值单位
  推断。
- 被压制的 atom 不获得该效果的候选价值，也不为该效果派生 dependency 或 `shift_bind`；同一
  干员的其他有效 atom 不受影响。
- rotation 不从候选列表或 owned roster 二次选择 Plan 未解析的 `PickOne` / `OptionalFixed`。

## 3. 单一责任边界

首次违规在中枢结算与评分交界：`control/interpreter.rs` 对办公室、会客室直接做标量合并，
`search/control.rs` 再按固定 `buff_id` 重写心情和候选语义，rotation 又重解释中枢候选。

修复后，`ControlEffectLedger` 是中枢效果激活、合并、winner/suppression 和解释的唯一 owner。
`GlobalInjectManifest`、办公室/会客室/训练室投影、trace、候选选位和 dependency 只能消费冻结后的
ledger，不得再次自行做 max、sum 或条件判断。

ledger 的稳定记录单位为：

```text
source_buff_id + stable_atom_id + EffectKey + target_context
```

每条记录至少包含候选值、最终有效值、激活原因和以下状态：

```text
Winner | TiedWinner | Suppressed | Accumulated | NoEffect | Unsupported
```

`EffectKey` 至少表达：

```text
domain + scope + target + selector_scope + result_unit + aggregation
```

条件先决定 atom 是否激活；只有条件改变作用范围或目标时才进入 key。聚合器必须显式表达
`max`、`sum`、`clear`、`count-scaled` 或 `conditional-exclusive`。

## 4. 已裁定效果区

### 4.1 贸易全局区

所有“所有贸易站订单效率”属于同一区，取最高：

```text
trade / all_trade_rooms / order_efficiency / max
```

阿米娅、诗怀雅、明椒、阿斯卡纶、望的贸易分支、火龙 S 黑角的有效怪猎条件，以及若叶睦的
实际有效全贸易结果在该区竞争。动态 producer、当前贸易房、标签、谢拉格/格拉斯哥和订单上限
效果不进入该区。

### 4.2 制造全局区

所有“所有制造站生产力”属于同一区，取最高：

```text
manufacture / all_factory_rooms / productivity / max
```

凯尔希、Mon3tr、布丁、麒麟 R 夜刀、望的制造分支和斩业星熊在条件生效后竞争；斩业星熊
`+3%` 压过任意 `+2%`。配方、标签、当前房间和按人数缩放的制造效果独立结算，不进入该区。

### 4.3 办公室区

八幡海铃「可靠伙伴」的办公室联络速度 `+10%` 属于：

```text
office / global_hire_speed / max
```

琴柳「感染力」是办公室联络速度低于 `30%` 时的唯一条件效果，不与普通办公室 max 混算。

### 4.4 会客室区

会客室线索搜集速度属于：

```text
meeting / global_clue_speed / max
```

老鲤、魔王、祐天寺若麦、摆渡人、怒潮凛冬和维什戴尔先按条件/人数求值，再进入该区取最高。
若麦「勤学苦练」和「成效优先」不叠加；维什戴尔 alpha/beta 不叠加。现有
`meeting_speed_pct += value` 路径必须删除或改为 ledger 投影。

### 4.5 训练室区

在运行时上下文确认训练室有专精进行时，阿斯卡纶 E0、烛煌 E0、斩业星熊 E0 的专精训练速度
`+5%` 属于：

```text
training / mastery_speed / max
```

缺少“正在专精”上下文时，该 atom 是 `Unsupported`，不能成为有效候选收益。

### 4.6 心情补位

实际心情 owner 与候选补位必须区分：

- 中枢满 5 人的 `-0.25/h` 与恢复效果、设施人数减免、角色自身/同房心情效果叠加。
- 玛恩纳 E2 自身是笑脸 provider `+0.05/h`；其固定 `+0.1/h` 只覆盖发电站、办公室、会客室，
  并把中枢笑脸总量扩散到发电站、制造站、贸易站、办公室、会客室。制造/贸易只取笑脸数量乘
  `0.05/h`；发电/办公室/会客室取 `0.1 + 笑脸数量乘0.05/h`。
- 维什戴尔 E2 的 `+0.1/h` 覆盖发电、制造、贸易、办公室、会客室；魔王同在时额外 `+0.1/h`。
- 重岳 E2 的 `+0.05/h` 覆盖发电、制造、贸易、办公室、会客室。
- 玛恩纳、维什戴尔、重岳是同一设施全局恢复族，自动选用最多一个有效 owner；族内取最高，不叠加。
- 彩虹小队和异格者恢复只作用控制中枢，按 `0.05 × provider_count × member_count` 计算；清单由
  `data/mood_model.json` 维护。

普通心情补位的顺序为：维什戴尔存在时优先魔王；玛恩纳存在时优先笑脸 provider；没有全局恢复时
优先派系/人数 provider 或笑脸 provider；最后才用普通合法角色补满 5 人。该顺序是低优先级候选政策，
实际净消耗仍由 mood owner 结算。

## 5. 顺序选位

中枢不使用跨域评分函数，严格按以下顺序填位：

```text
1. Plan 硬锚点和原子体系
2. 贸易全局区有效最高来源
3. 制造全局区有效最高来源
4. 训练室区有效最高来源
5. 办公室区有效最高来源
6. 会客室区有效最高来源
7. 心情去重补位
8. 任意合法普通角色补满 5 人
```

- 每个区只比较自身同类效果的有效值；同值稳定 tie-break。
- 后序区不替换前序已选成员；已满 5 人后不再替换。
- 同一干员首次入选后，可以自然贡献其后续独立 atom。
- 条件技能只在“当前已选成员 + 当前候选”上下文直接结算；条件不满足则该效果无效，尝试同区
  下一候选。
- 后续普通补位不为激活前序条件技能专门选人。
- 不增加 witness package、回溯或条件组合搜索。

动态 producer 继续遵守当前 canonical 的联合 resolve 责任边界；本顺序不改变其已有的
presence/consumer 求值语义，也不宣称多房 exact joint。

## 6. 后续：全量 inventory 与缺失技能

以下是后续完整审计目标，不属于当前 stable atom identity 阶段。保留本节用于约束未来扩展，
当前实现不得为了完成本阶段而引入完整 inventory 或批量补齐技能。

建立版本化、fail-closed 的控制中枢技能 inventory。`MECHANICS_REGISTRY.csv` 的每条控制中枢
技能及有效 tier 必须记录：

```text
CSV row | skill | operator | tier | buff_id | atom_id | EffectKey | status | reason
```

合法状态为：

```text
supported | unsupported | ignored | delegated
```

- 数值、范围、条件和人数缩放明确的技能补成 EffectAtom。
- 纯概率、倾向或公式不明确的技能标记 `unsupported`；不得参与候选、普通补位奖励、dependency
  或 `shift_bind`。
- `delegated` 只用于由既有 mood 或其他明确 domain owner 结算的技能。
- 未映射、重复映射、facility/tier 不一致或缺少稳定 atom id 都是校验失败。

## 7. 后续：Plan、轮换和缓存

`PickOne` / `OptionalFixed` 的实际选择只在 Plan 编译阶段完成。Plan 写入已解析 placement；
execute 和 rotation 只能消费该事实，不能从候选列表或 owned roster 重选。`min_count` 保留为独立
候选组 hard constraint，不固化为某一个干员。

rotation 每班在当班活跃中枢候选闭包中重新结算，而不重跑全账号体系选型或完整全基建候选空间。
每班继续硬校验中枢 5 人、required 覆盖、`min_count`、无重复干员和既有明确 `shift_bind`。本轮
不新增跨班动态 producer bind 规划。

EffectKey、ledger、顺序选位和 inventory 改变候选语义后，未来必须升级 Bake/cache schema。缓存键至少
包含 policy、effect manifest、当班 roster、布局和完整条件上下文；上下文签名不完整时禁用缓存并
live evaluation。旧 Bake 明确拒绝并回退 live，不得静默复用旧 winner。

本阶段明确不处理 Bake/cache：当前不进行 Bake 计算时，live 求解速度足够；不得为了 atom_id
迁移修改 Bake schema、缓存指纹或 Bake 产物。

## 9. 明确延期与保证边界

本任务不实现或不宣称：

- 纯概率/线索倾向中枢机制；
- 贸易/制造多房 exact joint 或全局最优；
- 中枢与办公室、会客室、训练室的联合最优；
- 实际心情恢复模型重构或默认 ABC 跨周期心情永续；
- 菲亚梅塔后处理、办公室独立轮换缺员路径；
- 新增跨班动态 producer bind 规划。

当前 stable atom identity 阶段另外延期：

- 全量 control inventory 与 fail-closed 覆盖校验；
- 14 个空 atom 的语义补齐或分类；
- `operator_instances.json` 中缺失的 control buff 定义；
- 搜索层现存按 `buff_id`/前缀识别心情的清理；
- Bake/cache schema、指纹和旧 Bake 迁移。

完成后应把确认的 current 行为吸收至对应 canonical，拆分仍有效的开放项并按文档生命周期归档本计划。
