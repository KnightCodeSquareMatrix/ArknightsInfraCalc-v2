## 4. 目标状态与责任

```text
请求与只读数据
  → 模式构造：Plan、主备或 α/β/γ、各班岗位
  → 构造完成：普通补位、支持/普通宿舍、动作及执行方式
  → 定稿：实际岗位、Plan 归属与动作不可再变
  → 最终结算：逐班与周期收益
  → 只读终检：结构、预算、动作、收益与诊断
  → 既有专用候选收益比较（适用时）
  → 文本/JSON/profile/MAA 等投影
```

这是责任顺序，不要求强行把 ABC 改成三个独立单班，也不要求消灭合法的候选试算。**构造期的暂态依赖必须显式保留并在提交时兑现；“草稿”不是允许带失效前提进入最终收益比较。**

建议内部表达三种职责，具体类型和文件名由接手者决定：

- 可修改构造状态：保存本次 Plan、已选岗位、队伍归属、班时和待完成动作；未评分状态不放最终零分。每次候选试放整体提交或放弃，不能只写了一半。
- 定稿并结算的结果：只有构造完成后才能生成公共 `TeamRotationReport`；评分是读岗位/动作后生成的派生值，不能再改变执行事实。
- 结构化问题与执行提示：内部记录类别、来源、班次/房间/干员及必要事实；最终渲染现有 warning 文本。MAA 宿舍 autofill 单独读构造决定的执行事实。

不强制做泛型状态机、事件总线、版本号框架或面向全项目的 Error 重写。用最少类型/API 限制让未结算草稿不能传给导出与练卡建议即可。外部字段默认保持，不为内部重构升级 Worker schema；要传输新增内部执行事实时先区分核心内存值与外部 JSON 的职责。

Team 保留在构造侧统一写入。不能用最终所有房间的成员并集倒推队伍，因为宿舍和菲亚跨班工作例外具有不同语义。岗位变动需同步真正受影响的归属和相邻续班，终检从实际岗位独立复核。

### 单元 1：把保守准入放在承诺成员之前

当前已核实的漏洞：`layout/assign/control_fill.rs::filter_control_pool_for_mood` 把 `candidate_requirements` 中全部名字、已 pin 成员及动态 `required_all` 合并为 protected，protected 直接 `return true`；满 5 个 pin 的快捷分支还会提前返回，跳过该过滤。`pipeline.rs::prepare_peak_control_candidate` 将动态 producer mask 的 required 传入这个集合。

按现有 MoodModel，涤火杰西卡 E2 单人保守预算为 `1 + 0.5 - 0.25 = 1.25/h`，24h 需 30 点，不能由普通技能填充选入。这个例子用于验证一般规则，禁止按姓名/fixture 特判。五例的实际 producer 选择链需在单元 0 确认；现有静态证据不等于五例都已追到唯一根因。

实施要求：

1. 明确普通候选、动态 producer、固定体系 claim、requirement-group 和已承诺 pin 各自第一次准入的 owner。复用现有逐人保守公式与实际工作窗口，不加临时完整五人搜索，不改减免公式。
2. 动态 producer 先满足当前班/队伍的工时资格，才可成为该 mask 的 required；不满足则该正常枚举组合不成立，按原有枚举继续。不能先通过后靠“protected”免检。
3. 固定体系在选型/认领前按其既有规则检查；requirement-group 的可选成员在承诺具体人之前落实资格。已经生效的 required/min_count/绑定不能在下游为了过滤而静默拆掉。不要简单删除 `protected` 分支却没有修好上游 owner。
4. 满 pin 快捷路径、`producer_fill.rs::place_system_producers` 的后写入以及普通补位必须消费已完成的资格或在最早可确定处补检查，不能出现第二条免准入入口。普通补位已有实际 ETA 检查，保持它与逐人保守筛选不同的职责，不机械双重重算。
5. registry 含 Search 或依赖外部状态的技能，不能用“整条 claim 已检查”掩盖未检查者；标清在后续哪一处、用什么已具备信息完成资格。保留既有专用机制边界；缺信息时先追真实消费路径，不猜一个统一公式。
6. ABC 自由中枢仍按实际队伍完整工作窗口筛一次：α=`H1+H3`、β=`H1+H2`、γ=`H2+H3`；主备按各自班时。终检保留真实组合与首尾周期复算，不恢复逐班反复筛池或报错重求。

这是落实已定 hard constraint 的修复，不是新的收益 heuristic。其导致的候选/输出变化需要解释，但不要求错误旧结果保持相同。
