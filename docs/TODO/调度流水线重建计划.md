# 调度流水线重建计划

> 文档角色：active-change
> 生命周期状态：ready-on-request
> 当前真源：docs/ORCHESTRATION_LAYER.md
> 摘要：在独立分支重建从用户请求到完整排班结果的确定性调度流水线

## 1. 目标

在独立分支重建调度主线，替换当前 `team_rotation` 与单班
`pipeline` 平行推进排班、结算和跨班状态的结构。

新主线从用户请求开始，到完整的排班、效率、心情、休息、依赖、MAA
与其他导出投影结束。一次执行只产生一份可审计结果；所有导出只投影该
结果，不再次求解。

重建不是把旧文件换目录，也不是拆出可独立发布的效率库。效率和机制依赖
完整布局、人员互斥、跨房依赖与排班状态，核心仍保持在同一个求解器 crate。

## 2. 不变量

1. 主线从标准化用户请求开始，`plan`、`plan.compute`、Worker 与 CLI 仅是
   输入/输出适配器，不拥有独立计算分支。
2. 每个 Shift 只经一条顺序推进：编译目标与约束、房间求解和提交、`resolve`、
   终态校验、跨班状态推进。
3. 任何房间提交、特殊机制换人或状态变更之后，后续步骤只能读取更新后的
   当前排班状态，不得继续消费旧 layout 或旧 `used` 集合。
4. 房间、菲亚梅塔、深海、岁等具名机制都是同一流水线中的工作步骤；它们可
   使用共享当前状态，但不得绕开提交、重算与校验顺序形成另一条排班链。
5. 调度继续是阶段式、按房间的具名 policy，不宣称全局最优；每项策略限制和
   阶段结果必须进入可审计 trace。
6. 迁移期对既有批量验收页面要求完整确定性输出完全一致，包括 JSON、MAA、
   数值和稳定排序。任何差异必须先解释或修正，不能以容差、快照更新或
   fallback 吞掉。

## 3. 目标流水线

```text
用户请求
  -> 标准化请求与数据快照
  -> 编译调度目标、硬约束和具名策略
  -> 对每个 Shift：求解房间并提交当前 assignment
  -> resolve 当前完整 layout
  -> 校验人员、容量、绑定、心情和 profile 终态
  -> 推进休息、心情、依赖与下一 Shift 可用性
  -> 汇总整轮结果与阶段 trace
  -> CLI / Worker / MAA / JSON 投影
```

代码按实际流程、房间求解与具名特殊机制组织，而不是延续
`team_rotation.rs`、`pipeline.rs` 的历史边界。房间 solver 与机制计算在新主线中
同步重写；旧实现不作为新代码依赖，只在迁移期作为输出对照。

## 4. 迁移边界

### 保持不变

- 当前效率语义、领域机制和已裁决的特殊策略含义。
- `plan`、`plan.compute`、Worker/serve、CLI 的请求与返回契约。
- 当前阶段式求解保证等级。
- 既有批量验收页面及其完整结果对照职责。

### 必须消除

- `team_rotation` 与 `pipeline` 对 assignment、resolve、dependency 的平行推进。
- Recovery shadow winner 提交后继续使用旧 layout。
- 公共 assignment facade 返回未解析 dependency、由调用者补跑的契约缺口。
- gamma half 未完整消费 Plan constraints 的隐式缺口。
- 失准 baseline fallback 和不再有消费者的遗留路径。
- 中枢 buff 分类在多个 owner 中分别维护。

### 非目标

- 不拆出独立发布的机制/效率 crate。
- 不在首轮改变外部 wire 协议或要求前端同步迁移。
- 不以全局联合优化取代现有阶段式 policy。
- 不为迁移新增单一 operbox golden 或第二套本地 oracle。

## 5. 重建顺序

1. 在独立 branch 冻结现有外部契约和批量验收入口。
2. 建立从标准化请求到完整结果的空主线与同源 result/trace 模型。
3. 同步重写每 Shift 的 Plan、房间求解、提交、resolve、验证和跨班状态推进，
   逐步接入中枢、贸易、制造、电站、办公室、会客室与宿舍。
4. 将菲亚梅塔、深海、岁和其他具名策略接入相同主线，消除绕过当前状态的
   旧分支。
5. 用批量验收页面逐段比较完整输出；差异归因后才继续下一段。
6. 全量一致后删除旧 `team_rotation`、`pipeline`、遗留 baseline/probe 与旧内部
   分支，并更新当前架构文档。

## 6. 测试处置

不迁移 `team_rotation`、`pipeline` 中服务于旧函数结构、固定快照或实现细节的
测试。代码内只保留终态约束：

- 同一 Shift 无重复人员，房间容量正确。
- Team/Shift bind、依赖与 required placement 闭合。
- 心情、休息、连续工作和 profile 特有终态合法。
- 所有导出来自同一次完整求解结果。

批量验收页面与人工审阅负责完整结果、策略合理性和真实用户可见差异；自动化
测试不伪装成对全局排班质量的证明。

## 7. 完成标准

1. 新主线覆盖所有当前支持的布局、profile 和具名特殊机制。
2. 批量验收页面对迁移范围内的完整输出完全一致。
3. 每个结果可追溯到输入快照、Shift 阶段、房间提交、resolve 结果与策略限制。
4. 旧编排路径、无消费者 baseline/probe 和重复 owner 已删除，而非仅被新路径
   绕过。
5. 当前架构真源吸收新事实；本任务归档，不在 `docs/TODO/` 保留已完成计划。
