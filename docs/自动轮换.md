## 1. 状态与范围

自动轮换是一种**建议模式**：为每个工作站给出主力与替补配置，让玩家使用游戏内置队列自行换班；不模拟实际换班时刻、错班或宿舍恢复。当前入口为 `plan --rotation auto@H1/H2`，独立建议报告；共用排班步骤与验收见 [建议调用链](调用链/自动轮换建议.md) 和第8节。

用户对模式的总体描述（2026-10-26 原话）：

> 自动轮换也只是去掉一些功能的正常排班。确定我说的对不对。你把工程量和难度混为一谈了。

出处：会话 `838409c4` L1416（2026-10-26T10:18）。这是一句模式定位，不是新增规则；本页把它作为理解后续裁决的上下文，不据此推导未裁决的实现细节。

本轮范围：不接网站、MAA 或部署（2026-10-24 用户原话）。2026-10-11 第 8 题曾答“8包含”（网站与 CLI 都纳入），该部分已被 2026-10-24 的收窄取代。

## 3. 已裁决的语义

以下每条都标注类型：**用户裁决**（有逐字原话或结构化答复）、**由原话推断**、**agent 建议默认**。只有前两类可以写成产品规则；第三类在用户确认前不得当作已裁决。

### 3.1 特殊两班制：每站一主一替、工作成员互斥、主力优先

- **用户裁决**：整体结构沿用主备轮换的“特殊两班制”（2.1 原话：“整体逻辑是与主备轮换是相似的，仍然是特殊的两班制”），但触发与输出不同（见第 4 节）。
- **用户裁决**：每站一主一替，不同站的主力和替补完全不同（工作成员互斥）。原话：“为每一个站设计完全不同的轮换组，只要保证1主1替补，不同站的主力和替补完全不同”（2.1）。
- **用户裁决**：主力优先，替补不齐时保留主力（第 5 题 `5A`，2.2）。
- **用户裁决**（2026-10-28，2.6）：中枢也分主备、且互不重叠。结构化问答：“自动轮换里，控制中枢也分主力和替补吗？”=“分主备、不重叠 (Recommended)”。该条关闭第 6 节原第 1 项。

### 3.2 允许与禁止的协同

允许：

- 单站组合（第 2 题 `2禁用` 所选 A；2.1 原话“尽量使用纯粹的单站可以用的组合”）。
- 宿舍挂件 1＋1：一个常驻宿舍挂件 + 一个生产受益者；挂件可供主备共用（第 2 题 A、第 3 题 `3可以使用`）。
- 发电＋制造自动化组合（第 2 题 A；2.1 原话“自动化组合这个发电加制造的方式”）。
- 依赖建筑数量或等级、不要求其他站放特定干员的技能（第 2 题所选 A 的选项说明；该说明是 agent 文字，用户未逐字复述。用户的 2.1 原话直接支持中枢全局光环，没有逐字说建筑数量/等级类技能，但也没有把它列入禁止的跨站协同）。
- 中枢全局光环（2.1 原话“加贸易+7制造+3+2人力+10…全局光环”）。
- 中枢内部组合（第 4 题 `4允许`），但中枢全局光环优先。
- **用户裁决**（2026-10-28，2.6）：分类表放行边界——“只放行发电＋制造分支；莱茵宿舍 1＋1 按‘一挂件一受益者’放行，其余拒绝”。答句是“按 ADR 建议默认 (Recommended)”；清单内容是 agent 建议默认，因用户答句采纳而成为已裁决语义，不是用户逐字写出。该条关闭第 6 节原第 5 项。
- **用户裁决**（2026-10-28，2.6）：宿舍挂件 1＋1 不受 `support_combinations_enable` 总开关控制。结构化问答：“宿舍挂件 1+1 在自动轮换里受不受‘支持组合’总开关（support_combinations_enable）控制？”=“不受开关控制 (Recommended)”。该条关闭第 6 节原第 4 项。

禁止：

- 除上述例外外的其他跨站协同。第 2 题题干明确包括“制造站甲依赖制造站乙的特定成员”这类跨房间、同设施类型的关系（`auto-rotation.md:178-186`）。
- 四赤金。2026-10-28 结构化问答答“禁用”（2.5）。四赤金依赖全基建杜林人数和跨贸易房的虚拟赤金线，属于被禁止的跨站协同。

### 3.3 缺员标注

**用户裁决**（第 5 题 `5A`，2.2）：替补配不齐时，主力保持不变，替补先用普通散件补齐；仍无法补齐，标出具体缺员和方案不完整。2026-10-28 进一步裁决（2.6）：缺员“按建议默认”标注；标注内容是 agent 建议默认（列出哪个站、哪个位置缺人，并标该站替补不完整；该站照常输出），因用户答句采纳而成为已裁决语义。该条关闭第 6 节原第 3 项。具体输出字段与文案形态仍是 **agent 建议默认**。

### 3.4 时长评估

- 当前裁决见2.7：主力 H1、替补 H2；每组从满心情撑满自己的输入时长，收益只算该时长，不模拟宿舍恢复或长期周期。
- 完整组合用实际同房成员与中枢计算净消耗。Plan尚未补齐的前缀不能仅因当前ETA不足就被拒绝；完整房间候选、补位与最终逐房混合配置各自检查实际成员。
- 每房可独立选主或备，中枢也可切换。最终配置中，每房按其名单来源的 H1/H2 检查，不能把所有房统一按一段时长或只检查两套整班。
- 输入时长是收益计算的 policy；撑满输入时长是 hard constraint。沿用有序竞争与搜索，不声称全局最优。

## 4. 与定时轮换的区别

| 维度 | timed_rotation | auto_rotation |
|---|---|---|
| 触发与时间 | 固定班次表或有序时长（named profile、`main-backup@H1/H2`、`abc@H1/H2/H3`） | 没有求解器侧班次时刻；每站按红脸独立换班，只给主备配置建议（用户 2.1“不用考虑它实际上的错班或者轮换的问题”） |
| 输出 | `TeamRotationReport`：teams、shifts、按周期归一的 `daily`、`peak_mood_eta`，外部可投影到 MAA | 按站的主备建议配置；不进入 MAA（用户 2026-10-24） |

## 5. 保证等级

以下分类均为 **agent 建议默认**，用户未逐字裁决；用户已明确项目不承诺全局最优（2026-10-27 原话“我们也从来没有保证全局最优”，会话 `e235e78e` L3369）。

- 禁令（允许/禁止的协同、四赤金禁用）：**hard constraint**。违反即拒绝或最终态断言失败；不因效率更高而放行。
- 选人（主班、备班、缺员补位）：**heuristic**。沿用现有 Peak 与互斥备班构造，不声称全局最优。
- 时长评估：**policy**。按2.7输入窗口计算并参与比较；撑满窗口是 **hard constraint**。不声称能证明最优。
- 整体：不声称全局最优；不证明普通排班内部或跨 layout 的完整方案最优。

## 8. 当前实现责任

统一 core `schedule_rotation` 按模式和时长分派，输出仍分独立建议与定时报告。入口 `infra-cli plan --rotation auto@24/12 --operbox <path> --rotation-out <path>` 调用独立 `schedule_auto_rotation`，输出 `AutoRotationReport`；不经过定时 profile、事件、恢复、MAA 或 Worker。公共 `AssignBaseOptions` 的模式输入只参数化 Plan、设施搜索和普通完成步骤，不把建议报告包装成定时轮换。

先按既有优先级确定主中枢，再从剩余成员确定备中枢；随后通过现有 `solve_owned_peak_seed` 建立主力，工作候选同时检查两个中枢下的预算，预选备中枢成员保留给替补。公共主备 owner 排除全部主力工作成员构造替补，并沿用预选备中枢。主力先完成普通空座，替补使用剩余候选同样完成。宿舍挂件沿现有角色递归临时放置；对应房清除预选受益者后按原设施搜索选出完整赢家，只有受益者入选才保留挂件、Plan anchor与依赖。制造和发电不再为这条路径补排全基建比较总收益；贸易沿用有序role及普通搜索，普通搜索用已有full_pool保证试算受益者不被白名单排除。替补新增挂件的准入同时检查固定主力，选中的宿舍集合在两态常驻。不会安排普通宿舍休息。

能力准入消费真实成员、技能 atom、资源转换来源、贸易委托依赖和支援技能注册表，拒绝已激活的禁止跨站成员关系；Plan registry 只放行单站，自动化仅发电加制造分支，宿舍角色只允许一挂件一受益者。后续候选不能通过新增成员激活已选房的禁止协同。建筑数量等级和中枢静态光环保留；公式仍由既有机制 owner 负责。

主力/替补输入窗口进入 Plan 早期比较、贸易、制造、发电及支援设施候选评分和终态快照；完整 ETA 使用同一心情 owner 复核预算。自动制造负心情差成员不走≥12小时身份排除，按既有心情分段和连续暖机积分结算。输出逐站成员、普通效率、充能/支援速度/中枢效果、评估窗口、首人红脸、缺额，单独说明常驻挂件；没有主备占比或平均日产出。

Rust 最终 gate 检查身份、结构、主备工作互斥、Plan 必需成员与真实依赖、能力准入、两态宿舍共享、完整房间覆盖、缺额标注、窗口、快照重算，并用独立assignment ETA数值复核两个中枢下的预算。验收规模与边界见[挂件选人修正交付记录](ARCHIVE/done/自动轮换挂件选人修正-20261029.md)及前轮归档；这些检查不证明全局最优。

会客室成员不计莱茵基内人数，准入与WorkforceIndex使用同一范围；贸易同房标签只查本房，中枢对贸易标签的注入仍查目标站。办公室按招募栏位向会客室注入速度属于建筑配置收益，允许；依赖中枢特定成员、跨站精英成员或资源的支援技能仍按成员关系检查。发电逐站选入后更新同轮真实成员快照，再检查下一候选。

替补候选按实际RoomId只替换本房，与其他房主备可共存状态成对检查；不把同房两态成员合并。建议返回前和终态gate均精确枚举每工作房取主或备的全部混合状态，宿舍固定共享，用同一能力门禁复核；没有时间线或恢复模拟。

资源来源读取中枢实际资源写入、发电虚拟产出及跨设施global执行器的非零写入；全局转换只沿原执行器实际执行的边传播来源，并登记启用转换的在岗成员。保留蓝图初始资源池，初始资源本身不伪造成员依赖；需要外站特定成员转换后才生效时仍拒绝。无预置碎片时，一级办公室絮雨净碎片0不会成为外站感知来源；预置碎片可经她转换，因此仍构成成员依赖。

黑键/迷迭香的房内转换不发布给外站；房内转换读取共享感知时仍核对原始来源。平台条件保留实际触发阈值，布丁在仅一个平台时不被误判为已激活跨站制造加成。来源在同一次准入中按需读取，仅实际资源消费者触发原解释器。
