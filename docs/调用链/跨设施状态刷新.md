## 刷新触发和顺序

`run_shift_pipeline` 在 Plan 执行、control/producer/power/trade/manufacture fill 的阶段边界调用 resolve。每次使用当前 assignment 和 blueprint，生成新的 `WorkforceIndex`、control ledger、support/power facts、global state/inject 和 room inputs；未来分支的 snapshot 不可复用。

独立单班 `assign_shift_with_plan` 在流水线返回后先由办公室 owner 排序选择余员，再把完整 assignment 与已裁剪候选交给 `layout/vacancy_fill.rs` 补七类普通工作空座，最后刷新贸易/制造快照。轮换使用的 skip/preclaimed 流水线不在此阶段补普通人，而在完整周期与归属确定后统一补位，再落普通休息宿舍并重算最终效率。不能把最终快照正确等同于所有前序候选都已按未来普通入住者联合比较；现有顺序 policy 不作该保证。

灵知线路的市井孑能力候选仍由 pool 的具名注入处理，但实际 layout 使用 `add_owned_jie_market_to_trade_pool`：先确认账号持有且已解锁对应档位，再使用账号真实 progress，不把无持有的能力模板或模板 1 级写成实际岗位。假想单房搜索保留原能力模板入口，不作为全基建持有证明。

夜烟贸易/制造归属比较仍只覆盖既定首房冲突：当前未占用候选必须同时存在于两池，贸易 pick 也必须实际选中夜烟，才继续探测制造 pick。制造探测与普通制造填房一样，在满员搜索没有合法命中时使用现有容量 fallback 保留合法的 0..N 人；没有双侧竞争就保留已经选定的 Peak 结果。空贸易命中按空房提交而不生成虚假的效率快照。候选不足不是可选比较的执行故障；正式 resolve 和机制结算错误仍向上传递。这是既有 policy 的缺员边界修复，不是通用冲突闭包或联合最优实现。

主动挂件目前是 Plan 已解析的 `proactive_support` anchor，不是通用延迟 `SupportClaim`：execute 在 Peak 搜索前真实落位，逐班按活跃 bind 从 peak 复制后评分。普通宿舍休息成员由后置 finalizer 生成，它们不是提前承诺的挂件；末尾重新评分保证最终实际 presence 正确，但不伪造尚不存在的承诺层。开启挂件的真实逐班证据与限制见活动重构 checkpoint。

主备 24/24 显式设置 `AssignBaseOptions.control_work_hours`。Peak 中枢候选提交前由 `prepare_peak_control_candidate` 试放整套中枢并调用 `shift_eta_with_instances`，在 `search_control_combos_with_eligibility` 的 top-K 前筛选；Plan 已满五人也执行同一检查。缺省为 `None` 的单班与旧 profile 保持既有选人策略。该局部可行性读取当前 Plan seed，完整生产成员落位后的持续工作仍由排班最终 gate 复核。

魔王配对恢复不经过第二次 control/global inject：技能表显式承认两档委托来源后仍由原建池准入处理；ETA 的净消耗 owner 从试放或最终 assignment 的实际房间成员结算配对。候选可工作时长和周期末复核因此使用同一份 mood 数据；维什戴尔既有外部设施协同继续读取当班实际中枢，不把阿米娅或魔王精二增加为其触发条件。未知 buff 仍跳过，余位及队伍范围不被该接入绕开。

```text
partial assignment
 -> WorkforceIndex
 -> control solve + ledger
 -> power/office/meeting
 -> collect_global_atoms
 -> orchestrate_global_atoms (StateWrite)
 -> resource conversion + GlobalInjectManifest
 -> room snapshots
 -> next fill/search
```

## 状态 owner

| 状态 | 写入函数 | 消费者 | 失效条件 |
|---|---|---|---|
| Control ledger | `apply_control_to_layout_with_trace` | control policy/trace | 中枢成员改变 |
| workforce/tag counts | `WorkforceIndex::build` | selectors/producer rules | 任一 assignment 改变 |
| global state | `orchestrate_global_atoms` | global pool/consumer | global source/level 改变 |
| 赤金虚拟线来源 | `resolve_base_core` | 金单贸易房 L2 和实时贸易候选投影 | 任一贸易站供线者、杜林实际进驻或赤金制造配方改变 |
| inject manifest | `control` + `global_resource` | trade/manufacture | producer admission/target 改变 |
| room snapshots | `resolve_base` | domain solver/export | 上游状态再次变化 |

producer 必须 source 在当前 assignment、admission 和 target/relation 同时满足；标签存在不能代替 presence。resolve 错误向上返回，不能用旧快照继续。

杜林人数只从本班实际进驻房间计数（排除副手和会客室，封顶 4）。`resolve_base_core` 遍历所有贸易站的供线者，把鸿雪与绮良的虚拟线加入全局读数；金单房的 `apply_gold_flow_chain` 扣回本房供线再按进驻和技能顺序重放，其他金单房直接读到跨站供线。绮良、鸿雪、图耶中两名或三名同房时，assignment 在技能效率快照生成前按该链的顺序排序，导出沿用顺序。贸易候选尚未提交时，`project_trade_combo_layout` 仅对新增干员和人数增量投影，防止已有来源重复计入。

诊断顺序：比较 assignment/used → 查看 resolve trace/ledger/global manifest → 检查 producer rules → 检查下一阶段 room input → 最后才查域内公式。验证用 `layout eval --explain-json`、`plan --assert-invariants` 和代表性/high-owned fixture。
