## 输入类型

### 文件型 CLI 输入

`plan` 和 `layout` 命令从文件加载：

- `BaseBlueprint`：布局房间、等级、生产配置、无人机上限和场景参数；语义校验由 `BaseBlueprint::validate` 完成。
- `OperBox`：JSON 数组或 `plan` 支持的一图流 xlsx；每项必须有 id、name、elite、level、own、potential、rarity。
- 运行时表：`operator_instances.json`、`skill_table.json` 等由 `default_*_path` 定位；数据搜索和 fallback 归 `infra-core::skill_table`。

`plan` 默认使用 243 布局和 full-e2 operbox。正式调用应显式传入输入与输出路径，避免把结果写回输入目录。

`scenario.initial_global` 可以为其他资源提供场景初值，但 `monster_cuisine` 只由当前编制中精二森西的宿舍技能产生；旧请求中的该键仍可读取，但会从结算初始池忽略，不能成为料理来源。消费者不要求与森西绑定；没有料理时仍可凭自身基础技能工作。

宿舍 `level` 是唯一的技能等级输入，必须为 1–5；`dorm_beds` 单独表示床位容量，不能代替等级。已发布的请求和旧布局中的 `dorm_ambience_level` 仍能解析，但不参与等级计算，也不再由当前生成器输出；旧双等级输入以 `level` 为准。

### `plan.compute` 内联输入

请求 `method` 为 `plan.compute` 时，`params` 必须包含：

```json
{
  "schema_version": 6,
  "layout": { "rooms": [] },
  "operbox": [],
  "labels": { "layout": "optional", "operbox": "optional" },
  "options": {
    "rotation": "abc_12_6_6",
    "top": 20,
    "system_preferences": {},
    "maa_title": null,
    "fiammetta_enable": true,
    "support_combinations_enable": false,
    "assert_invariants": false
  }
}
```

`additionalProperties=false`：未知字段在 schema admission 阶段拒绝。当前源码与契约支持 schema v1–v7；v6 保持旧闭集，v7 保留 v6 的 named profile 字符串并新增两类普通 topology 对象：`{"topology":"main_backup","shift_hours":[H1,H2]}` 与 `{"topology":"abc","shift_hours":[H1,H2,H3]}`。本地最终release的v7 ABC8/8/8与主备8/16已通过显式终态断言，尚未部署；消费者以实际ping为准。数组长度由拓扑结构限定，时长组合业务合法性由调用方负责；后端不通过增加 profile 枚举实现泛型。v1–v6 的 schema 文件和 wire 解释不变。历史 v3–v5 schema 仍会结构接受其旧龙巫 wire，但解码所得 tombstone 只用于在排班前明确拒绝，不映射到普通主备。每个版本允许的结构 profile 以对应 schema 文件为准；schema 结构接受不等于当前 Worker 支持该产品语义。

`main_backup_24_24` 从 v5 请求枚举开始提供，v7 继续接受：两个 24h 状态，总周期 48h。v1–v4 保留各自原有枚举并拒绝该值。文件型 CLI 接受 `24/24`、`main-backup-2424` 和 wire 名。泛型主备自定义时长属于 v7，不继承姓名排除名单；named与泛型长班仅最初中枢名单按实际ETA窗口试算，后续心情不足只诊断，泛型 >24h 使用输入的实际班长。旧 named 24/24 的 24h control ETA 窗口保持不变。48h 模式的 `rotation.daily` 是按全周期归一的 24h 平均值；MAA 仍为两班，相对间隔各 24h。兼容消费者应核对本次 Worker 的契约 hash。

generic 时长在 schema 结构解码后还须通过 core 数值安全检查，规则唯一见[定时换班](../定时换班.md)：有限正数、分钟权重非零及整数算术边界。该检查不是 24/36/48h 业务组合限制，不改变 v1–v7 schema 文件或 hash。失败使用既有 `PLAN_FAILED` / `plan.compute` 错误 envelope，消息含 `rotation_duration_input:`，不会生成可供导出的完整 rotation；同一 Worker 进程仍可继续处理后续请求。JSON 不支持 NaN/Infinity 数字；非有限值的直接 core/CLI 检查不应冒充 JSON Schema 新能力。

`support_combinations_enable` 为布尔值，缺省 `false`，包括 v1–v4 的旧请求。`true` 沿用目前主动补挂件行为；`false` 禁止受控组合主动补人，哪怕只补 1–2 名，但不关闭主角色正常竞争或技能的真实编制读取。普通同房组合、深巡和鸿雪豁免；思衡托仍自然读取精英设施数。默认关闭是本次明确接受的行为兼容变化，输出不新增模式字段。

限制由代码和 schema 同时约束：operbox 1–1000 项、layout 房间 1–64、`top` 1–100、label 非空且不超过 200 UTF-8 字节。通过 JSON Schema 后仍执行布局唯一性、设施/产品匹配和 operbox 进度等语义校验。

## 输出类型

### `plan.compute` 外层响应

每行响应都有：`id`、`ok`、`elapsed_ms`、`solver`。成功时 `result` 包含 `schema_version`、`profile`、`rotation`、`maa` 和 `training_advice`；失败时通常 `ok=false`，外层 `error` 有 `code=PLAN_FAILED`、`stage=plan.compute`，`result.error` 同时包含业务失败信息，便于前端保留部分 rotation/profile。

`rotation` 是当前排班的结构化结果：profile、daily 三域效率、每个 shift 的时长、active/resting team、assignment、分房效率和加权效率。Trade 分房的 `final`/`trade_efficiency` 已包含单位产出倍率，`total_efficiency` 仍是纸面总效率；该内部语义变化不新增或改变 wire 字段。`profile` 是账号分析投影，不是完整 assignment 副本；在v7中，它是求解后的 scalar identity，不是请求回显，generic `[12,12]` / `[24,24]` / ABC `[12,6,6]` / `[12,12,12]` 会归一到对应 named profile，其他泛型分别为 `generic_main_backup` / `generic_abc`。实际时长读取 `rotation.shifts[].duration_hours`，`maa` 读取同一 rotation 的最终 assignment；导出层不重新选人。本地v7已验证8/8/8→generic_abc及8/16→generic_main_backup；未逐一验收所有归一映射，契约文件不能证明线上已部署。

对 Worker 消费者，`method=plan` 返回的 `shifts` 是完整 `TeamShiftResult`，包含最终菲亚动作；`plan.compute` 的 `rotation.shifts` 摘要只含岗位、班时和效率，不含该动作字段，但同一响应中的 `maa.plans[].Fiammetta` 保留最终动作。不要把 `rotation` 摘要缺少该字段推导成求解未产生动作，也不要从 MAA 反推其他班次的工作 assignment。

### `plan` Worker 方法

`method=plan` 接受文件路径参数并返回 `PlanResult`：layout、operbox、owned、top、rotation、可选的 profile/MAA/output_dir 路径、daily 效率、shifts 和 warnings。它与 CLI `plan` 共用 `compute_plan`，但输出是 Worker result，不是 `plan.compute` schema。

### 文件输出

- profile：`BoxProfile`，当前 `schema_version=4`；包含 summary、domains、rotation 和 baseline rotation。
- rotation：`TeamRotationReport`，由 `--rotation-out` 写出；用于后续 `layout eval` 或人工审阅。
- `main_backup_24_24` 的 CLI 文本在有菲亚动作时，逐班列出最终目标及其 TradePost；若回池目标出现在两个 owner assignment，队伍花名册只在其动作班所属 owner 下计一次，逐班工位行仍显示各班真实岗位。该可读摘要不改变 `TeamRotationReport` wire 或动作选择。
- MAA：`MaaSchedule`，由 `build_from_team_rotation` 生成；读取 rotation 已确认的班次，不重新选择干员。`main_backup_24_24` 的 plan description 在存在菲亚动作时说明本班实际目标；这是给执行者看的提示，不扩展字段或证明目标也在另一班工作。
- `layout eval --explain-json`：`schema_version=1` 的固定编制结算 trace，包含 room 结果、control events、final state 和 totals。

当布局包含回收站时，MAA 每个 plan 的 `rooms.recycle` 按蓝图顺序投影最终 assignment，每项形如 `{ "operators": ["干员名"] }`；不输出 A/B 或 product，也不在导出层补选。布局没有回收站时省略该键。当前 MAA 读回路径不恢复 recycle，不能把导出支持推导为双向导入支持。

消费者应读取结构化 JSON，并检查 schema/version；不要从 stdout 文本或历史 fixture 推断 wire 字段。

## 兼容原则

兼容层是字段、枚举、单位、缺省和错误表达的契约。可以重写内部求解，但不能静默改变 `BaseBlueprint`、`OperBox`、`BaseAssignment`、效率分量、轮换 profile 名称和“不支持/无解”的表达。新字段应升 schema 或进入明确兼容版本；旧版本 schema 不接受未知字段。

自动建议CLI使用 `auto@H1/H2`，独立`AutoRotationReport.timing.shift_hours`保存有序输入，各房主备`evaluation_hours`分别对应H1/H2。该建议报告不进入定时profile/MAA/Worker契约；详情见[自动轮换](../自动轮换.md)。
