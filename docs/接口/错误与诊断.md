# 接口错误与诊断

> 文档角色：canonical
> 生命周期状态：current
> 领域键：interface.errors
> 当前真源：self
> 摘要：按输入、协议、求解、断言和导出阶段定位错误
> 代码范围：`crates/infra-cli/src/main.rs`、`commands/serve.rs`、`commands/plan_compute.rs`、`commands/debug.rs`、`commands/layout.rs`、`commands/verify.rs`
> 代码锚点：`handle_request`、`validate_plan_compute_params`、`compute_plan_attempt`、`rerun_cmd`、`layout_eval_cmd`
> 关联链路：[debug 与验证](../调用链/debug与验证.md)、[plan 请求](../调用链/plan请求.md)
> 核验基线：错误输入最小复现；`layout eval --explain-json`；`debug rerun --pretty`

## 错误类别

| 类别 | 首个定位点 | 典型表现 | 下一步 |
|---|---|---|---|
| 协议错误 | `serve::handle_request` / `read_ndjson_frame` | JSON 无法解析、非 UTF-8、frame 超限、未知 method | 保留 request id 与原文摘要，修调用方协议 |
| schema 错误 | `validate_plan_compute_params` | schema 版本不支持、未知字段、字段类型/范围错误 | 对照对应 `contracts/plan-compute-v*.schema.json` |
| 输入语义错误 | `BaseBlueprint::validate`、`inline_operbox` | 房间重复、产品与设施不匹配、operbox 重复 id/name、练度不可达 | 先修 layout/operbox，不判断 solver 根因 |
| 资源加载错误 | `OperatorInstances::load`、`SkillTable::load`、`BaseBlueprint::load` | 文件不存在、JSON/CSV 解析失败、运行时表缺项 | 核对数据根、版本和 `skill_table`/instances 配对 |
| 求解失败 | `compute_plan_inner`、schedule/layout owner | 无解、候选不足、约束冲突、阶段错误 | 记录输入、rotation、首个阶段和 partial result |
| 最终断言失败 | `assert_final_rotation_invariants` | `--assert-invariants` 失败 | 检查最终 rotation assignment 与 invariant 名称；不是输出格式问题 |
| 导出失败 | `build_from_team_rotation`、`MaaSchedule::save` | MAA 写出或 JSON 序列化失败 | 先确认 rotation 已成功，再查导出路径/字段 |
| 回归失败 | `commands/verify.rs` | `FAIL ...` 后 `regression failures` | 对照 CSV 期望、fixture 选择和 solver 结果 |
| debug 重跑限制 | `commands/debug.rs::rerun_cmd` | bundle 版本不支持、缺 inline snapshot、focus 无 output-dir | 按 bundle 合同补齐输入；不能执行 bundle 中旧命令 |

## `serve` 错误外形

请求解析或未知方法错误只返回外层 `error`。`plan.compute` 业务失败在 `ok=false` 时同时保留 `result.error`；当 `assert_invariants=true` 时失败会直接作为外层错误，不保证 partial result。成功响应的 `error` 必须为 null/省略。

常见协议 code：`FRAME_TOO_LARGE`、`INVALID_UTF8`、`PLAN_FAILED`。普通解析错误可能没有 code/stage，这是实现事实；调用方必须先看 `ok`，再读取 `error`。

## 诊断证据顺序

1. 保存完整请求或文件输入的 hash/副本，避免只贴 stdout。
2. 记录命令、layout、operbox、rotation、top、数据目录和 commit。
3. 记录首个失败阶段及完整错误文本；区分输入失败、无解、超时和最终状态错误。
4. 若是已生成结果但某房错误，用 `layout eval --explain-json` 检查固定编制的正式结算 trace。
5. 若是生产 bundle，使用 `debug rerun`；它按 bundle 内联 snapshot 优先，按当前 executable/catalog 计算指纹，只比较稳定 assignment projection，不宣称 bit-identical。
6. 修复后分别重跑相同入口和适用的 `verify --case/--all`；不要用一次成功的 plan 代替全局保证。

不要把历史日志、旧 top hit、profile 或 baked catalog 当作当前规则真源。机制问题引用游戏机制知识库；实现问题沿[plan 请求](../调用链/plan请求.md)和代码锚点继续向 core owner 定位。
