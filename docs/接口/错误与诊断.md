## 错误类别

| 类别 | 首个定位点 | 典型表现 | 下一步 |
|---|---|---|---|
| 协议错误 | `serve::handle_request` / `read_ndjson_frame` | JSON 无法解析、非 UTF-8、frame 超限、未知 method | 保留 request id 与原文摘要，修调用方协议 |
| schema 错误 | `validate_plan_compute_params` | schema 版本不支持、未知字段、字段类型/范围错误 | 对照对应 `contracts/plan-compute-v*.schema.json` |
| 已删除 profile | CLI profile 解析、`serve::handle_plan` / `handle_plan_compute`、`schedule_timed_rotation_request`、`debug::rerun_cmd` | 旧龙巫别名、Worker v3–v5 wire、直接 core 旧 token 或旧 bundle | 明确报不支持；不映射普通主备、不构造 fallback；普通 ABC 同站组合不受影响 |
| 输入语义错误 | `BaseBlueprint::validate`、`inline_operbox` | 房间重复、产品与设施不匹配、operbox 重复 id/name、练度不可达 | 先修 layout/operbox，不判断 solver 根因 |
| 资源加载错误 | `OperatorInstances::load`、`SkillTable::load`、`BaseBlueprint::load` | 文件不存在、JSON/CSV 解析失败、运行时表缺项 | 核对数据根、版本和 `skill_table`/instances 配对 |
| 轮换质量诊断 | `schedule_timed_rotation_request`、profile/finalizer owner | 缺员、专用组合未成立、动作缺席、结构或预算问题 | 保留排班与 warnings，不把质量问题称为账号无解 |
| 求解执行失败 | `compute_plan_inner`、schedule/layout owner | 尚未生成报告的未处理构造故障、未知阶段错误 | 记录输入、rotation、首个阶段和 partial result；不能将“既有失败”当作合理拒绝的豁免 |
| 最终断言失败 | `assert_final_rotation_invariants` | `--assert-invariants` 失败 | 检查最终 rotation assignment 与 invariant 名称；不是输出格式问题 |
| 导出失败 | `build_from_team_rotation`、`MaaSchedule::save` | MAA 写出或 JSON 序列化失败 | 先确认 rotation 已成功，再查导出路径/字段 |
| 回归失败 | `commands/verify.rs` | `FAIL ...` 后 `regression failures` | 对照 CSV 期望、fixture 选择和 solver 结果 |
| debug 重跑限制 | `commands/debug.rs::rerun_cmd` | bundle 版本不支持、缺 inline snapshot、focus 无 output-dir | 按 bundle 合同补齐输入；不能执行 bundle 中旧命令 |

## `serve` 错误外形

请求解析或未知方法错误只返回外层 `error`。`plan.compute` 业务失败在 `ok=false` 时同时保留 `result.error`；当 `assert_invariants=true` 时失败会直接作为外层错误，不保证 partial result。成功响应的 `error` 必须为 null/省略。

常见协议 code：`FRAME_TOO_LARGE`、`INVALID_UTF8`、`PLAN_FAILED`。普通解析错误可能没有 code/stage，这是实现事实；调用方必须先看 `ok`，再读取 `error`。

## 轮换质量诊断

ABC 的 `control rotation ETA candidate budget exhausted` 表示当前朝向的有界中枢候选预算耗尽，不是领域无解证明；`control rotation ETA cannot cover` / `nonproduction rotation ETA cannot cover` 指出实际班次和失败成员。明确的 ETA 失败允许完整重算另一生产半区朝向，再尝试 Plan 确认的可选中枢角色回退；机制、容量、绑定或其他阶段错误不触发这条重试。终态仍须通过原有 Rust ETA、required anchor 和绑定检查。

`rotation_cycle_rest:` 由 core 在最终全部班次及宿舍落位后生成，通过现有 `TeamRotationReport.warnings`、CLI 与 Worker warnings 投影输出。它表示干员整周期在工作岗位且无具名豁免，包含姓名、各班房间/岗位和豁免判定；不是求解错误，成功响应仍为 `ok=true`，不阻断 MAA 导出。MAA 继续只执行最终 assignment 和已确认的菲亚 `target/order=pre` 指令，不证明游戏内实际执行。

`--assert-invariants` 的 `rotation_cycle_rest_diagnostics` 只在诊断与最终状态不一致时失败，包括漏报、误报、重复或陈旧诊断。普通产品调用保留容量、绑定、恢复和连续工作问题的诊断；显式验收仍可因真实终态违规失败，不能把这两种结果合并成“求解失败”。规则与两项豁免见[每周期休班底线](../定时换班.md#每周期休班底线目标规则)。

深海专用能力缺失时，普通降级保留请求 profile 的班数和时长，并在 `rotation_final_invariant:` 诊断中明确专用前提未成立。已删除的独立龙巫二班不是可降级的 profile；旧别名、wire 和 bundle 均明确报不支持。缺员仅保留当前合法候选，不回读全 roster，不拆除已形成的 required/bind，也不伪造专用动作或恢复组。质量 warnings 随正常 `Ok(TeamRotationReport)` 进入 CLI/Worker、profile 与 MAA；不依赖 `PLAN_FAILED` 的 partial result 通道。非法输入、资源加载/计算故障以及显式 assertion 失败继续使用错误通道；未迁移的构造拒绝必须作为实现缺口调查，而非产品规范。

人数不足由完成层统一处理：技能池少于满房人数不等于普通候选已经用尽，贸易不再通过总技能人数预检丢弃整份 Peak，合法空贸易池与制造 anchor 的普通 filler 不足保留已有岗位。六个当前 profile 与独立单班共用完整 assignment 普通补位；最终缺员、宿舍和休班诊断从实际结果重新生成，不保留补位前已失效的缺员 warning。显式 `ordinary_fallback_admission` / `ordinary_fallback_complete` 分别验证实际来源和声明的补位 policy 已稳定；普通房间人数低于容量本身不使 gate 失败，但仍有可加入合法候选、超容量或违反其他真实约束时照常失败。它们仍是验收门禁，不是正常产品拒绝输出的开关。

空贸易命中提交为空房，不要求不存在的单站收益分解；后续普通补位和终态结算继续消费该 assignment。夜烟贸易/制造的可选归属比较仅在两侧有同一实际候选且两侧 pick 都选中夜烟时启动；制造探测沿用普通填房的不足满员路径。没有可比较的夜烟冲突不能因为制造池不足三人而拒绝已有排班。该边界不吞输入、资源或正式机制结算错误，也不扩展通用能力影子设计。

`rotation_cycle_mood failed:` 是所有定时 profile 共用的周期心情预算拒绝：按最终 assignment 和实际班次时长累计同人跨设施工作，覆盖末班接首班，并拒绝整周期正消耗却无恢复的安排。错误列出干员、岗位和预算；候选阶段它是筛选条件；所有候选都被拒绝且已有完整排班时，降级为 `rotation_final_invariant:` 警告随结果返回，不再作为求解错误；公开断言重算时带 `assert-invariants` 前缀。`rotation_cycle_mood_unsupported_activity` 表示独立训练副手缺活动心情输入，不能被当作零消耗或已验证通过；训练室内无训练任务的占位按零小时消耗处理，不触发该错误。预算近似与加工事件边界见[全模式周期心情预算](../定时换班.md#全模式周期心情预算)。ABC 菲亚分支只跳过已识别的候选可行性错误；资源、输入和未知内部错误原样返回。

## 诊断证据顺序

1. 保存完整请求或文件输入的 hash/副本，避免只贴 stdout。
2. 记录命令、layout、operbox、rotation、top、数据目录和 commit。
3. 记录首个失败阶段及完整错误文本；区分输入失败、无解、超时和最终状态错误。
4. 若是已生成结果但某房错误，用 `layout eval --explain-json` 检查固定编制的正式结算 trace。
5. 若是生产 bundle，使用 `debug rerun`；它按 bundle 内联 snapshot 优先，按当前 executable/catalog 计算指纹，只比较稳定 assignment projection，不宣称 bit-identical。
6. 修复后分别重跑相同入口和适用的 `verify --case/--all`；不要用一次成功的 plan 代替全局保证。

不要把历史日志、旧 top hit、profile 或 baked catalog 当作当前规则真源。机制问题引用游戏机制知识库；实现问题沿[plan 请求](../调用链/plan请求.md)和代码锚点继续向 core owner 定位。
