## 1. 状态与范围

自动轮换是一个**独立排班入口**：为每个工作站给出主力与替补配置，让玩家使用游戏内置队列自行换班；不模拟全基建实际换班时刻、错班或普通宿舍恢复；菲亚目标的独立交换服务关系见第2.12节。当前入口为 `plan --rotation auto@H1/H2`，独立排班报告；共用排班步骤与验收见 [计算调用链](../调用链/自动轮换.md) 和第8节。

用户对模式的总体描述（2026-10-26 原话）：

> 自动轮换也只是去掉一些功能的正常排班。确定我说的对不对。你把工程量和难度混为一谈了。

出处：会话 `838409c4` L1416（2026-10-26T10:18）。这是一句模式定位，不是新增规则；本页把它作为理解后续裁决的上下文，不据此推导未裁决的实现细节。

当前范围：独立 core/CLI 排班入口，并由 Check 网页调用和呈现正式主力/替补配置；菲亚梅塔允许按既定静态优先级启用。2026-11-01 用户裁决覆盖历史“建议”“固定关闭”与“不接网站”的限制，见2.12；MAA及线上部署未纳入本轮。

### 2.13 2026-11-01 初始 ETA 与普通 Fallback

用户追问：“还有自动轮换为什么没有拦住地灵践行者这种。心情不足以支撑整个班次的人，我们有eta试算，你在哪里弄丢了”。据此补齐原先仅中枢存在的初始单人试算：主力和替补按各自H1/H2冻结每设施资格，普通技能候选与规则选人消费同一资格。试算只计满中枢基础减耗、计划满房人数和本人技能；不借未来中枢/同房减耗。办公室、会客室、贸易、制造、发电及回收均覆盖；最终组合仍保留真实ETA及warning。

用户随后明确：“Fallback不需要添加心情检查，直接随机塞人就行了，不需要检查任何东西，直接往里塞人。”因此普通Fallback从未占用的剩余持有人随机补真实空位，不作心情、技能、效率、组合或Plan候选准入；不复制技能搜索。它只消费调用方给出的剩余人手及空席，保留持有、容量、同人不重复、主备工作互斥的结构事实。实际Fallback成员写入assignment.fallback_operators，初始ETA门禁不把它误当成技能选择；最终心情诊断仍输出。此为用户授权policy，不保证最优或随机补位的技能兼容性。

用户补充：“在触发Fallback选人之后，生成一条warning提示。我是可用的干员太少，部分设施没法使用有技能的干员。”任一主备状态实际发生随机补位时，报告追加一条“可用干员太少，部分设施无法使用有技能的干员，已使用 Fallback 随机补位。”；未触发不提示，网页侧边原样呈现。

## 3. 已裁决的语义

以下每条都标注类型：**用户裁决**（有逐字原话或结构化答复）、**由原话推断**、**agent 建议默认**。只有前两类可以写成产品规则；第三类在用户确认前不得当作已裁决。

### 3.1 特殊两班制：每站一主一替、工作成员互斥、主力优先

- **用户裁决**：整体结构沿用主备轮换的“特殊两班制”（2.1 原话：“整体逻辑是与主备轮换是相似的，仍然是特殊的两班制”），但触发与输出不同（见第 4 节）。
- **用户裁决**：每站一主一替，不同站的主力和替补完全不同（工作成员互斥）。原话：“为每一个站设计完全不同的轮换组，只要保证1主1替补，不同站的主力和替补完全不同”（2.1）。
- **用户裁决**：主力优先，替补不齐时保留主力（第 5 题 `5A`，2.2）；第一次完成的工作名单绝不回选，后续心情问题只作质量诊断（2.11）。
- **用户裁决**（2026-10-28，2.6）：中枢也分主备、且互不重叠。结构化问答：“自动轮换里，控制中枢也分主力和替补吗？”=“分主备、不重叠 (Recommended)”。该条关闭第 6 节原第 1 项。

### 3.2 允许与禁止的协同

允许：

- 单站组合（第 2 题 `2禁用` 所选 A；2.1 原话“尽量使用纯粹的单站可以用的组合”）。
- 宿舍挂件 1＋1：一个常驻宿舍挂件 + 一个生产受益者；挂件可供主备共用（第 2 题 A、第 3 题 `3可以使用`）。
- 发电＋制造自动化组合（第 2 题 A；2.1 原话“自动化组合这个发电加制造的方式”）。
- 依赖建筑数量或等级、不要求其他站放特定干员的技能（第 2 题所选 A 的选项说明；该说明是 agent 文字，用户未逐字复述。用户的 2.1 原话直接支持中枢全局光环，没有逐字说建筑数量/等级类技能，但也没有把它列入禁止的跨站协同）。
- 中枢全局光环（2.1 原话“加贸易+7制造+3+2人力+10…全局光环”）。
- 中枢内部组合（第 4 题 `4允许`），但中枢全局光环优先。
- **用户裁决**（2026-10-28，2.6）：分类表放行边界——“只放行发电＋制造分支；莱茵宿舍 1＋1 按‘一挂件一受益者’放行，其余拒绝”。答句是“按 ADR 建议默认 (Recommended)”；清单内容是 agent 建议默认，因用户答句采纳而成为已裁决语义，不是用户逐字写出。该条关闭第 6 节原第 5 项。
- **用户裁决**（2026-10-28，2.6）：宿舍挂件 1＋1 不受 `support_combinations_enable` 总开关控制。结构化问答：“宿舍挂件 1+1 在自动轮换里受不受‘支持组合’总开关（support_combinations_enable）控制？”=“不受开关控制 (Recommended)”。该条关闭第 6 节原第 4 项。

禁止：

- 除上述例外外的其他跨站协同。第 2 题题干明确包括“制造站甲依赖制造站乙的特定成员”这类跨房间、同设施类型的关系（`auto-rotation.md:178-186`）。
- 四赤金。2026-10-28 结构化问答答“禁用”（2.5）。四赤金依赖全基建杜林人数和跨贸易房的虚拟赤金线，属于被禁止的跨站协同。
- 中枢内依赖指定生产站消费方的动态 producer（当前包括灵知、八幡海铃、戴菲恩等）在自动轮换中枢 roster 建立时直接排除，不进入候选枚举；不能先生成错误方案再由终检淘汰。普通中枢全局光环和中枢内部组合仍按允许项处理。

### 3.3 缺员标注

**用户裁决**（第 5 题 `5A`，2.2）：替补配不齐时，主力保持不变，替补先用普通散件补齐；仍无法补齐，标出具体缺员和方案不完整。2026-10-28 进一步裁决（2.6）：缺员“按建议默认”标注；标注内容是 agent 当时提出的默认方案（列出哪个站、哪个位置缺人，并标该站替补不完整；该站照常输出），因用户答句采纳而成为已裁决语义。该条关闭第 6 节原第 3 项。缺员输出保留实际岗位与显式Plan归属；心情不足与缺额分别提示，不作后续拒绝条件（2.11）。

### 3.4 时长评估

- 当前输入窗口仍为主力 H1、替补 H2；收益只算该时长，不模拟普通宿舍恢复或全基建长期周期；仅菲亚续班目标核对重复服务预算。工作预算筛选按2.11、2.13裁决限于最初正常技能候选的ETA roster；随机Fallback豁免。
- 完整组合、Plan后续前缀和普通补位均不做心情准入。实际同房技能与中枢用于正式效率、ETA和终态质量提示。
- 每房可独立选主或备，中枢也可切换。最终配置中，每房按其名单来源的 H1/H2 检查，不能把所有房统一按一段时长或只检查两套整班。
- 输入时长与初始ETA筛选是 policy；后续撑满窗口不再是候选或输出的 hard constraint。沿用有序竞争与搜索，不声称全局最优。

### 3.5 输出口径

## 4. 与定时轮换的区别

| 维度 | timed_rotation | auto_rotation |
|---|---|---|
| 触发与时间 | 固定班次表或有序时长（named profile、`main-backup@H1/H2`、`abc@H1/H2/H3`） | 没有求解器侧班次时刻；每站按红脸独立换班，输出正式主备配置（用户 2.1“不用考虑它实际上的错班或者轮换的问题”） |
| 输出 | `TeamRotationReport`：teams、shifts、按周期归一的 `daily`、`peak_mood_eta`，外部可投影到 MAA | 按站的正式主备排班配置；不进入 MAA（用户 2026-10-24） |
| 宿舍 | 有普通宿舍休息与周期安排 | 不安排普通宿舍（2.1“宿舍不用管”）；只保留已选 1＋1 挂件的常驻说明 |
| 菲亚梅塔 | 可按 profile 启用 | 按既定优先级支持目标同房续班（2.12，覆盖历史6A） |
| 评估时长 | 每班固定 `shift_hours` | 主力 H1、替补 H2（2.7） |
| 心情质量检查 | 完整周期诊断，gate核对提示准确性 | 不模拟普通恢复；菲亚续班单独核对共享预算，其余实际两态及混搭ETA不足只作质量提示（2.11） |
| 类型与报告复用 | `TimedRotationProfile`、`TeamRotationReport` | **agent 设计结论**：不扩展 `TimedRotationProfile`，不复用 `TeamRotationReport`；原因见 ADR 0014 第 2.2 节（定时语义会一并带入） |

用户 2026-10-24 还明确：“不要把自动轮换等同定时 generic 二/三班”（2.3）。因此不能用 `main-backup@H1/H2` 或 `abc@H1/H2/H3` 冒充自动轮换，也不能靠给 `timed_rotation` 加布尔开关来实现。

## 5. 保证等级

以下分类均为 **agent 建议默认**，用户未逐字裁决；用户已明确项目不承诺全局最优（2026-10-27 原话“我们也从来没有保证全局最优”，会话 `e235e78e` L3369）。

- 禁令（允许/禁止的协同、四赤金禁用）：**hard constraint**。禁止规则进入编排搜索；不保证零散选人和任意混搭没有偶发跨站关系（2.10）。
- 选人（主班、备班、缺员补位）：**heuristic**。沿用现有 Peak 与互斥备班构造，不声称全局最优。
- 时长评估及最初ETA筛选：**policy**。按输入窗口计算并参与比较；2.11删除后续工作预算准入，不声称能证明最优。
- 整体：不声称全局最优；不证明普通排班内部或跨 layout 的完整方案最优。

## 8. 当前实现责任

统一`schedule_rotation`按模式及时长分派独立排班入口。主中枢先定，公共Peak与普通补位完成第一次主力后冻结；替补排除主力非菲亚目标的工作成员、继承常驻宿舍。确认的菲亚目标以同房Plan锚点进入替补，队友仍由普通设施搜索选择。正常技能候选建池时按设施及H1/H2进行初始单人ETA筛选；中枢沿原试算；备中枢不再复筛固定主力，不回选、不缩H。

`restrict_auto_rotation_catalog`在角色递归前删除禁用alternatives；自动不调用兼容registry，因为其中现有条目均已由贸易规则处理或被本模式禁止。自动不走动态producer前缀候选/上界/排序，直接一次公共发电→贸易→制造填充；正常局部选人、Plan required和used占用、同房禁配、原效率公式保留。允许的中枢内部组合和普通夜烟归属比较不被误删。

宿舍挂件沿原角色临时环境和原设施搜索；受益者赢才提交anchor与active dependency。`orchestrate/auto_support.rs`只按显式producer→consumer及实际房号维护一挂件一受益者；同一房主备可以共享，不同工作房不能同时认领同一挂件。替补继承主力归属，终态从两份Plan和assignment独立重建，不扫描潜在技能或资源图。

初始普通工作候选由`OperBox::with_auto_roster_eta`冻结设施资格；规则、设施池及普通技能补位消费它。随机Fallback不复筛。最初单人中枢ETA由`mood::control_roster_fits`结算，`pool::admit_control_roster`在建池时消费；搜索和普通补位不复筛。已删除工时预算模块与候选owned成员物化。`auto_work_duration_issues`仅从最终两态及实际中枢重算质量提示，外站深海人数仍按各房主备最大人数诊断，不用于选人。制造负心情差与暖机仅参与请求窗口的真实效率积分。

已删除`layout/admission.rs`、CandidateAdmission、资源来源重演、房对及所有主备混搭穷举，删除相应全站presence与迁房身份。真实资源仍由普通resolve及设施solver结算；memo只保留实际收益layout、模式和H，不再携带已删除的工时预算状态。

显式gate独立重算最终两态的心情质量提示，漏报、误报或陈旧提示才失败，心情不足本身不失败。另核对身份、容量、工作互斥、受限目录中的Plan来源/无registry认领、显式挂件归属、房覆盖、缺额、H、ETA与效率快照；不检查任意混搭的禁用协同。输出每站主备、普通效率、效果、首人红脸、缺额、心情提示、常驻挂件说明与实际菲亚续班/交换记录，由Check通过独立CLI入口调用并复用排班呈现；仅菲亚目标使用共享恢复预算，不模拟普通宿舍；不进入MAA、plan.compute或日均产出。
