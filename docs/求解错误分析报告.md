# 求解错误分析报告

> 文档角色：current-reference
> 生命周期状态：current
> 当前真源：docs/QUALITY_AND_AUDIT.md
> 摘要：记录 operbox 求解错误的复现结果、首个失败阶段、原因和后续处理状态

## 1. 用途与边界

本文是可持续追加的求解错误调查记录，不是机制语义或求解保证的裁决文档。

每条记录应回答以下问题：

1. 哪个输入、布局、模式和命令产生了错误。
2. 错误首先出现在哪个阶段和代码责任边界。
3. 错误是输入失败、求解无解、运行超时还是最终状态校验失败。
4. 当前证据支持的直接原因、可能根因和仍未确认的事项。
5. 是否需要代码修复、数据修复、规则裁决或仅保留为账号不可行。

本文不以历史提交、旧输出或单个 top hit 推断当前行为。若旧日志与当前运行结果不同，以当前工作树和新鲜真实入口结果为准，并在记录中标明时间和版本状态。

## 2. 调查方法

### 2.1 标准记录字段

新增案例时复制以下结构：

```markdown
### ERR-YYYYMMDD-NNN：输入名称

- 调查时间：YYYY-MM-DD，时区
- 输入：`path/to/operbox.json`
- 布局：`path/to/layout.json`
- 模式：`Peak` / `ABC` / 其他
- 入口命令：完整命令
- 结果分类：`input_failure` / `solver_failure` / `timeout_failure` / `invariant_failure`
- 首个失败阶段：加载 / Plan / 单班编排 / ABC rotation / control fill / resolve / final invariant / 其他
- 错误原文：完整错误文本
- 直接原因：当前证据能直接证明的原因
- 可能根因：仍需代码或规则复核的上游原因
- 证据：日志、代码位置、输入事实
- 状态：`open` / `fixed` / `deferred` / `input_not_feasible`
- 后续动作：下一步调查或修复责任
```

### 2.2 结果分类

| 分类 | 含义 | 处理口径 |
|---|---|---|
| `input_failure` | operbox、布局或运行时数据无法加载/解析 | 先检查输入和数据版本，不进入求解根因判断 |
| `solver_failure` | 求解流程主动返回无解或约束冲突 | 定位首个返回错误的阶段和约束来源 |
| `timeout_failure` | 命令在规定时间内未完成 | 记录耗时、入口和搜索规模，不等同于无解 |
| `invariant_failure` | 已生成结果，但最终状态断言失败 | 检查最终 assignment、projection 和导出状态 |

### 2.3 证据要求

- 必须保留完整错误原文，不只记录摘要。
- 至少记录一次当前工作树的新鲜真实入口运行。
- 需要区分“输入拥有某干员”和“该干员在当前 Plan/班次中被 required、pin、used 或 exclusion 约束实际允许”。
- 对轮换错误，记录 active/resting 队伍、required anchors、shift binds、`used` 集合和过滤后的候选池；缺少这些信息时将根因标为待确认。
- 对最终断言错误，记录断言名、班次、期望值和实际值。

## 4. 调查记录

### ERR-20260827-001：28-325-operbox 中枢锚点容量超限

- 调查时间：2026-08-27，UTC+08:00
- 输入：[`28-325-operbox.json`](../data/fixtures/collected_operboxes/collected_operboxes/28-325-operbox.json)
- 布局：当前 CLI 默认 243 布局，运行日志未改变输入文件
- 模式：ABC 轮换，`12/6/6`
- 入口命令：`cargo run -q -p infra-cli -- plan --operbox data/fixtures/collected_operboxes/collected_operboxes/28-325-operbox.json --assert-invariants`
- 结果分类：`solver_failure`
- 首个失败阶段：ABC rotation 中每个活跃班次的 required control anchor pinning
- 错误原文：`active required control anchors exceed capacity: ["三角初华", "丰川祥子", "八幡海铃", "歌蕾蒂娅", "祐天寺若麦", "若叶睦"]`
- 直接原因：当前活跃班次被同时要求固定 6 名中枢干员，而中枢容量为 5 人。`team_rotation.rs:4535-4554` 构造 required 集合并在 `ops.len() > 5` 时直接返回该错误。
- 可能根因：Mujica fallback 的准入判断只检查已经进入统一 Plan 的组合；普通 ABC 的深海候选在 S2 后置分支才出现，因此没有被视为“已有其他中枢组合”，Mujica 先占满五席，随后歌蕾蒂娅被额外 pin。
- 证据：
  - 输入中六名干员均存在且为 `own=true`，因此不是 JSON 缺员或解析失败。
  - Mujica fallback 的 5 人 `min_count/max_count` 和 `bind_all` 定义见 [`data/orchestration_rules.json`](../data/orchestration_rules.json)（约第 5 行）。
  - 中枢容量检查见 [`team_rotation.rs`](../crates/infra-core/src/schedule/team_rotation.rs)（约第 4535 行）。
  - 当前批量结果为 `invariant_failures=0`、`solver_failures=2`、`input_failures=0`、`timeout_failures=0`。
- 状态：`open`
- 后续动作：已按用户裁决将可用深海组合纳入 Mujica fallback admission；继续检查其他后置中枢组合是否都在同一准入集合内。不得通过降低 required 或扩大中枢容量修复。

### 修复记录：Mujica 最低组合优先级（2026-08-27）

- 用户裁决：Mujica 是兜底组合。只要存在任何会占用中枢的其他完整组合，就不得启用 Mujica；只有没有任何组合、仅剩通用中枢加成时，Mujica 才可启用。Mujica 的优先级低于所有其他组合，但高于无组合的普通通用加成。
- 实现位置：[`select.rs`](../crates/infra-core/src/layout/orchestrate/select.rs)。已编译的 registry/声明式组合继续由 `has_other_cross_station` 判定；普通 ABC 的后置深海 S2 候选由 `has_usable_abyssal_combination` 纳入同一 admission 判断。
- 验证结果：28-325 当前 `plan --assert-invariants` 已通过 ABC 三班求解，不再出现 6 个 required control anchors 超过 5 席位的错误；35-343 仍有独立的 `control: no combo extending pins after pool filter`，不属于 Mujica 六人容量错误。
- 保证边界：本次修复按机制准入门槛识别深海组合：未被前置 Plan 占用的歌蕾蒂娅提供 `control_mp_aegir2[010]`，且另有至少 3 名 `cc.g.abyssal` 深海猎人；不把普通通用 control buff 当作组合，也没有修改中枢容量或静默丢弃 required anchor。制造站具体落位仍由 ABC S2 候选阶段处理。

### ERR-20260827-002：35-343-operbox 中枢补位无法扩展固定成员

- 调查时间：2026-08-27，UTC+08:00
- 输入：[`35-343-operbox.json`](../data/fixtures/collected_operboxes/collected_operboxes/35-343-operbox.json)
- 布局：当前 CLI 默认 243 布局，早期成功 profile 使用同一 243 布局和该 operbox
- 模式：ABC 轮换，`12/6/6`
- 入口命令：`cargo run -q -p infra-cli -- plan --operbox data/fixtures/collected_operboxes/collected_operboxes/35-343-operbox.json --assert-invariants`
- 结果分类：`solver_failure`
- 首个失败阶段：ABC rotation 的 `assign_ctrl`，进入 `assign_control` 的 control fill 搜索
- 错误原文：`control: no combo extending pins after pool filter`
- 直接原因：控制中枢已有 pin 后，`filter_control_pool_for_fill` 先排除 `used`、control exclusion 和自动排除候选；`search_control_combos` 返回的组合没有同时保留所有 pin 并满足未重复使用约束，因此 `pick_control_extending_pins` 返回空值并报错。相关路径见 [`control_fill.rs`](../crates/infra-core/src/layout/assign/control_fill.rs)（约第 220 行）。
- 可能根因：轮换阶段的生产队伍、共享脚手架或 required/rotating anchor 已占用了可用于补满中枢的候选；也可能是当前 Plan 的 pin 与 `used` 集合冲突。仅凭错误文本不能证明是账号缺少合法中枢角色，因为该账号曾在更早执行中生成完整 ABC profile。
- 证据：
  - 输入文件是合法数组，拥有 343 名干员，目标中枢相关干员均能在输入中找到。
  - 过滤逻辑见 [`control_fill.rs`](../crates/infra-core/src/layout/assign/control_fill.rs)（约第 265 行），pin 扩展检查见同文件（约第 301 行）。
  - 旧 profile 曾记录 `ABC 三班 12/6/6` 成功，但该证据不能覆盖当前工作树运行结果；它只说明失败依赖运行上下文或代码状态，而非静态输入格式错误。
  - 当前批量结果为 `invariant_failures=0`、`solver_failures=2`、`input_failures=0`、`timeout_failures=0`。
- 状态：`open`
- 后续动作：增加或采集失败前的 `active_names`、pin 列表、`used`、exclusions、过滤前后 pool 和组合搜索统计，定位是候选池不足、pin/used 冲突还是 Plan admission 错误。

## 5. 后续案例登记区

后续调查按编号递增追加到“当前案例总览”和“调查记录”。编号格式为 `ERR-YYYYMMDD-NNN`，同一日期从 `001` 开始。每次记录应保留：

- 新鲜命令及完整错误原文；
- 首个失败阶段，而不是最后一层包装错误；
- 输入/布局/运行时数据的路径或版本；
- 直接原因与未确认的可能根因分栏；
- 证据文件链接和状态；
- 修复后重新运行的结果，不覆盖旧失败证据。
