# 求解错误分析报告

> 文档角色：current-reference
> 生命周期状态：current
> 当前真源：self
> 摘要：记录求解失败的可复现输入、首个失败阶段、证据和后续动作
> 代码范围：`crates/infra-cli/src/commands/{plan.rs,serve.rs,debug.rs,layout.rs}`、`crates/infra-core/src/schedule/`、`layout/assign/`
> 代码锚点：`compute_plan_inner`、`rerun_cmd`、`assert_final_rotation_invariants`
> 关联链路：[错误与诊断](接口/错误与诊断.md)、[debug 与验证](调用链/debug与验证.md)
> 核验基线：每个案例至少一次当前 runtime fresh entrypoint

本页是调查台账，不是游戏机制或求解保证的真源。案例必须区分输入失败、求解失败、超时和最终状态断言失败；不得用历史日志覆盖当前代码事实。

## 记录模板

```markdown
### ERR-YYYYMMDD-NNN：简短名称

- 调查时间：YYYY-MM-DD +08:00
- 输入：路径或 hash
- 布局：路径或 hash
- 模式：rotation profile / fixed assignment
- 入口命令：完整命令
- 结果分类：input_failure / solver_failure / timeout_failure / invariant_failure
- 首个失败阶段：load / schema / plan / room / rotation / invariant / export
- 错误原文：完整文本
- 直接原因：当前证据能证明的内容
- 未确认事项：仍需代码、规则或用户裁决的内容
- 证据：代码锚点、产物、fresh run
- 状态：open / fixed / deferred / input_not_feasible
- 后续动作：责任 owner 和下一步
```

## 当前已知案例

仓库历史案例保留在 Git 记录中；新增案例应使用上面模板，并在 `docs/调用链/debug与验证.md` 规定的入口留下 fresh evidence。不要把某次 profile、top hit、绝对本机路径或旧 bundle 当作当前结论。

## 归因规则

- `input_failure`：先修输入或运行时数据，不进入 solver 根因判断；
- `solver_failure`：定位第一个返回错误的阶段和约束来源；
- `timeout_failure`：记录入口、top、搜索规模和耗时，不能等同无解；
- `invariant_failure`：结果已生成但最终 assignment/rotation 违反断言；
- `export_failure`：assignment 已正确，错误只在 MAA/profile/JSON 写出；
- `deferred`：证据不足或需要领域裁决，不得写成已修复。

失败 bundle 用 `debug rerun` 重放当前输入快照；`layout eval --explain-json` 只解释已选编制的结算，不回答候选为什么落败。修复提交应同时说明未验证边界。
