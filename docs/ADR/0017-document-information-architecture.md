# ADR 0017：文档信息架构与分工作流 TODO

> 文档角色：decision
> 生命周期状态：accepted
> 当前真源：docs/文档生命周期.md；docs/INDEX.md；docs/PROJECT_MAP.md
> 摘要：以三个根 hub、七个领域入口、五条 TODO 工作流和生成式全量目录建立可预测的文档检索路径
> 核验基线：2026-11-07 当前工作树

日期：2026-11-07。决策状态：用户明确要求“整个文档体系也要重新规划，保证能高效查找到需要的内容”，据此接受本信息架构。实施范围为文档目录、导航、生命周期元数据、生成索引和检查脚本；不改变任何求解、排班、接口或游戏机制语义。

## 1. 决策

文档入口按读者已知信息分层，不再要求先知道历史目录名：

| 已知信息 | 唯一首入口 | 责任 |
|---|---|---|
| 现象、报错或 bundle | `docs/生成索引/Agent路由.md` | route 到调用链、模块、机制与验证 |
| 问题领域 | `docs/INDEX.md` → 七个领域 `README.md` | 给推荐阅读顺序和领域 owner |
| 代码、数据或命令 | `docs/PROJECT_MAP.md` | 稳定源码 owner、入口和命令 |
| 全部页面、查漏 | `docs/生成索引/文档目录.md` | 按目录列角色、状态和摘要 |
| 当前开放工作 | `docs/TODO/README.md` | 按五条工作流进入详情 |
| 历史与长期决策 | `docs/ARCHIVE/`、`docs/ADR/` | 追溯完成记录、替代关系和裁决 |

`docs/` 根只保留 `INDEX.md`、`PROJECT_MAP.md` 和 `文档生命周期.md`。七个稳定主题入口是 `指南/`、`架构/`、`机制/`、`排班/`、`接入与前端/`、`质量与维护/`、`产品与训练/`。

## 2. TODO 层级

`docs/TODO/` 顶层只允许总板、五个工作流和 `详情/`：

- `核心求解.md`：候选、机制解释、Plan admission、跨设施状态和求解质量。
- `排班轮换.md`：profile、Team/Shift、事件、休息、回岗、bind 和跨班状态。
- `接口产品.md`：CLI、Worker、前端、训练室输出和网站产品。
- `性能质量.md`：正确性归因、搜索、Bake、cache 和验证。
- `文档协作.md`：Agent 规则、文档 owner、导航和门禁。

活动详情必须位于 `docs/TODO/详情/<工作流>/`，并在元数据写 `所属工作流`。workflow tracker 与详情一一对应；tracker 只提供状态和摘要，详情页拥有目标、证据、依赖和关闭条件。

## 3. 为什么这样分工

- 症状检索适合跨目录，不能要求读者先判断机制、排班或接口分类；因此 route 保持独立生成入口。
- 领域检索需要稳定阅读顺序和 canonical 注册表；因此七个主题 `README.md` 承接“知道问题属于哪类”的读者。
- 代码检索需要稳定 owner 和命令表；因此继续由 `PROJECT_MAP.md` 与生成的代码地图承接。
- TODO 原问题是一次性暴露四十多份活动文档，没有状态层次；五条工作流把选择问题缩成一层，详情仍保留各自完整证据。
- 标记优先、文档角色和 owner 规则是多份手工索引容易漂移的属性，适合生成；语义结论和历史背景仍由人维护。
- 全量目录作为兜底，不承担首屏导航。它保证任何受治理页面都能被找到，同时不迫使所有读者先读巨表。

## 4. 机械保证

`scripts/codex/doc_layout.py` 统一登记根 hub、主题入口、TODO tracker、详情组、ADR、ARCHIVE 和生成页路径。`docs_inventory.py` schema 5 检查：

- 角色、状态、摘要、当前 owner、领域键唯一性和生成器存在。
- `docs/` 根只能有旧三个 reference hub；七个领域 README 和五个 tracker 必须存在。
- `docs/TODO/` 顶层只允许总板、五个 tracker 和 `详情/`；详情根只允许五个已知工作流目录，组内只放详情或附件。
- 每个 `active-change` 只能位于已知详情组，`所属工作流` 必须匹配目录，tracker 必须覆盖本组每个详情恰好一次。
- canonical、ADR、TODO、七个领域目录和全量文档目录由确定性标记生成，手改会 drift fail。
- `doc_layout.py` 同时供 route 生成器、知识检索、仓库事实检查与 feedback 开放项校验使用，避免第二套路径常量。

目录、链接和 owner 检查只证明导航结构完整，不证明正文语义一致。两份 current 文档仍有冲突时登记在 `docs/TODO/详情/文档协作/文档真源冲突与循环核对.md`，保持 `blocked` 直到用户裁决。

## 5. 后果与边界

- 新增稳定领域文档前先判断应属于哪个主题入口；新增 open task 前先选择工作流并写 `所属工作流`。
- 关闭 task 时，先把事实吸收到 current owner，再归档详情并重建索引。
- 生成页不保存独占事实，不需要在每次正文修改时人工维护全量链接。
- 本次不迁移游戏机制正文、不合并相似但责任不同的活动项、不裁决 Bake 门禁或 owner 循环。
- 文档任务不运行 solver 或批量 Box；验证使用 inventory、生成器、仓库事实、知识检索和 Markdown 链接检查。
