## 背景

当前 `pozyomka_durin` 用跨站 Plan 表达绮良、鸿雪、图耶的四赤金组合。先前文档称它为“独立的跨站 Plan 核心”，容易让执行者误把它建模成普通 Trade Core 之外的另一种模式。用户于 2026-10-24 明确：四赤金应当是一种 `trade_core`。

本文只裁决产品分类、候选关系和不允许推导的边界，不声称当前实现已完成公平比较，不修改十月排班 ADR 0012 的历史交付判定。

## 决策

### D1. 候选分类

四赤金是 Trade Core 候选中的一种专用、跨站候选。跨站 Plan 是它的表达和构造方式，不代表它是独立排班模式，也不代表它可以绕开普通 Trade Core 的候选选择责任。

满足四赤金自身的准入条件时，它可以与普通完整 Trade Core 候选竞争；它不是必须采用的硬策略。四赤金不适用或完整候选无法合法完成时，应撤销整套四赤金候选并让普通 Trade Core 搜索继续，不保留半套核心。

### D2. 专用准入与可选搭配

继续沿用已确认的 `pozyomka_durin` 条件：四条真实赤金制造线、绮良/鸿雪/图耶三名核心均精二、四名杜林能在实际基建中兑现，并且存在恰为两座或三座的赤金金单贸易站。两站与三站的分房几何及核心同步轮休沿用 [`docs/调用链/plan请求.md`](../调用链/plan请求.md) 和 [`docs/模块/贸易求解.md`](../模块/贸易求解.md) 中的既有合同。

巫恋、龙舌兰、但书、可露希尔是优先建议，不是核心准入条件或必需 anchor。建议搭配缺失或无法落位时，可以省略；失败的建议成员回到普通 Trade 候选。不得因此把四人搭配变成完整四赤金候选的必要条件。

### D3. 比较对象与已知指标

当四赤金候选符合准入且完整 Plan 可以生成时，比较必须发生在同一个 Trade Core 候选选择责任中。双方必须从同一 Box、Layout、站位容量及共同求解约束出发，并比较各自完整、合法的 Trade Plan / assignment；不能拿四赤金的局部核心或未完成 Plan 与普通方案的完整结果比较。

用户已确认单房最终效率口径为 `TradeEfficiency::final_efficiency`：包括特殊订单单位产出倍率；`mechanic_equivalent_efficiency` 只是解释值，不可重复计入。不得以单独的 `total_efficiency` 替代该单房口径。

### D4. 尚未裁决的评分维度

现有决策没有唯一规定以下事项，执行者不得自行补成产品政策：

- 比较单次 Peak 的完整 assignment，还是完整轮换周期；
- 多个贸易站的 `final_efficiency` 如何聚合；
- 完整候选总分相同时如何裁决。

这些缺口只限制需要这些策略的候选择优实现，不妨碍独立调查候选生成、现有 consumer、完整 assignment 读取点、失败回退和证据边界。若既有 canonical 或用户会话不能唯一回答，评分器写入应按 `docs/QUALITY_AND_AUDIT.md` §2.3 记录 `PAUSE_REASON: CANONICAL_CONFLICT_OR_GAP`；不得把“对各站求和”等合理猜测写成已裁决规则。

## 后果与验收边界

- `pozyomka_durin` 应被理解为 Trade Core 候选类型，而不是与 Trade Core 并列的模式。
- 专用准入失败、完整候选失败与普通候选回退是不同阶段；可选搭配失败不应使三人核心自动失去准入。
- 当前 Plan 按顺序提交首个可行候选，尚未证明四赤金完整 Plan 与普通完整 Trade Plan 同场比较；本 ADR 不把当前代码或历史批次升级为完成证据。
- 即使未来比较器按已裁决口径完成，也只证明该候选集合及其明示评分策略；除非候选完备性与搜索保证另有证明，不得声称全局最优。
- 实现后需在同一真实输入上留存四赤金候选、普通 Trade Core 候选、双方完整最终 assignment、所用 Trade 指标与选择理由；代表与 high-owned Box 的 release gate 和适用独立复审按排班 active-change 执行。
