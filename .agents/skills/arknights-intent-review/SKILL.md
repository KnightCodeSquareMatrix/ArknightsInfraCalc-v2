# 意图复审

用户是这个项目的架构师，心里对模块归属和逻辑有清晰模型。复审不替代用户判断，也不重新设计方案；它只回答三个问题：

1. **照用户的想法改了吗**：用户要求的每一条都做到了吗？有没有多做（顺手加功能、扩大范围、加 TopK 之类没要的东西）？有没有把用户的裁决换成 agent 自己的理解？
2. **实现干净吗**：同一种计算是否只有一个地方负责？有没有新增重复或散落各处的同类计算、为某个 box/房间/班次写的特判、被替换后仍留着的旧路径或兼容分支？
3. **耦合代码还能正常工作吗**：被改部分的调用方和下游，原来依赖它的哪些前提（顺序、谁先写入、某个集合不会为空、某个值只算一次）？改动后这些前提还成立吗？

## 准绳

- 只用**改动之外**的材料当标准：用户原话、用户裁决（决策文档、ADR）、改动开始前版本的领域文档。
- 本次改动里刚改过的文档不能当准绳——它们和代码出自同一个作者，只能当被审对象。
- 复审者看不到主 agent 的解释、根因分析和自评结论；只看 diff、准绳和收集到的事实。

## 步骤

### 1. 冻结材料（主 agent）

记下改动的起点 commit 和终点 commit，整理：

- 用户原话：与本次改动相关的要求和裁决，原文引用，不改写。
- 准绳文档的路径，用起点 commit 的版本（`git show <base>:<path>`）。
- 改动范围：`git diff <base>..<head> --stat` 和完整 diff。

### 2. 收集事实（`simple-query`，可并行）

按下面三条拆成独立调查，各派一个或多个 `simple-query`，每份只交回带 `路径:行号` 和原文的事实清单，不下结论：

- **调用方与下游**：被改的函数、数据结构、输出被谁读取；读取方在改动前假设了什么（引用代码原文）。
- **同类计算**：仓库里还有哪些地方在算同一个东西或做同一种判断（包括本次没改的）。
- **旧路径残留**：被替换的逻辑在改动后是否还有调用、分支或兼容层。

### 3. 判断（新会话的强模型复审者）

只给它：用户原话、准绳文档（起点版本）、diff、第 2 步的事实清单。不给主 agent 的说明。

复审者按三个问题逐条判断，每条发现写清：

- 违反了哪条用户原话或裁决（引用原文）；或者哪个下游前提不再成立（引用事实清单）。
- 具体会出什么错：用一个能核对的例子说明（什么输入、原来怎样、现在怎样）。
- 证据不足时标"未查清"，不要猜。

复审者不重跑构建和测试，不提出替代架构，不审代码风格。

各工具可用的复审者：

| 工具 | 复审者 |
|---|---|
| Codex | `sol-blind-reviewer` |
| opencode | `sol-reviewer`；涉及候选、剪枝、目标时加 `solver-guarantee-reviewer`，涉及班次、心情、绑定、MAA 时加 `rotation-maa-reviewer` |
| Claude Code | 新开一个不继承上下文的强模型 subagent（不用 fork） |

### 4. 收口（主 agent）

每条发现只能落到三种结果之一，不能悄悄放过：

- **已修复**：改了，并说明改了什么。
- **有证据驳回**：引用代码或用户原话证明它不成立；"我觉得没问题"不算证据。
- **交给用户**：涉及用户语义或范围的取舍，用选项问用户，并给出推荐。

## 给用户的报告

用行为和逻辑讲，不用代码字段名代替解释。按三个问题分组，每组写：结论、具体例子、处理结果。没有发现的问题写"未发现"，不凑数。
